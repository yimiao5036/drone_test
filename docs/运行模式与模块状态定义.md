# 运行模式与模块状态定义

> 本文件是**运行模式**（`runtime.enable_control`）与**模块状态标记**的**唯一事实来源**。
> 其他文档写这两类概念时只引用本文件，不各自再写一份定义。
>
> 最后更新：2026-11-17（维护者决定：废弃"影子"作为状态词与分支依据）
>
> 历史定义（2026-09 ~ 2026-11-16 使用的"安全影子 / 影子链路"口径）已归档到
> [`archive/影子模式与状态标记-历史定义-2026-11-17.md`](archive/影子模式与状态标记-历史定义-2026-11-17.md)。

## 1. 为什么要重写

旧的"影子"一词同时被用在**两件完全不同的事**上，越用越含混：

| 旧用法 | 实际指的东西 | 问题 |
|---|---|---|
| "回纯影子" / "`enable_control=false` 影子运行" | **整机运行模式**：试飞期保险，程序只读不收控制 | 试飞完成后仍被当成"阶段"，装配层之外的功能也去判断它 |
| "TargetEstimator 是影子" / "影子链路" | **模块状态**：运行真实算法，但输出不产生控制 | 被误解成"还没做完"，掩盖了它是**设计边界** |

后果在 S13 拆两段（2026-11-17 P2）时暴露：设计稿写 `landing_descent_phase_ = (enable_control && …)`，
等于让状态机去判断"整机跑在哪条装配路径"。那会造出**两条都要测、现场分不清跑在哪条**的代码。
维护者当日的裁决是：**功能里不判断影子，只看能力**；本文件把这条原则固化成定义。

## 2. 运行模式（唯一开关：`runtime.enable_control`）

`config/config.json` → `runtime.enable_control`（bool）。它**只回答一个问题**：
**本次运行允不允许向 PX4 下发控制**。

| 模式 | `enable_control` | 装配行为 | 用途 |
|---|---|---|---|
| **控制运行** | `true` | `FlightController::SetPx4LinkSource()` 注入 + `Px4Link::SetInput(FlightController::SetpointOutput())` 绑定 + 状态机 `SetCommandSender()` 注入；启动打一次 WARN「正式控制输出已启用」 | **生产唯一正常模式**（2026-10-30 起为仓库默认） |
| **只读运行** | `false` | 以上三项全部不注入/不绑定：授权链恒不通过、保持 IDLE、`Px4Setpoint` 无消费者、命令接口物理缺席。只读遥测 + 视频 + 地面站回传 | 地面排查：事故后采日志、链路排查、新机体首上电 |

**控制运行 ≠ 什么都会发。** 具备控制能力之后，具体动作仍由各自的功能门禁决定：
`interception.enabled=false`（不自动拦截）、`actuator.gcs_fire_enabled=false`（65016 直控不装配）、
`landing.enabled`（S13 两段/回滚）、S9/S10 入口判据等。

### 2.1 硬规则：功能代码不得按运行模式分支

```text
✗ 禁止：if (enable_control) { … }        // 功能逻辑里判断整机装配模式
✓ 允许：if (command_sender_ != nullptr)  // 判断能力（命令接口是否真的注入）
✓ 允许：if (flight.home_valid)           // 判断数据（快照是否有效）
```

- **唯一允许读 `enable_control` 的地方**：`DroneApplication::BindTopics()` 的装配门禁，
  以及 `config.cpp` 的加载期校验（`enable_control=true` 必须同时启用 PX4 与地面站链路）。
- 功能内部一律按**可观测事实**判断能力：命令接口是否注入、Topic 是否绑定、快照字段是否有效。
- 理由：一旦功能内判断运行模式，就产生两条路径——**两条都要维护、都要测，且现场出故障时
  第一件要猜的事变成"现在跑在哪条"**。只读运行本来就只有"不发控制"这一个差别，
  由装配层一次做掉即可。

**既有落地例子**：S13 两段降落的入口判据是
`landing.enabled && command_sender_ != nullptr && !landing_takeover_`
（`src/state_machine/mission_state_machine.cpp`），不判断 `enable_control`。

### 2.2 回滚

| 场景 | 操作 |
|---|---|
| 现场需要只读排查 | `runtime.enable_control=false` 重启（日志出现"控制输出已禁用"而非 WARN） |
| 只停用某个功能，不停整机控制 | 用该功能自己的开关（`landing.enabled`、`interception.enabled`、`actuator.gcs_fire_enabled` 等） |

## 3. 模块状态标记

文档与代码边界统一用下面六种状态。**不再使用"影子"作为状态词**——历史文档里的"影子"
按时间读，含义见 §5。

| 状态 | 含义 | 判据 |
|---|---|---|
| **正式** | 已进入 `DroneApplication` 实际装配，输出被决策/控制链**消费** | 产物有真实消费者 |
| **观测** | 已进入实际装配，跑真实算法，但输出只进观测/诊断或**无消费者的影子 Topic**，不产生控制输出 | 产物存在且被记录，但无人据此控制 |
| **预留** | 接口、配置项或骨架已定，实现未接入 | 能找到接口/配置，但无生产实现 |
| **Stub** | 只有接口与占位生命周期，没有业务算法 | 方法返回默认值 |
| **独立** | 单独子工程/工具，不进入 `DroneApplication` | 自有 CMake，独立构建 |
| **阻塞** | 缺硬件资料、标定或实机条件，禁止猜测实现 | 有明确的外部前置 |

**"观测"不是"没做完"**，而是**设计边界**（例：`TargetEstimator` 只供状态机做交接判据参考与
热备份，本身不驱动控制；`StereoRanger` 只喂控制律距离通道）。若某模块确实"做了一半还没接"，
应标 **预留** 而不是"观测"。

## 5. 历史词对照

| 历史说法 | 现在应该怎么说 |
|---|---|
| "回纯影子" / "影子模式（`enable_control=false`）" | **只读运行**（§2） |
| "影子/正式由 `enable_control` 门禁决定" | 运行模式决定；模块状态见 §3 |
| "TargetEstimator 是影子" / "影子链路" | **观测**（§3）；数据流章节叫"观测链路" |
| "影子意图"（`VisualTrackingShadow`） | 该 Topic **无消费者**；不是"暂时没接"，是永不接线 |

## 6. 修改指引

新增功能时按顺序自问：

1. **它需要控制输出吗？** 不需要 → 产物进观测/诊断，模块标"观测"，不要新增控制意图。
2. **它需要发指令/设定值吗？** 需要 → 只能在 `command_sender_ != nullptr` / 控制器已绑定的前提下发，
   **不要**判断 `enable_control`，也不要读 `config.runtime`。
3. **它有独立开关吗？** 有 → 回滚粒度就落在那个开关上；别用 `enable_control` 当功能开关。
4. **文档怎么写状态？** 用本文件 §3 的六种状态之一；不要再用"影子"。

违反 §2.1 的写法应在代码评审中直接打回。
