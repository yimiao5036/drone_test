# YOLO26在RK3588上的性能来源核查

> 核查日期：2026-09-09  
> 外部项目：https://github.com/li2390893/yolo26-rk3588-cpp  
> 核查提交：`db83c751b2eb55998b88f06084e6b294e1573739`  
> 官方RKNN来源：https://github.com/airockchip/rknn-toolkit2  
> 当前板端：RKNN SDK 2.3.2、驱动0.9.8、NPU governor=`rknpu_ondemand`、采样频率1GHz

## 1. 本项目实测

当前模型`models/yolo26n-drone-best.rknn`：

- 文件约4.6MB，SHA-256：`e1402bc4721da39e30c0a28131b9a4bf57103b7d51414f4186fa4cebf8195eeb`；
- RKNN编译器2.3.2，目标RK3588；
- 输入`[1,3,640,640]`，原始float32归一化，RKNN内部INT8；
- 输出`[1,5,8400]` INT8，单类别；
- 使用`rknn_create_mem + rknn_set_io_mem`绑定输入输出，单帧调用`rknn_run(ctxs_[0])`；
- `ctxs_[0]`设置`RKNN_NPU_CORE_ALL`。

香橙派120秒实测：

| 阶段 | 平均 |
|---|---:|
| RGA缩放与颜色转换 | 约2.5～3.2ms |
| CPU letterbox | 约0.3ms |
| `rknn_run` | 约24～29ms |
| 输出布局转换 | 约0.01ms |
| 阈值过滤/NMS | 约0.13～0.20ms |

因此当前主要计算瓶颈是模型在NPU上的执行，不是单类后处理。

## 2. 用户提供的Python片段核查

官方`rknn_toolkit_lite2-2.3.2` wheel中，`RKNNLite.init_runtime`签名为：

```python
def init_runtime(self, target=None, device_id=None,
                 async_mode=False, core_mask=NPU_CORE_AUTO)
```

没有`zero_copy`参数。因此：

```python
rknn.init_runtime(..., zero_copy=True)
```

不是RKNNLite 2.3.2有效调用，会产生参数错误。官方`RKNNLite.inference()`内部仍按`set_inputs → run → get_outputs`执行，不能因为传入numpy数组就称为`rknn_create_mem/rknn_set_io_mem`零拷贝。

“单核12ms、三核4.8ms、三核零拷贝4.2ms”的片段只是对同一个同步`inference()`循环计时，没有三个并发请求、三个上下文或三个工作线程。`NPU_CORE_0_1_2`表示单次模型运行允许组合核心，并不等于把单核耗时简单除以3。代码中的预期数字没有可复现日志、模型哈希、RKNN转换参数、温度/频率或统计分位依据。

该片段还存在接口/后处理不一致：

- `get_sdk_version()`返回SDK版本，不是tensor名称；
- 假定输出`[1,84,8400]`，与本项目`[1,5,8400]`不一致；
- `scores`过滤后再次用原mask索引，并对一维数组按`axis=1`执行`argmax`，逻辑不成立；
- 直接resize到640×640会改变16:9画面比例，与本项目letterbox语义不同。

因此不能用该片段的“预期结果”作为本项目性能基准。

## 3. 外部C++仓库核查

外部仓库当前实现：

- 只创建一个RKNN context，未调用`rknn_set_core_mask`，使用默认AUTO；
- 使用`rknn_inputs_set + rknn_run + rknn_outputs_get`，没有使用`rknn_create_mem/rknn_set_io_mem`；
- 预处理使用OpenCV `copyMakeBorder/cvtColor/resize/memcpy`，不是RGA；
- 输出获取后再次复制到自定义buffer；
- 源码逐帧`printf`预处理/推理/后处理时间；
- README和源码中没有用户表格所列15ms/55FPS或4.8ms/208FPS数据。

仓库README还明确记录：其“原始结构n、s量化模型都无法正常推理出结果，此问题待解决”。因此该仓库可以参考YOLO26模型转换和输出兼容思路，但不能直接作为本项目低延迟实现或量化模型正确性的证明。

外部`yolo26n-original.int.rknn`：

- 约4.7MB；
- SHA-256：`7688918a31844681354243f9c1999de1b8446793dece93860a49d7348c50253d`；
- 输出`[1,300,6]`，与本项目`[1,5,8400]`不同。

模型图、导出方式和输出结构不同，不能只按“YOLO26n 640 INT8”名称横向比较。

## 4. 单类别为何不会让NPU快很多

单类别主要减少检测头的类别通道和CPU后处理工作；YOLO的大部分计算量位于backbone和neck。当前Y4后处理实测仅约0.15ms，已经证明单类别收益主要不在后处理之外。若网络主体结构、输入640×640和算子图不变，类别数从80降到1通常不会让整个`rknn_run`按类别比例下降。

## 5. 可复现对比所需条件

任何“15ms”数据必须同时冻结：

1. RKNN模型文件及SHA-256；
2. 输入尺寸、布局、量化方式；
3. 输出结构及是否把NMS融合进模型；
4. RKNN Toolkit/Runtime/驱动版本；
5. core mask；
6. NPU governor与频率；
7. 是否只测`rknn_run`还是包含输入输出；
8. warmup次数、样本数、P50/P95/P99；
9. 板卡温度和同时运行的RGA/编码任务。

缺少这些信息的网上FPS表只能作为目标参考，不能作为缺陷判据。

## 6. 后续验证顺序

1. 保持当前模型和数据通路不变，使用探针`--npu-core all/core012/core01/core0/auto`做Y2 A/B；生产仍为`all`；
2. 旧实现“创建3个上下文但只运行ctx0”已清理为单上下文，删除未使用的两套模型I/O内存；组合多核由该上下文core mask控制，不预期无依据的3倍加速；
3. 同步记录NPU频率和温度，确认`rknpu_ondemand`是否导致首段升频延迟；
4. 若仍需明显降低Y2，再用同一验证集比较640与480/512模型的召回率和小目标精度；
5. 不优先优化Y3/Y4，它们合计不足0.3ms。

## 7. 当前结论

本项目当前24～29ms的`rknn_run`数据是板端真实模型、真实视频并行负载下的墙钟统计。用户提供的Python“零拷贝/三核4.2ms”代码与RKNNLite 2.3.2官方接口不符；外部C++仓库也没有使用零拷贝、RGA或显式三核，更没有提供相应性能证据。当前已提供同一模型core mask A/B并清理无效上下文，后续以板端Y2分位决定模式，而不是按不可复现数字修改模型。
