# 多机身份与功能寻址设计

> 文档状态：方案冻结；C++配置与GroundStationLink下行身份已实施，Vue3二元键改造和自定义目标协议仍待完成  
> 创建日期：2026-09-01  
> 适用范围：Orange Pi机载电脑与自研Vue3地面站之间的HM30 MAVLink 2数传链路  
> 不适用范围：Orange Pi与PX4之间的本机串口链路

## 1. 背景与目标

系统将从单架飞机扩展为“一套地面站管理多架不同功能飞机”。现有每架飞机内部均使用PX4默认MAVLink身份，不希望因机队扩展而修改PX4固件参数：

```text
PX4：system=1, component=1
Orange Pi面对PX4：system=1, component=191
```

Orange Pi与PX4、Orange Pi与地面站是两条独立物理链路，分别拥有独立串口、`MavlinkHandler`、发送序号和协议上下文。因此地面站链路不复用PX4链路身份，而重新定义机队寻址规则。

本设计目标：

1. 不修改PX4默认system/component ID；
2. 地面站能直接从MAVLink帧头区分“飞机功能类别”和“同类别编号”；
3. 支持捕网类、火箭类及后续新增类型；
4. 地面站能精确向某一类型的某一号飞机发送消息；
5. 标准遥测继续复用MAVLink `common`消息，不为每条姿态/GPS/电池数据重复增加身份字段；
6. 为后续目标位置、任务状态、健康状态和功能命令的自定义dialect预留一致身份规则。

## 2. 核心决策

### 2.1 两条MAVLink链路身份完全独立

PX4链路固定：

```text
Orange Pi → PX4：source=1/191，target=1/1
PX4 → Orange Pi：source=1/1
```

地面站链路重新配置：

```text
飞机 → 地面站：source=(aircraft_system_id, aircraft_component_id)
地面站 → 飞机：source=255/190，target=(aircraft_system_id, aircraft_component_id)
```

地面站链路身份变化不影响PX4链路，也不要求修改PX4的`MAV_SYS_ID`。

### 2.2 system ID表达同类别编号

地面站链路中：

```text
system_id = aircraft_number = 同功能类别中的飞机编号
```

规则：

- 有效编号暂定1～254；
- 0不分配，保留广播/未指定语义；
- 编号在每个功能类别内部独立计数；
- system ID不是PX4 system ID，两者仅数值可能相同，协议上下文完全独立。

### 2.3 component ID表达飞机功能类别

地面站链路中：

```text
component_id = aircraft_type = 飞机功能类别
```

使用MAVLink预留的用户组件ID，避免占用官方标准组件语义：

| component ID | MAVLink名称 | 项目定义 | 状态 |
|---:|---|---|---|
| 25 | `MAV_COMP_ID_USER1` | 捕网类飞机 | 已冻结 |
| 26 | `MAV_COMP_ID_USER2` | 火箭类飞机 | 已冻结 |
| 27～99 | `MAV_COMP_ID_USER3～75` | 未定义 | 全部预留 |

当前只确认捕网类和火箭类，不对其他飞机类型作任何猜测或预命名。27～99仅保留数值空间，不代表侦察、中继、测试或任何其他具体功能。新增类型必须由维护者确认后，再更新本表、dialect、配置校验和两端实现；不得在代码、Vue3或配置中私自占用预留值。

### 2.4 飞机身份是二元组

正式身份键：

```text
AircraftAddress = (aircraft_system_id, aircraft_component_id)
                = (同类编号, 功能类别)
```

示例：

| 飞机 | system ID | component ID | 身份键 |
|---|---:|---:|---|
| 捕网-01 | 1 | 25 | `(1,25)` |
| 捕网-02 | 2 | 25 | `(2,25)` |
| 火箭-01 | 1 | 26 | `(1,26)` |
| 火箭-02 | 2 | 26 | `(2,26)` |

`system_id`可在不同类别间重复；任何地面站数据结构、路由表、心跳表和任务表都必须使用二元组，禁止只用system ID作为主键。

## 3. 配置设计

### 3.1 捕网类1号

```json
"px4": {
    "onboard_system_id": 1,
    "onboard_component_id": 191,
    "target_system_id": 1,
    "target_component_id": 1
},
"ground_station": {
    "aircraft_system_id": 1,
    "aircraft_component_id": 25,
    "aircraft_type": "net_capture",
    "aircraft_number": 1,
    "callsign": "捕网-01",
    "ground_system_id": 255,
    "ground_component_id": 190
}
```

### 3.2 火箭类1号

```json
"ground_station": {
    "aircraft_system_id": 1,
    "aircraft_component_id": 26,
    "aircraft_type": "rocket",
    "aircraft_number": 1,
    "callsign": "火箭-01",
    "ground_system_id": 255,
    "ground_component_id": 190
}
```

### 3.3 字段语义

| 字段 | 含义 |
|---|---|
| `aircraft_system_id` | 地面站链路中的同类别飞机编号，等于`aircraft_number` |
| `aircraft_component_id` | 地面站链路中的飞机功能类别ID |
| `aircraft_type` | 可读类型名称，用于配置审查和双重校验 |
| `aircraft_number` | 同类别业务编号 |
| `callsign` | 界面与日志显示名称，不参与协议寻址 |
| `ground_system_id` | 地面站来源system ID，当前固定255 |
| `ground_component_id` | 地面站来源component ID，当前固定190 |

原地面站配置中的`onboard_component_id`应改名为`aircraft_component_id`，避免继续暗示其必须是标准机载电脑组件191。

## 4. 配置校验规则

启动期必须严格校验：

1. `aircraft_system_id`在1～254；
2. `aircraft_number`在1～254；
3. `aircraft_system_id == aircraft_number`；
4. `aircraft_type="net_capture"`时component必须为25；
5. `aircraft_type="rocket"`时component必须为26；
6. `callsign`不能为空；
7. 地面站system/component当前必须为255/190；
8. PX4链路身份继续独立校验，不得被地面站身份覆盖；
9. 发现未知类型或类型与component不匹配时拒绝启动，不做猜测或自动修正。

错误示例：

```json
{
    "aircraft_system_id": 1,
    "aircraft_component_id": 26,
    "aircraft_type": "net_capture",
    "aircraft_number": 1
}
```

该配置声明为捕网类但component 26属于火箭类，必须拒绝。

## 5. MAVLink帧头表现

### 5.1 捕网类1号发送ATTITUDE

MAVLink 2帧头示意：

```text
FD 1C 00 00 SEQ 01 19 1E 00 00 ...
```

其中：

```text
01 = system ID 1
19 = component ID 25
1E 00 00 = message ID 30，ATTITUDE
```

### 5.2 火箭类1号发送ATTITUDE

```text
FD 1C 00 00 SEQ 01 1A 1E 00 00 ...
```

其中：

```text
01 = system ID 1
1A = component ID 26
```

### 5.3 地面站发送消息

地面站来源固定：

```text
source_system=255
source_component=190
```

发给捕网类2号：

```text
target_system=2
target_component=25
```

发给火箭类2号：

```text
target_system=2
target_component=26
```

## 6. 地面站数据模型

Vue3通信层及后端不得再以system ID单独保存飞机：

```javascript
// 禁止
vehicles.get(systemId)
```

必须使用二元键：

```javascript
function MakeAircraftKey(systemId, componentId) {
  return `${componentId}:${systemId}`
}
```

示例：

```text
25:1 → 捕网-01
25:2 → 捕网-02
26:1 → 火箭-01
26:2 → 火箭-02
```

每个身份键独立维护：

```text
connected
lastHeartbeatTime
lastAttitudeTime
lastPositionTime
lastGpsTime
lastBatteryTime
attitude
localPosition
globalPosition
gps
battery
mission
health
```

同一个system ID下出现不同component ID是不同飞机，不得合并为同一“系统组件列表”。

## 7. 心跳与发现

### 7.1 飞机心跳

每架飞机按自己的二元身份发送：

```text
捕网-01：source=1/25
火箭-01：source=1/26
```

地面站按二元组维护连接超时。

### 7.2 地面站心跳

地面站统一发送：

```text
source=255/190
type=MAV_TYPE_GCS
autopilot=MAV_AUTOPILOT_INVALID
```

当前`HEARTBEAT`没有目标字段，因此所有飞机都可接收。后续每架飞机只将合法255/190心跳计为地面站在线，是否增加来源白名单或签名属于后续安全阶段。

### 7.3 身份声明

标准`HEARTBEAT`不能携带`aircraft_type`、`aircraft_number`和`callsign`。后续自定义dialect应增加`AIRCRAFT_IDENTITY`或`AIRCRAFT_ANNOUNCE`，至少包含：

```text
aircraft_system_id
aircraft_component_id
aircraft_type
aircraft_number
callsign
protocol_version
capability_bits
boot_id
```

地面站收到后校验Payload声明与MAVLink帧头来源一致。不一致时标记身份冲突并禁止任务下发。

## 8. 任务与功能消息寻址

### 8.1 双字段精确寻址

所有任务、目标位置、载荷授权和功能命令必须同时包含：

```text
target_system
target_component
```

机载端必须同时匹配本机配置：

```cpp
目标system匹配 && 目标component匹配
```

只匹配其中一个不得接受。

### 8.2 广播限制

安全查询可按后续协议允许广播；以下消息默认禁止广播：

- 任务分配；
- 目标位置更新；
- 模式切换；
- 解锁/上锁；
- 起飞/降落/返航；
- 捕网执行授权；
- 火箭类载荷相关授权与执行；
- 任何会改变飞行状态或载荷状态的命令。

这些消息要求：

```text
target_system != 0
target_component != 0
```

### 8.3 功能门禁

component ID不仅用于显示类型，也参与机载端功能门禁：

- component 25只接受捕网类协议允许的功能命令；
- component 26只接受火箭类协议允许的功能命令；
- 公共状态查询和链路消息按统一协议处理；
- 地面站界面门禁不能替代机载端校验，两端都必须验证。

具体功能消息、授权流程和安全条件需在对应载荷设计确认后单独冻结，本文件不定义执行细节。

## 9. 标准MAVLink兼容性边界

标准MAVLink生态通常将相同system ID、不同component ID解释为同一系统中的多个组件。本项目地面站链路明确采用私有语义：

```text
(system ID, component ID)共同表示一架飞机
```

因此：

1. 正式多机地面站必须使用自研通信层；
2. QGC仅可用于单链路抓包和基础消息调试，不能作为正式多机身份展示依据；
3. MAVLink路由器若只按system ID建表，会合并“捕网-01”和“火箭-01”，使用前必须确认支持二元路由或做项目适配；
4. 任何中间层都必须保留component ID，禁止只向上层传system ID；
5. 日志必须打印完整`system/component`，例如`source=1/25`。

这是本方案换取“不修改PX4、每类可独立编号1～254”的明确取舍。

## 10. 重复与冲突检测

地面站必须检测：

1. 同一二元身份从两条不同物理链路同时出现；
2. 同一链路短时间内出现互相冲突的身份声明；
3. 同一callsign对应多个二元身份；
4. 身份声明Payload与MAVLink帧头不一致；
5. 类型映射与冻结表不一致。

发生冲突时：

- 显示红色告警；
- 禁止向冲突身份发送任务或功能命令；
- 保留链路地址、首次/最近接收时间和消息计数；
- 不采用“最新消息覆盖”自动消除冲突。

## 11. 永久物理身份预留

`(aircraft_type, aircraft_number)`表示机队业务身份，例如“捕网-02”，可能在设备替换后继续沿用。为了未来维修记录和设备追踪，协议应预留128位`aircraft_uuid`：

```text
业务身份：捕网-02，可转移
物理身份：aircraft_uuid，不随软件升级或PX4更换改变
```

第一阶段可不依赖UUID完成实时寻址，但自定义身份消息和地面站数据库设计不应阻止后续加入。

## 13. 当前冻结结论

```text
PX4链路：
  Orange Pi source = 1/191
  PX4 target        = 1/1

地面站：
  source = 255/190

捕网类N号：
  source/target = N/25

火箭类N号：
  source/target = N/26

正式飞机身份键：
  (system_id, component_id)
  = (同类编号, 功能类别)
```

捕网类与火箭类的功能执行协议、安全授权和目标位置格式将在后续专项设计中定义；在协议冻结和测试完成前，不启用任何新增控制或载荷输出。
