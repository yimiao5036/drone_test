### 2.2 “到达目标后，多久不识别会返航？”

**现状：没有这条规则。** 只要地面站持续给目标，S5 可以无限等视觉锁定。

`EvaluateTargetWatchdog()`（`src/state_machine/mission_state_machine.cpp:1601`）只在
`kGpsApproach` 且 `command_sender_ != nullptr` 时生效，三条判据（`include/config/config.h:246-251`）：

| 配置 | 默认 | 含义 |
|---|---|---|
| `takeoff.target_wait_timeout_ms` | 10000 | 进 S5 后**从未**拿到新鲜目标 |
| `takeoff.target_lost_timeout_ms` | 10000 | 拿到过，之后连续失效 10 s |
| `takeoff.target_hold_max_ms` | 60000 | 本次 S5 内“原地保持”累计 60 s |

三条都走 `AbortForTargetWatchdog()` → S12 返航。

为什么 0100 里 3.5 分钟没自动返航：地面站 65010 实测 **5 Hz** 持续送达
（`count` 300→1200，每包 `valid_for_ms=999`），`HasFreshEstimate()`
（`:3371`）每拍为真 → 三个计时器都不启动；视觉侧整段
`state=SEARCHING valid=false … 从未检测`，也不会进 S6。
直到 22:16:40 用户手动 65020（`command_id=2801664001`）才 `GPS_APPROACH -> RETURN_HOME`。

**结论**：“到达目标点但视觉始终不识别”目前没有任何超时或提示，只有人工返航或电量兜底。

### 4.2 机载（`src/state_machine/mission_state_machine.cpp`）

现有代码里**没有“到点”概念**，S5 每拍只是 `EvaluateEstimateGuidedIntent()` 把目标位置交给控制器；
S5→S6 只由 `EvaluateVisualHandover()`（`:3201`）在视觉 `LOCKED` 连续帧超过
`handover.lock_frames=10` 时驱动。建议新增：

1. **到点判定**：水平 ≤ `arrival_radius_m`（建议 3.0）、垂直 ≤ `arrival_vertical_m`（2.0）、
   速度 ≤ 0.5 m/s、持续 `arrival_hold_ms`（2000），带迟滞；
2. **到点后视觉等待计时**：`handover.visual_wait_warn_ms`（建议 20000）到点置告警位，
   `handover.visual_wait_abort_ms`（默认 0 = 不自动处置）；
3. **不能复用 `PublishTargetHoldIntent()`**：那条路径会计入 `target_hold_accumulated_ms_`，
   60 s 后触发 `AbortForTargetWatchdog()` → S12，与“一直等”冲突；到达等待需单独的状态标志；
4. **告警位**：现有 `kWarningTargetHold = 1U << 5U`（`mission_state_machine.cpp:87` 附近），
   65013 的 `active_warning_bits` 已能上报；建议新增 bit6「到点未识别」，
   同步 `docs/数据接口文档.md` 与前端 `StatusPanel.vue` 的 `WARNING_BITS` 表；
5. **退出条件**：视觉锁定 → S6；目标移动超出半径 → 重新接近并重新计时；人工返航立即生效；
   低电走 `TriggerBatteryAbort()`（PX4 `BAT_LOW_THR` + `takeoff.battery_low_debounce`）。

## 7. 环境备注（避免重复踩坑）

- WSL `Ubuntu` 24.04.1 的 Node 已升到 **v26.13.0**（`/usr/local/bin/node`，npm 11.20.0），
  `tools/web平台` 在 WSL 内可跑 `npm test`（112/112）；
- **WSL 虚拟机时基比 Windows 慢约 9%**：机载 `steady_clock` 与 Web `process.hrtime.bigint()`
  不同源时，TIMESYNC 的 `offset` 每秒涨 ~91 ms，贴着 `max_offset_jump_ms=100`，
  每 2~3 s 抖一次 `DEGRADED` → 65010 上行点全部被 `TIME_SYNC_UNAVAILABLE` 拒绝。
  规避：Web 服务端跑在 WSL 内（同钟），或设备两端都是被 NTP 校时的真时钟；
  根治方向是代码做漂移容忍（offset 线性拟合 + 残差判跳变），**尚未实施**；

## 13. PX4 解锁前置（GCS 心跳）仿真核实与修正（2026-11-05）

### 13.1 结论

PX4 的 `Preflight Fail: No connection to the GCS` **只看 PX4 自己那条 MAVLink**
（SITL 为 UDP 14550；实机为 TELEM 口）上有没有 `MAV_TYPE_GCS` 心跳。
Web 地面站的心跳走 `/tmp/gcs_app → /tmp/gcs_test` 的**机载地面站链路**，到不了 PX4，
因此"Web 连上"不能替代 GCS——这也解释了为什么现场 0100 会话里 Web 未连接时解锁被拒。

### 13.2 三组实测（WSL2 + PX4 SITL，`tools/sitl_harness.sh`）

| 组 | 条件 | 结果 |
|---|---|---|
| A | `stack`（`sitl_gcs.py` 在跑，14550 有 255/190 心跳） | `commander arm` 通过；PX4 日志无 GCS 报错 |
| B | 停掉 `sitl_gcs.py`，另起一个只发 255/190 心跳的脚本占 14550 并外部下发 `MAV_CMD_COMPONENT_ARM_DISARM` | `COMMAND_ACK result=0`（ACCEPTED），解锁成功 → **14550 上的 GCS 心跳就是前置条件本身** |
| C | 同上但**不发**心跳（占着 14550 也不发），15 s 后外部下发 arm | `COMMAND_ACK result=1`（TEMPORARILY_REJECTED），PX4 日志 `Preflight Fail: No connection to the GCS` |

结论：只要 14550 上有 255/190 的 `MAV_TYPE_GCS` 心跳就能解锁，与 Web 是否连接无关；
反过来掐掉它必然拒解锁。

### 13.3 修正

- `tools/sitl_harness.sh`：原 `webgcs` 分支会 `pkill sitl_gcs`（注释写的"抢心跳"不成立，

## 14. 动点（移动目标）地图表现：分段 / 方向 / 预测航迹 / 清除轨迹（2026-11-05）

现场反馈三条：①「这个给了方向，但地图上的点我得知道他向哪个方向要跑」；②「不能删除
轨迹，重新打点再跑，会把之前的轨迹连起来」；③「跑起来后有两个点，一个在原地、一个在
运动」。全部是前端可视化问题，机载与协议零改动。

### 14.1 根因

| 现象 | 根因 |
|---|---|
| 两个点 | 静态点是「地图选点」`store.selectedCoordinate`（橙色实心点，永远不动）；动点是 `target-tracks` 里每条轨迹末尾追加的「当前位置」圆点。两者本来就是两个不同东西，但长得一样、都没有标注。 |
| 轨迹连起来 | `store.targetSamples` 按飞机累积，只按 `elapsedSeconds` 去重，**没有分段**；`targetTrackFeatures()` 把同 `飞机#目标` 的全部采样连成一条 `LineString`，换起点后线段横穿场地。服务端 `repeatTargetUpdate()` 每拍按 `p(t)=p₀+v·t` 现算、不存历史，前端清采样是安全的。 |
| 没有方向 | 轨迹头只是 `circle-radius: 5` 的圆点，既没有箭头也没有预测线；而 `TargetSample.headingDeg` 与 `TargetRepeatState.motion/progress` 里本来就有方向与剩余量。 |

### 14.2 做法（`tools/web平台/`）

- **分段**：`TargetSample` 新增前端派生字段 `segment?: number`；`appendTargetSample()` 在
  「时间回退（`elapsedSeconds` 变小）」或「单步位移 > `max(3×速度×时长, 50 m)`」时把上一段
  封口、另起一段。阈值取「速度自适应 + 50 m 下限」是因为目标速度可设到 50 m/s，单拍位移
  就是 50 m，固定阈值会把正常推进误判成换点。`targetTrackFeatures()` 按 `飞机#目标#段`
  分组，每组一条线，天然断开。
- **方向**：
  - 当前位置盖一个随航向旋转的箭头（Canvas 图标 `target-arrow`，与飞机箭头同一套画法，
    不依赖 `style.glyphs`）；航向优先用服务端随采样下发的 `headingDeg`，缺失时退回
    「最近两点的实际走向」，两者都没有就**不画方向**（不用 0° 假装朝北）。
  - 预测航迹：从当前位置沿航向画一条虚线到预测停止点，长度 = 按距离时的剩余路程 /
    按时长时的 `速度×剩余时长` / 手动停止时预览 200 m，上限 5 km；终点画空心圈 +
    「终点 120 m」。
  - **实线=已走过的轨迹、虚线=将要走的预测航迹**，两者用颜色深浅区分。
- **两个点**：静态点在有轨迹时改标「起点」并缩小、画淡（`circle-radius 3.5`），没有轨迹时
  标「目标」；动点仍是跟随移动的实心圆 + 箭头。一眼能看出「原地这个点是出发点」。
- **清除轨迹**：`.map-actions` 新增「清除轨迹」按钮（无轨迹时禁用），只清前端会话内采样；
  另外「确认并发送」在发起单次发送/持续发送前会先清该机采样，所以**重新打点即从零开始画**。

### 14.3 实测（`python tools/measure_motion.py`，1440×900，WS 打桩 + 注入机队）

| 采样分段 | 注入 8 拍（东向 0.0001°/拍）+ 重打点后 5 拍 → `segments = [0×8, 1×5]`，共 13 条 |

| 清除轨迹 | 按钮存在且可用 → 点击后 `targetSamples['25:1'].length === 0` |
| 方向/预测 | 截图 `tools/layout_evidence/motion-map-1440.png`（起点标注、实线轨迹、箭头指向东、虚线到终点圈） |

## 15. 任务调度接管目标流后动点停止（2026-11-05）

### 15.1 现象

打点后开「目标位置下发 · 持续发送」，地图上目标点按航向正常移动；一执行
「任务调度 · 下发任务分配并授权」，动点立刻停在原地，轨迹不再延长。

### 15.2 根因

任务分配接受后由服务端自动接管 65010 目标流（`startMissionAssignment()` →
`startTargetRepeat(..., { source: 'assignment' })`），但这条路径**没有传运动参数**：

- `startTargetRepeat()` 的 `motion` 参数缺省为 `undefined`；
- 旧代码对 `undefined` 的处理是 `{ ...DEFAULT_TARGET_MOTION, stopMode: 'manual' }`，
  而 `DEFAULT_TARGET_MOTION.speedMps === 0` —— 即「静止 + 手动停止」；
- 于是每拍 `repeatTargetUpdate()` 都按 `p(t) = p₀ + v·t` 算出同一个点，前端采样
  不再增长，表现为动点停在原地。

任务调度抽屉当时也只提供经纬度/高度/频率，没有运动参数入口，操作员无从覆盖。

### 15.3 修法

1. **协议复用，不扩字段**：运动参数仍走现有 `TargetMotion`（`server/target_motion.ts`），
   65010 本身不变（三轴速度早在 `TRACK_TARGET_UPDATE` 里）。
2. **服务端兜底沿用**：新增纯函数
   [`AssignmentRepeatMotion()`](../tools/web平台/server/target_motion.ts)——
   显式参数优先；否则沿用同一 `target_id` 上正在跑的手动持续发送参数；都没有才静止。
   三种情况一律强制 `stopMode: 'manual'`，避免按时长/距离到点自动停流（机载在飞时断流
   会被判目标丢失→S12）。
3. **分配请求可带运动**：`POST /api/missions/assign` 与
   `POST /api/aircraft/:componentId/:systemId/assignments` 的 body 新增可选 `motion`
   （`ParseTargetMotion` 校验，非法返回 422「65010 目标运动参数错误：…」），并随
   `AssignmentRuntime.motion` 保存，65015 回执后重启目标流（`accepted` 分支）同样带上。
4. **抽屉里可改**：任务调度抽屉新增「65010 目标运动」小节（航向/速度/垂直速度），
   与「目标位置下发」共用 `store.targetDraft` 同一份草稿，确认框逐行打印「目标运动」。
5. **位置也接续**：只把参数接上还不够——分配流如果按抽屉里的打点原点重新起算，
   目标会先"闪回"原点再前进（前端按 >50 m 跳变会断段）。`IsSameTargetPoint()`
   （同一 `target_id`、经纬度一致、高度差 < 0.5 m）成立时，新流的起点取
   `AdvanceTargetPoint(上一流的起点, 上一流的运动参数, 已跑秒数)`，从当前推进点继续；
   操作员重新打点（坐标变动）则按新起点走。

### 15.4 验证

| 项 | 结果 |
|---|---|
| 单测 | `AssignmentRepeatMotion` 4 分支（显式/沿用/换目标/空）+ `IsSameTargetPoint` 5 断言；`npm test` **140/140** |

| 端到端动点 | 需要在线飞机 + 已冻结机型的 ready 状态（`controllable && availability=ready`）才能走到 `startTargetRepeat`；本次未起 SITL 机队，行为由 15.3 的沿用/接续规则 + 单测覆盖，现场联调时按 §15.5 复核 |

## 17. 接近段速度剖面：交互演示（2026-11-05）

口头描述"梯形"没有说服力，故做了一张**可操作**的演示页，用同一套物理把"设计（梯形 + 余量）"
和"对照（无余量、纯尾追）"并排跑，参数全部可调。

- 文件：`docs/示意图/追踪梯形曲线-交互演示-2026-11-05.html`（单文件、零依赖，双击即可打开）
- 校验：`python tools/verify_demo.py`（Windows 侧，playwright；版式 + 四条物理断言）
- 操作：空格暂停、R 重跑、右侧滑块改目标速度/航向/机动/余量/加速度/剖面/末端/地板/播放倍速

### 17.1 两个世界的唯一差别

| | 设计（蓝） | 对照（红虚线） |
|---|---|---|
| 巡航上限 | `v_cruise = max(1.5, \|v_t\| + 余量)` | `v_cruise = \|v_t\|` |
| 参考剖面 | 加速斜坡 → 巡航平台 → 减速斜边 → 速度匹配 | 无斜坡，第一拍就按 `v_cruise` 推进，只有末端 √ 刹车 |

两架飞机用**完全相同**的机载跟随律（加速度受限、朝向视线、`v_ref` 为参考速度），
所以差异只能来自"参考点怎么推进"——这正是本页要证明的因果。

### 17.2 公式（与 §16.4 的讨论一致）

```text
v_cruise = max(地板 1.5, |v_t| + 余量)                        # 稳态接近速率 = v_cruise - |v_t|
d_brake  = R_arr + (v_cruise² - v_end²) / (2a) × 1.3 + 0.5    # 1.3 安全系数、0.5 离散/延迟补偿
v_end    = |v_t|（速度匹配） 或 0（减到 0）
四段：加速  v_ref += a·dt（d > d_brake 且未到平台）
      巡航  v_ref = v_cruise
      减速  v_ref = √(2a(d - R_arr) + v_end²)
      匹配  d ≤ R_arr 时 v_ref = v_end
```

关键一点：**"余量"不是礼貌距离，而是稳态收敛速率**。目标匀速直线时
`ḋ = -(v_cruise - |v_t|) = -余量`；余量为 0 时 `ḋ = 0`，距离永远停在加速期被拉开的差值上。

### 17.3 实测（`tools/verify_demo.py`，1440×900@2x）

| 场景 | 结果 |
|---|---|
| 默认（目标 2.0 m/s，余量 1.0，a=1.0，起始 40 m） | 到点 **49.2 s**，`d = 3.02 m`，`v_c = 0.01 m/s`，末相位"匹配" |
| 同一场景的对照组（无余量） | `d` 收敛不到底，**停在 42.02 m**，页面判定"追不上" |

### 17.6 策略对比：保守 vs 时间最优（同日追加）

维护者指出"目标不动时，最多加速到 2 就没了。难道不是如何时间最短吗？"——这条批评成立。
§17.2 的 `v_cruise = max(1.5, |v_t| + 余量)` 是**"刚好够追上"**的策略：它把巡航高度锁在
目标速度附近，目标静止时只飞 1.5 m/s，40 m 要 26 s。演示页因此加了「策略」开关，同参数对比：

| 目标静止、起始 40 m（a=1.0，余量 1.0） | 巡航上限 | 到点用时 |
|---|---|---|
| 保守：`max(1.5, |v_t| + 余量)` | 1.50 m/s | **25.9 s** |
| 时间最优：顶到 `V_max = 4.0` | 4.00 m/s | **12.9 s** |

时间最优的写法不是"先定平台再加速"，而是反过来：

```text
v_ref = min(V_max, √(2a·(d − R_arr) + v_end²))     # 能多快就多快，直到刹车包络
```

加速斜坡 → 平台 → 减速斜边是这条式子**自然长出来的**：远距离时刹车包络远高于 `V_max`，
所以顶在 `V_max`；接近包络后自动沿抛物线减速。目标运动时末端仍是速度匹配。

三件东西的分工也随之改变：

| 参数 | 时间最优下的角色 |
|---|---|
| `V_max` | 唯一巡航上限；由视觉跟踪能力（帧率 / FOV / 运动模糊）、围栏刹车距离、机体能力定 |
| 余量 | ① 可行性判据 `V_max ≥ |v_t| + 余量`，否则追不上；② 末段闭合速率（距离已在包络内、速度已匹配时靠它把最后几米挤进去） |
| 地板 1.5 | 不再参与巡航；最多作为"目标静止时也至少给 N m/s"的下限，可与 `V_max` 合并 |

对现有代码的含义：`track_speed_margin_mps` 保留为"可行性 + 末端闭合"，但接近段巡航要改成
`min(V_max, 刹车包络)`，需新增 `approach.max_speed_mps`（或给 `position_guide_speed_mps`
单独一个 4.0 的值）。

### 17.8 最高速度不是拍出来的：峰值由距离 + 两个加速度算出（同日追加）

维护者指出"最高速度不应该是固定的，关键是加速度；有两个加速度就能把总时间和匀速时间算出来"——
这条成立，而且上一版 §17.6 还把包络写错了。两处一起改：

**① 包络必须用相对系。** 目标以 `v_t` 后退时，"刹到停止"的曲线 `√(2a(d−R)+v_end²)` 不对：
要先追上 `v_t` 才谈得上收敛，正确包络是

```text
v_ref ≤ v_t + √(2·a_d·(d − R_arr))          # 相对闭合速度 u = v − v_t ≤ √(2 a_d s)
```

用错公式时演示页 25.2 s / 峰值 7.32 m/s，与闭式解差一倍多；改对后 14.1 s / 8.24 m/s，与公式只差 0.4 s。

**② 峰值由几何决定，不是先定平台。** 相对系里 `u = v − v_t`，从 `u0` 加速、再减到 0：

```text
u_p² = (2·a_a·a_d·D + a_d·u0²) / (a_a + a_d)      # 无上限 ⇒ 三角形，匀速段 = 0
u_cap = max(0, V_max − v_t)                        # 有安全帽才削平峰顶
u_p   = min(u_cap, u_p几何)
t_a = (u_p − u0)/a_a,  t_d = u_p/a_d,  t_匀速 = (D − s_a − s_d)/u_p
```

也就是说：**`V_max` 只是安全帽，`a_a / a_d` 才是决定时间的量**；上限压到接近 `v_t` 时时间会爆炸。

实测（`python tools/verify_demo.py`，目标 2 m/s 后退、起始 40 m、`a_a = a_d = 1.0`）：

| 场景 | 峰值 | 到点 | 匀速段 | 理论 |
|---|---|---|---|---|
| 无上限（三角形） | 8.24 m/s | **14.1 s** | 0 s | 14.49 s / 8.24 m/s |
| 上限 4.0 | 4.00 m/s | 23.3 s | 17.5 s | 23.50 s / 4.00 m/s |
| 目标静止、无上限 | 6.08 m/s | 11.8 s | 0 s | 12.16 s |
| 目标静止、保守 1.5 | 1.50 m/s | 25.9 s | — | — |

注意第二行：上限 4.0 对 2.0 m/s 的目标意味着相对闭合只剩 2 m/s，时间从 14 s 涨到 23 s——
"安全帽"一旦当成巡航速度用，就是 §17.6 里那个 26 s 的老毛病。

### 17.9 我们能控制加速度吗（PX4 v1.17.0 源码核实）

**我们发的不是加速度。** `src/communication/px4_link.cpp:654-685` 的 `BuildSetpointTypeMask()`
无条件置 `AX/AY/AZ_IGNORE`：位置型按轴放行速度前馈，速度型忽略位置，yaw/yaw_rate 可选。
加速度字段永远是 0、且被 PX4 忽略。

**PX4 侧其实是支持的**（只是我们没用）：

- `src/modules/mavlink/mavlink_receiver.cpp:1057` `setpoint.acceleration[0] = (mask & AX_IGNORE) ? NAN : afx`；
- `src/modules/mc_pos_control/PositionControl/PositionControl.cpp:103` `_acc_sp = Vector3f(setpoint.acceleration)`，
  之后才叠加速度环 `vel_error·(P, I, D)` 修正（:147）。

所以加速度在 PX4 里是**前馈项**，不是"加速度指令模式"：位置/速度闭环照旧跑，加速度只是把
期望值提前告诉它。

**限幅在哪**：`MPC_XY_VEL_MAX`(12 m/s) 钳速度；`MPC_TILTMAX_AIR`(45°) 与推力饱和决定实际加速度上限。
`MPC_ACC_HOR`(3) / `MPC_ACC_HOR_MAX`(5) **只被 GotoControl 与 navigator 电子围栏预测使用**
（`GotoControl/GotoControl.cpp:172-183`、`navigator/GeofenceBreachAvoidance/geofence_breach_avoidance.cpp:219-259`），
offboard 的位置/速度通路不读它们——改这两个参数不会改变我们现在的加速度，这也解释了实测里
"参考点一跳速度就台阶"。

**工程结论**：现状下我们能控制的只有"参考轨迹的斜率"，`a_a / a_d` 写进 `v_ref` 的生成式，
PX4 负责跟上（实际加速度 = 速度环对斜率误差的响应 + 上述饱和），演示页里 0.4 s 的差值就是这一步。
要更精确可以发加速度前馈（去掉三个 IGNORE 位），但前馈错了会和 P 律叠加、更抖，**建议先不加**。

闭式解的推导（为什么要 `u_p²(a_a + a_d) = 2 a_a a_d D + a_d u₀²`）：
相对系里先以 `a_a` 加速到 `u_p`、再以 `a_d` 减到 0，两段路程之和等于 `D`，
即 `(u_p² − u₀²)/(2a_a) + u_p²/(2a_d) = D`，两边乘 `2 a_a a_d` 就得上式。
无上限时匀速段为 0（三角形）；峰顶被安全上限削平后才有 `t_匀速`。

#### 卡尔曼接入（演示页与机载同构）

- 模型与 `include/perception/linear_target_kalman_filter.h` 一致：每轴独立 `[位置, 速度]` 二状态，
  白噪声加速度恒速度模型，`Q = σ_a²·[[dt⁴/4, dt³/2], [dt³/2, dt²]]`，位置量测按 `K = P/(P+R)` 更新。
- 时延建模：量测取"`latency` 之前的真值 + 高斯噪声"，与 65010 的实际链路一致。
  - **量测模式**：飞机直接追这个过期点 → 误差 = 噪声 + `|v_t|·latency`；
  - **卡尔曼模式**：滤波器状态停在量测时刻，再按估计速度前视 `latency` → 补掉时延。
- 实测（σ=1.5 m、5 Hz、latency=200 ms、目标 2 m/s，`python tools/verify_demo_kf.py`）：

| σ_a | 量测误差 | 估计误差（滤波状态 vs 量测时刻真值） | 前视误差（前视到"现在"） |

| 2.0（整定后，演示默认） | 2.57 m | 1.22 m | **1.37 m** |

**结论二**：机载现在的 `σ_a = 8.0` 适合"跟住位置"，不适合"往前推"——用它做前视，

**结论三**：σ 归零时估计误差为 0，说明实现没有引入偏置；预测点领先估计点 `≈ 估计速度 × 提前量`

### 17.12 绕圈 / 蛇形暴露的三个缺陷（2026-11-06 修正）

维护者看图后指出"绕圈和蛇形的运动问题很大"、"预测点为何一直在目标点之后"。逐项量测后确认是
演示页模拟核心的三个缺陷（不是渲染问题），已全部修正。

#### 缺陷一：参考点无限累积

原实现 `guide += u · v_ref · dt`——参考点沿 Instantaneous 视线以 8~15 m/s 往外走，从不回收，
目标一绕圈就被甩到 200 m 外（截图里「参考领先 73.1 m」）。真实系统里位置设定点是每拍从
当前机位重新生成的，不会累积。

改为「飞机 + 沿视线的前瞻距离」一阶跟随（`LEAD_TAU = 0.3 s`、`LEAD_MAX_M = 6 m`），
实测 lag 由 143~205 m 收敛到 **0.02~0.4 m**。

#### 缺陷二：刹车包络用了 |v_t| 而不是沿视线分量

原式 `envelope = vEnd + √(2a(d − R))` 把目标速度**整体**当作"在后退"。目标横向跑时
（绕圈/蛇形）`v_t` 与视线几乎垂直，多补的那部分让参考速度虚高——实测 v_ref 被顶到
**14.4 m/s**（当时 d 只有 57 m，正确上限 ≈10.5 m/s），于是冲过头再兜回来。

改为 `envelope = max(0, vtAlong) + √(2a(d − R))`，只有目标"沿视线后退"时才补偿。
直线后退目标 `vtAlong = |v_t|`，行为与原来完全一致（回归用例的到点时间未变）。

#### 缺陷三：没有转弯约束（绕圈/蛇形追不上的真正原因）

纯追击的稳态是被"冲过头 → 掉队 → 再冲"的极限环（实测 d 在 5~66 m 之间摆，
永远到不了点）。原因是飞机必须**绕着**目标转，速度越高所需向心加速度越大，
而可用横向加速度只有 `a`：

```text
转弯半径按当前视距估 → v ≤ √(a · d)        # 绕圈在 d=10 m 时只能飞 3.2 m/s
```

补上这条约束后：

| 场景 | 修正前 | 修正后 |
|---|---|---|
| 绕圈 `v_t=4`、`a=1`、`r=20 m` | 永不收敛，d 在 5~66 m 摆 | **15.1 s 到点**，末态 d=3.01 m |
| 蛇形 `v_t=4`、`a=1` | 同上 | 稳态 **7.8 m**（6.6~9.6 m），不到点 |
| 蛇形 `v_t=4`、`a=3` | — | **17.4 s 到点** |

蛇形在 `a=1` 下到不了点不是算法问题：蛇形目标自身的横向加速度约
`v_t · ω = 4 × 0.55 ≈ 2.2 m/s²`，超过飞机的 1 m/s² 预算——**能力边界，不是控制律缺陷**。
把加速度提到 3 就正常到点，正好验证了这一点。

#### 「预测点为什么在目标后面」

这是语义问题，两个原因叠在一起：

1. 原来画的点叫"预测 +200 ms"，它的定义是**把 200 ms 前的量测补时延推到"现在"**，
   所以它天然落在目标身上而不是前方；剩下的偏差是滤波器在机动目标上的平滑滞后。
2. 实现上用固定 `latency` 前视，而量测实际取的是 `lat−tick` 之前的真值，少推了一拍，
   于是系统性地偏后。

现在拆成两个点，语义各自明确：

| 图元 | 含义 |
|---|---|
| 灰点 | 量测（`latency` 之前的真值 + 噪声） |
| 青菱形 | 卡尔曼**估计**（滤波状态，在量测时刻） |
| 紫三角 | **瞄准点** = 估计点 + 目标速度 ×（时延 + 拦截提前 `t_go` + 手动提前） |

`t_go = 视距 / 相对速度`（上限 4 s，仅当目标横向速度 > 0.8 m/s 时才启用，直线后退为 0）。
绕圈实测瞄准点领先目标 **3~8 m**，这就是飞机真正飞向的点——"预测"本来就该指向前方。
前视时间也改用真实经过时间，不再少推一拍。

#### 对实机的影响（待拍板）

演示页是模拟，但它暴露的是**控制律层级的问题**，实机同样存在：

1. S5 现在按"当前位置"生成引导点（纯追击），目标一旦横向机动就落进同一类极限环；
2. 引导点推进速率上限里没有转弯约束——`v ≤ √(a·d)` 这条在实机上要不要加、`a` 取多少
   需要拍板（可用横向加速度受姿态倾角限制，`MPC_TILTMAX_AIR = 45°` 对应约 9.8 m/s²，
   但我们的 `controller.max_speed_mps = 2.0` 与加速度限幅都没这么高）。
3. 拦截提前量 `t_go` 要不要进 S5 的引导点，还是留给 S6 速度匹配段处理。

### 17.13 速度律拍板后的落地（2026-11-06，演示页）

拍板结论（D1=a 碰撞三角形、D2 夹紧、D3=B 比例接近律）已落进交互演示页，
蓝色「设计机」现在跑的就是基线律；旧的两条剖面保留成对照，用右侧「速度律」三段切换：

| 速度律 | 参考速度 | 用途 |
|---|---|---|
| 比例接近（**默认 / 基线**） | `u = clamp(k·(d_aim − R), 0, Vmax)`，`v_ref = clamp(v_t·n̂ + u, 0, min(Vmax, turnCap))` | 未来机载要实现的 |
| 梯形包络 | `v_ref = min(envelope, turnCap, Vmax)`，按 `a_a` 斜坡爬、按包络斜切 | 上一版设计，留作对照 |
| 现状台阶 | 同上但直接跳到包络值（无斜坡） | 复现当前机载的参考点跳变 |

同一轮修掉的三处问题（都是量测暴露出来的，不是猜的）：

1. **转弯约束的量纲错了**：上一版用 `turnCap = √(a·d)`，只是凑量纲，实测把增益 `k` 的作用整个盖掉
   （k=0.3 / 1.2 结果一模一样）。改成物理口径——以速度 v 跟着视线转需要向心加速度
   `a = v·ω`，而视线角速度 `ω ≈ v_t⊥/d`，于是 `v ≤ a·d / v_t⊥`。
   改完 k 才开始有作用，绕圈也从"永远追不上"变成 a=1.5 时 23 s 到点。
2. **显示距离和制导距离混用了**：制导要对准"瞄准点"（估计点 + 提前量），但读数里的 `d`
   必须回到**真实目标距离**，否则"追不上时的稳态间距"会被提前量虚增 2~3 m，
   和日志/IG 对不上账。现在 `s.d` 是目标距离、`s.dAim` 是瞄准点距离。
3. **方向归一化用错分母**：`dx/d` 里 `d` 换了含义以后，速度矢量会被缩水，
   表现为"到点时间翻倍"（24.56 s vs 14.49 s）。改为按 `dAim` 归一。

（jerk = 参考速率的最大变化率，只统计 `t>2 s && d>5 m`，避开起步与到点那一下。）

结论：**包络律必须补「机体总速度」这一层**——这是三律里唯一会突破机体上限的，绕圈时冲到 12 m/s。
补上之后（brake），峰值恒 ≤ 6、绕圈 jerk 1.9（比 prop 的 2.2 更低），到点时间 15.6 s 与 prop 的 14.6 s 只差 1 s。

**参考限速实测**（`python tools/probe_slew.py`，制动曲线、静止 40 m）：

| 参考限速 | 到点 | 到点瞬间 v_ref | 全程最大 jerk |
|---|---|---|---|
| 关闭 | 11.8 s | 0.00 | **10.6** |
| 1.0 m/s² | 11.8 s | 0.17 | **2.1** |
| 2.0 m/s² | 11.8 s | 0.17 | 2.1 |

即：这一条**只改平滑度、不改到点时间**，而它正好治「静止目标也急加速急减速」——那现象不是法则选错，
而是到点那一刻参考速率从 6 m/s 直接跳成 0，飞机只能靠姿态环硬吃。

`V_body` ↔ `controller.max_speed_mps`；`A_brake` ↔ `approach.decel_mps2`（新增）；
