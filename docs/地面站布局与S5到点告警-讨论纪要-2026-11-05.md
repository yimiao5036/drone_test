### 2.2 “到达目标后，多久不识别会返航？”

**现状：没有这条规则。** 只要地面站持续给目标，S5 可以无限等视觉锁定。

`EvaluateTargetWatchdog()`（`src/state_machine/mission_state_machine.cpp:1601`）只在
`kGpsApproach` 且 `command_sender_ != nullptr` 时生效，三条判据（`include/config/config.h:246-251`）：

| 配置 | 默认 | 含义 |
|---|---|---|
| `takeoff.target_wait_timeout_ms` | 10000 | 进 S5 后**从未**拿到新鲜目标 |
| `takeoff.target_lost_timeout_ms` | 10000 | 拿到过，之后连续失效 10 s |
| `takeoff.target_hold_max_ms` | 60000 | 本次 S5 内“原地保持”累计 60 s |

三条都走 `AbortForTargetWatchdog()` → S12 返航。

为什么 0100 里 3.5 分钟没自动返航：地面站 65010 实测 **5 Hz** 持续送达
（`count` 300→1200，每包 `valid_for_ms=999`），`HasFreshEstimate()`
（`:3371`）每拍为真 → 三个计时器都不启动；视觉侧整段
`state=SEARCHING valid=false … 从未检测`，也不会进 S6。
直到 22:16:40 用户手动 65020（`command_id=2801664001`）才 `GPS_APPROACH -> RETURN_HOME`。

**结论**：“到达目标点但视觉始终不识别”目前没有任何超时或提示，只有人工返航或电量兜底。

### 4.2 机载（`src/state_machine/mission_state_machine.cpp`）

现有代码里**没有“到点”概念**，S5 每拍只是 `EvaluateEstimateGuidedIntent()` 把目标位置交给控制器；
S5→S6 只由 `EvaluateVisualHandover()`（`:3201`）在视觉 `LOCKED` 连续帧超过
`handover.lock_frames=10` 时驱动。建议新增：

1. **到点判定**：水平 ≤ `arrival_radius_m`（建议 3.0）、垂直 ≤ `arrival_vertical_m`（2.0）、
   速度 ≤ 0.5 m/s、持续 `arrival_hold_ms`（2000），带迟滞；
2. **到点后视觉等待计时**：`handover.visual_wait_warn_ms`（建议 20000）到点置告警位，
   `handover.visual_wait_abort_ms`（默认 0 = 不自动处置）；
3. **不能复用 `PublishTargetHoldIntent()`**：那条路径会计入 `target_hold_accumulated_ms_`，
   60 s 后触发 `AbortForTargetWatchdog()` → S12，与“一直等”冲突；到达等待需单独的状态标志；
4. **告警位**：现有 `kWarningTargetHold = 1U << 5U`（`mission_state_machine.cpp:87` 附近），
   65013 的 `active_warning_bits` 已能上报；建议新增 bit6「到点未识别」，
   同步 `docs/数据接口文档.md` 与前端 `StatusPanel.vue` 的 `WARNING_BITS` 表；
5. **退出条件**：视觉锁定 → S6；目标移动超出半径 → 重新接近并重新计时；人工返航立即生效；
   低电走 `TriggerBatteryAbort()`（PX4 `BAT_LOW_THR` + `takeoff.battery_low_debounce`）。

  不同源时，TIMESYNC 的 `offset` 每秒涨 ~91 ms，贴着 `max_offset_jump_ms=100`，
  每 2~3 s 抖一次 `DEGRADED` → 65010 上行点全部被 `TIME_SYNC_UNAVAILABLE` 拒绝。
  规避：Web 服务端跑在 WSL 内（同钟），或设备两端都是被 NTP 校时的真时钟；
  根治方向是代码做漂移容忍（offset 线性拟合 + 残差判跳变），**尚未实施**；
- SITL 用 `webgcs` 时 Web 必须连上并持续心跳，否则 PX4 拒绝解锁（见 §1.3）。

### 8.9 遗留修复：提示条压顶栏（2026-11-05，已实现）

**问题**：Element Plus 的 `ElNotification` 默认 `offset: 16`、`ElMessage` 默认贴 `top: 20px`。
PR1 把顶栏收口成 58 px 的单一信息层之后，任何提示都会直接盖住状态 chip / 飞行徽标 / 时钟 / 动作按钮。
外场最容易看到的就是 `FencePanel.vue` 的「围栏副本读取失败」——预览环境没有 `/api` 时每次进页面都会弹。

**做法**：新增 `tools/web平台/src/utils/notify.ts`，把"非阻塞通知"统一成一个出口
`notice(title, message, type)`，固定 `offset: NOTICE_OFFSET(70)`、`position: 'top-left'`、
`duration: 5000`。四类提示改用该出口：

| 位置 | 原实现 | 现在 |
| --- | --- | --- |
| `components/FencePanel.vue:84` | `ElMessage.warning(围栏副本读取失败…)` | `notice(..., 'warning')` |
| `components/MissionPanel.vue:151` | `ElNotification({已发送任务分配 #N})` | `notice(..., 'success')` |
| `components/TargetPanel.vue:83` | `ElNotification({网关已发送})` | `notice(..., 'success')` |
| `components/TargetPanel.vue:115` | `ElNotification({后端持续发送已启动})` | `notice(..., 'success')` |

顺带把 `refreshFenceSnapshot(notify = false)` 的第一个形参改名 `shouldNotify`——原先函数内
`if (notify)` 与刚引入的模块级 `notice` 同名，读起来像在调函数。

**实测**（1440×900，预览构建、无 `/api`）：通知卡片 `x16 y86 330×108`，即顶栏底边 58 之下 28 px，
`el-notification` 容器 `top: 70`、卡片自身再内缩 16 px；右侧「状态 chip / 时钟 / 更多 / 系统状态 / 切换连接」
全部无遮挡。代价是它会短暂盖住侧栏顶部的「收起侧栏 / 任务态势 / 运行日志」，5 s 自动关闭且带 ×。

**为什么选左上而不是右上**：右上会压住上下文条右侧的「返航 · 机名 / 重置 · 机名」——

**未动**：40 余处 `ElMessage.success/error/info` 这种"点了按钮立刻回执"的短提示仍贴在默认位置（约 2 s，
触发者是用户正在看的那个按钮），改它们收益小、面大；如果现场反馈仍然挡视线，再统一走 `notice()`。

## 11. PR3 机载：到点判据 + 65013 bit6（2026-11-05，已实现）

维护者拍板：**不扩 65013 协议**（只加告警位，「等了多久」由地面站按 bit6 首次置位时刻
自算），配置项取推荐值。

### 11.1 判据（与 §4.2 一致）

| 量 | 取值 | 说明 |
|---|---|---|
| 到点水平半径 `handover.arrival_radius_m` | 3.0 m | 飞机与**分配目标估计点**（`latest_estimated_`，局部 NED）的水平距离 |
| 到点垂直半径 `handover.arrival_vertical_m` | 2.0 m | 高度差绝对值 |
| 停稳地速 | 0.5 m/s（代码常量 `kHandoverArrivalSpeedMps`，不做配置键） | 局部 `vx/vy` 合成；被调高会把"掠过目标点"误判成到点 |
| 保持时长 `handover.arrival_hold_ms` | 2000 ms | 三条件连续满足才判到点 |
| 迟滞 | 离开用 **1.5 倍**半径 | 避免边缘抖动反复清零（与 `exit_lost_frames` 同思路） |
| 告警阈值 `handover.visual_wait_warn_ms` | 20000 ms | 到点后视觉未锁定累计超过即置 bit6 |
| 自动处置 `handover.visual_wait_abort_ms` | **0（关）** | 非 0 时按目标等待超时中止到 S12；现场只提示、人工决定 |

「视觉锁定」的取法与 S6 进入判据同口径：`VisualStatusStale()==false` 且
`VisualTargetStatus.state == kLocked`。

### 11.2 为什么独立于目标看门狗

`EvaluateTargetWatchdog()` 的三条计时器都以"目标失效"为前提；0100 记录里 65010 以
5 Hz 持续送达、`valid_for_ms=999`，`HasFreshEstimate()` 每拍为真 → 三条都不启动，
于是"悬停在目标点上方、视觉一直没锁定"既无告警也无处置。新判据只看**位置是否到点**
与**视觉是否锁定**，与目标新鲜度解耦；两者同时成立时互不干扰（bit5 管"目标没了"，
bit6 管"到点了但没看见"）。
