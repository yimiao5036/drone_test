# 故障排查手册

> 目标：按“现象→检查点→代码位置”的顺序定位问题，避免一出现故障就同时修改多个模块。  
> 最后更新：2026-09-11。

## 1. 排查基本原则

1. 先确认当前运行的是正式`drone_control`还是独立探针；
2. 先检查配置，再检查日志，再检查模块计数，最后才修改代码；
3. 一次只改变一个变量，并保存修改前后的日志；
4. 视频探针、正式程序不能同时占用摄像头、NPU和本地RTSP输出路径；
5. 串口调试工具和正式程序不能同时打开同一个串口；
6. 没有PX4时，不把PX4连接失败、无Home和状态机停留自检误判为其他模块Bug；
7. 禁止为“先跑起来”伪造距离、高度、Home、姿态或控制有效标志；
8. 正式配置始终保持`enable_control=false`。

## 2. 当前硬件条件提醒

当前现场只有：

```text
香橙派 + 摄像头 + 图传/HM30 + 地面站
```

没有PX4，因此预期现象是：

- 视频链路可以正常运行；
- 地面站串口物理链路可以连接；
- 正式Px4Link无法得到真实心跳；
- TargetEstimator一直等待PX4 Home；
- MissionStateMachine不能完成导航自检；
- 地面站上的GPS、姿态、电池和Home没有真实数据；
- 不可能验证飞行控制。

上述现象在当前硬件条件下不是Bug。

## 3. 三分钟快速检查

### 3.1 确认运行进程

```bash
pgrep -af 'drone_control|video_latency_probe|px4_link_smoke'
```

如果正式程序和视频探针同时存在，先正常停止其中一个。

### 3.2 确认实际配置

启动日志中查找：

```text
正式主程序加载配置: path=...
主程序集成创建: video=... px4=... ground_station=... target_estimator=... control=...
```

不要只看源码目录中的`config/config.json`。构建目录和部署目录可能各自有配置副本，必须以启动日志的`path`为准。

### 3.3 找最新日志

```bash
ls -lt logs/ | head
```

实时查看：

```bash
tail -f logs/<最新日志文件>
```

按关键字过滤：

```bash
grep -E 'ERROR|WARN|启动失败|超时|回退|拒绝|断开' logs/<日志文件>
```

### 3.4 确认构建版本

开发机：

```bash
cmake -S . -B build
cmake --build build -j$(nproc)
ctest --test-dir build --output-on-failure
```

当前基线：188/188测试通过。

## 4. 程序无法启动

### 现象A：控制台提示配置文件不存在

检查：

```bash
./build/drone_control --config /绝对路径/config.json
```

配置查找顺序：

1. 显式`--config`；
2. 可执行文件旁`config/config.json`；
3. 当前目录`./config/config.json`。

代码：

- `main.cpp::ParseRequestedConfig()`；
- `src/config/config.cpp::ResolveConfigPath()`。

### 现象B：配置解析失败

常见原因：

- JSON逗号或引号错误；
- 队列容量、周期或超时为0/负数；
- 地面站启用但PX4关闭；
- TargetEstimator启用但地面站或PX4关闭；
- `enable_control=true`；
- 身份、component或串口参数不合法。

先运行：

```bash
./build/config_test
```

代码：`src/config/config.cpp`。

### 现象C：程序返回“没有任何模块成功启动”

检查启动日志中每个模块的启动失败原因。`DroneApplication`允许单模块降级，只要有一个模块成功就继续运行；全部失败才返回错误码2。

代码：`src/application/drone_application.cpp::Start()`。

## 5. 视频完全没有画面

按下面顺序检查，不能直接跳到YOLO。

```text
摄像头网络可达？
→ RTSP能否被ffprobe读取？
→ CameraReceiver是否收到字节？
→ VideoDecoder是否输出帧？
→ FrameCompositor是否输出标注帧？
→ VideoSender是否写出RTSP？
→ MediaMTX和HM30路径是否正确？
```

### 5.1 网络和RTSP输入

```bash
ping -c 3 192.168.144.25
ffprobe -rtsp_transport tcp 'rtsp://192.168.144.25:8554/main.264'
```

以实际配置地址为准。确认输入实际编码是H.265/HEVC，不要根据URL扩展名猜编码。

代码和文档：

- `src/video/camera_receiver.cpp`；
- `include/video/camera_receiver.md`。

### 5.2 CameraReceiver有连接但没有后续画面

检查日志是否出现：

- RTSP打开失败；
- 读取超时；
- 重新连接；
- 参数集未就绪。

关键计数：

```text
CameraReceiver::ReceivedBytes()
CameraReceiver::ErrorCount()
```

判断：

- `ReceivedBytes`不增长：问题在摄像头、网络或RTSP接收；
- `ReceivedBytes`增长但解码帧不增长：进入解码器排查。

## 6. 收到码流但解码失败

关键计数：

```text
EncodedFrameCount
DecodedFrameCount
DroppedFrameCount
ErrorCount
```

典型判断：

| 现象 | 优先检查 |
|---|---|
| 编码帧增长，解码帧一直为0 | 编码类型、VPS/SPS/PPS、关键帧、rkmpp加载 |
| 启动时短暂`invalid pps id`后恢复 | 可能是GOP中途接入，等待参数集/随机访问帧 |
| RGA DMA持续回退 | DRM对象/图层/线性NV12布局或librga |
| 帧池满 | 下游过慢、句柄未释放、池容量不足 |
| 软件解码正常、硬解失败 | ffmpeg-rockchip/rkmpp环境和像素格式 |

硬解和RGA相关日志必须结合计数判断，不能只看单条原生库输出。

代码和文档：

- `src/video/video_decoder.cpp`；
- `src/video/drm_nv12_transfer.cpp`；
- `include/video/video_decoder.md`；
- `include/video/drm_nv12_transfer.md`。

## 7. 有原始画面但没有YOLO检测

检查顺序：

1. `YoloDetector`是否启动成功；
2. 模型路径是否为部署目录中的实际文件；
3. `ProcessedFrameCount()`是否增长；
4. `ErrorCount()`是否增长；
5. NPU运行和后处理是否有样本；
6. 置信度阈值是否过高；
7. 当前画面是否确有模型可识别目标。

关键配置：

```json
"yolo": {
  "model_path": "...",
  "conf_threshold": 0.60,
  "nms_threshold": 0.45,
  "input_queue_capacity": 1,
  "npu_core_mode": "all"
}
```

注意：一帧没有目标时，当前YoloDetector不会发布`DetectionResult`，这本身不表示线程停止。

不要用未经重新训练的ReLU性能探针判断识别精度。

代码：

- `src/perception/yolo_detector.cpp`；
- `src/perception/rknn_detection_backend.cpp`；
- `src/perception/yolo_postprocess.cpp`。

## 8. YOLO有结果但画面没有框

重点检查`FrameCompositor`：

- 解码帧和检测结果的`frame_sequence`是否一致；
- 检测是否超过`max_detection_frame_lag`；
- 检测框宽高是否有效；
- `AnnotatedCount()`是否增长；
- `DroppedFrameCount()`或`ErrorCount()`是否增长；
- 类别名是否来自正确配置。

数据流：

```text
DecodedFrame ───────────────┐
DetectionResult(frame_seq) ─┴→ FrameCompositor → AnnotatedFrame
```

代码：`src/video/frame_compositor.cpp`。

## 8.1 视觉稳定性判定不锁定或频繁丢失

数据流：

```text
YoloDetector 帧级观测（每推理帧一条）
  → VisualTargetMonitor
  → VisualTargetStatus（SEARCHING/ACQUIRING/LOCKED/LOST）
```

排查顺序：

1. `YoloDetector::ObservationCount()` 是否随帧增长？
   - 不增长：问题在推理链路（后端异常、无输入帧、模型未加载），与门限无关；
   - 增长：继续下一步。
2. `YoloDetector::DetectedObservationCount()` 是否增长？
   - 不增长：模型当前看不到目标，检查画面内容、置信度阈值和模型是否匹配；
   - 增长：继续下一步。
3. 看日志中的视觉稳定性行（默认每5秒一条摘要，状态变化时另有一条）：

   ```text
   视觉稳定性状态变化: SEARCHING -> ACQUIRING 连续检测=1 ... 累计转换=1 累计观测=1
   视觉稳定性状态变化: ACQUIRING -> LOCKED 连续检测=5 ... 累计转换=2 累计观测=5
   视觉稳定性摘要: state=LOCKED valid=true 连续检测=812 ... 上次检测=0ms前 累计观测=1230 累计转换=2
   ```

   - 一直是 `SEARCHING` 但 `累计观测` 在涨：模型没看到目标，不是门限问题；
   - 长期 `ACQUIRING`：`visual_monitor.lock_frames` 相对实际检测率过大；
   - 频繁 `LOCKED <-> LOST` 且 `累计转换` 快速增长：检测在间歇抖动，先查YOLO侧；
   - 报 `视觉观测超时，判定目标丢失`：观测流中断，回到第1步查推理线程。

注意：

- 该状态当前只是影子输出，不驱动飞行控制；
- 不要为了让状态“看起来稳定”而盲目增大 `lost_frames`，应先确认漏检根因；
- 状态变化本身不打日志；需要看时序时观察 `LastStatus()` 或订阅 `kVisualTargetStatus`。

代码和文档：

- `src/perception/visual_target_monitor.cpp`；
- `include/perception/视觉目标稳定性判定.md`。

## 9. 香橙派本地有标注画面，但地面站没有图传

检查：

1. `VideoSender::SentFrameCount()`是否增长；
2. `ErrorCount()`和`DroppedFrameCount()`；
3. 输出RTSP路径是否展开为当前飞机身份；
4. MediaMTX是否监听；
5. 地面站拉流路径是否与飞机`component/system`一致；
6. HM30网络是否互通。

```bash
ss -lntup | grep 8554
ffprobe -rtsp_transport tcp 'rtsp://127.0.0.1:8554/drone_25_1'
```

生产捕网-01当前路径：

```text
/drone_25_1
```

不同身份必须以配置展开结果为准。

## 10. 地面站串口不通

### 10.1 设备节点

```bash
ls -l /dev/ttyS6
```

检查是否有其他进程占用：

```bash
fuser /dev/ttyS6
```

不要在正式程序运行时再用`screen`、Python脚本或其他工具打开同一串口。

### 10.2 串口参数

当前配置：

```text
/dev/ttyS6 @ 115200 8N1
```

检查设备树是否启用正确的`uart6-m1`复用。串口节点存在不代表引脚复用和电平连接正确。

### 10.3 身份

地面站来源固定：

```text
system=255 component=190 type=MAV_TYPE_GCS
```

飞机捕网-01当前身份：

```text
system=1 component=25
```

错误来源心跳不会刷新连接状态。

## 11. 地面站没有目标ACK

按顺序检查：

1. 地面站GCS心跳是否建立连接；
2. TIMESYNC是否达到`SYNCHRONIZED`；
3. 65010目标地址是否为当前飞机`1/25`；
4. `protocol_version`是否为1；
5. `target_id`是否非0；
6. 经纬度范围是否合法；
7. `flags`是否只使用bit0～bit6；
8. `update_seq`是否严格递增；
9. `valid_for_ms`和传输年龄是否仍有效。

错误地址按协议静默，不发送ACK。其他拒绝通常返回65011及原因码。

工具：

```bash
python3 tools/ground_station_target_update_tester.py --help
```

文档：[地面站目标位置与时间同步协议](地面站目标位置与时间同步协议.md)。

## 12. TargetEstimator没有输出

数据流：

```text
GroundStationTarget + PX4 Home → TargetEstimator → TargetState
```

检查：

- `runtime.enable_target_estimator`是否为true；
- 地面站和PX4组件是否都启用；
- PX4是否上报`home_valid=true`；
- 目标是否仍在有效期；
- `target_id`是否非0；
- `UpdateCount()`是否增长；
- `ErrorCount()`是否增长。

当前没有PX4时，日志出现：

```text
目标估计等待PX4 Home
```

是预期行为，不是Bug。正式程序禁止自动生成假Home。

高度为NaN时检查：

```text
flags.bit0=1
alt_reference=1（MSL）
```

否则只输出水平N/E，Z/VZ保持NaN。

## 13. MissionStateMachine一直停留在SELF_CHECK

当前影子状态机需要：

- PX4连接；
- GPS有效；
- 全局位置有效；
- Home有效；
- 健康条件满足；
- 后续收到新鲜地面站目标。

当前没有PX4时停留自检是正确行为。不要通过修改条件强行跳过自检。

## 14. HealthManager持续报超时

先区分：

- 模块从未启动成功；
- 模块启动成功但计数不增长；
- 阈值过小；
- 当前硬件根本不存在。

注册逻辑在：

```text
DroneApplication::RegisterHealthSources()
```

只注册实际创建的组件。当前配置仍启用Px4Link时，即使现场没有PX4，该健康源会超时，这是对真实配置和硬件不一致的正确反映。

不要为了消除告警直接增大所有超时。先确定数据源是否应该存在。

## 15. CPU/NPU负载或延迟异常

使用独占探针：

```bash
./build/video_latency_probe --config <配置> --duration 60 --interval 5
```

重点看：

- 解码队列和D1～D5/D4R；
- YOLO输入队列、Y1～Y4和Y2 NPU时间；
- 叠加队列；
- 编码/RTSP写出；
- 入口到最终RTSP的帧龄。

探针运行前确认正式程序已停止。

## 16. 停机时出现MPP告警

已知可能出现：

```text
mpp_mem_pool_put invalid mem pool ptr
mpp_buffer_service_deinit cleaning misc group
```

目前作为独立退出阶段问题跟踪。排查时记录：

- 是否只在退出出现；
- 是否影响运行期画面；
- 是否每次都出现；
- 使用RGA DMA还是FFmpeg回退；
- 停止顺序和最后一帧是否仍被持有。

不要因为退出告警直接修改运行期帧所有权逻辑。

## 17. 怀疑程序向PX4发送了控制

立即检查：

```json
"enable_control": false
```

全局搜索：

```bash
grep -RIn 'SetInput.*Px4Setpoint\|px4_link_->SetInput\|SendCommand' \
  src include main.cpp
```

正式`DroneApplication`当前不应存在`px4_link_->SetInput(...)`调用。

注意：`Px4Link`单元测试和`px4_link_smoke`包含命令或setpoint测试能力，不等于正式程序已经绑定控制。

## 18. 如何提交可复现的Bug信息

至少保存：

```text
1. Git分支和commit
2. 使用的配置文件完整路径和副本
3. 香橙派系统/内核/FFmpeg/RKNN版本
4. 启动到故障后的完整日志
5. 故障发生时间点
6. 摄像头、PX4、地面站哪些硬件实际连接
7. 是否同时运行探针或其他串口程序
8. 各模块关键计数是否增长
9. 最小复现步骤
10. 修改过哪些参数
```

推荐描述格式：

```text
现象：
预期：
实际硬件：
运行命令：
配置路径：
首次异常日志：
相关计数：
稳定复现步骤：
```

不要只截最后一条ERROR；很多故障的根因出现在更早的启动日志中。
