# 故障排查手册

> 目标：按“现象→检查点→代码位置”的顺序定位问题，避免一出现故障就同时修改多个模块。  
> 最后更新：2026-10-20（§11.1 双目室外 0% 已定位为超出 ≈7.95m 量程，<8m 近距有效占比 99.2%；新增 G4 串口台架排查入口见 `tools/px4_link_smoke.md` §2.5；§19/§20 保留）。

## 1. 排查基本原则

1. 先确认当前运行的是正式`drone_control`还是独立探针；
2. 先检查配置，再检查日志，再检查模块计数，最后才修改代码；
3. 一次只改变一个变量，并保存修改前后的日志；
4. 视频探针、正式程序不能同时占用摄像头、NPU和本地RTSP输出路径；
5. 串口调试工具和正式程序不能同时打开同一个串口；
6. PX4 已到位（装机体+GPS）：连接失败/无 Home/停留自检**不再属于预期现象**，按 心跳→GPS fix→Home 排查；未连接时（串口松动等）出现这些现象则不是 Bug，也不要伪造；
7. 禁止为“先跑起来”伪造距离、高度、Home、姿态或控制有效标志；
8. 正式配置始终保持`enable_control=false`。

## 2. 当前硬件条件提醒

当前现场具备（2026-10-10 更新）：

```text
香橙派 + 双目摄像头 + 图传/HM30 + 地面站 + PX4（装机体 + GPS）
```

预期现象（PX4 已连接）：

- 视频链路、地面站串口物理链路正常运行；
- `/dev/ttyS1` 建立心跳，`home_valid` 可成立，地面站可显示真实 GPS/姿态/电池/Home；
- TargetEstimator 可出有效 NED 影子状态，MissionStateMachine 可越过自检；
- **仍不可能验证飞行控制**：`enable_control=false`，且正式控制接入路径（阶段 4）未建成。

PX4 未连接（未上电/串口松动）时，仍可能出现旧现象：无法得到心跳、TargetEstimator
等待 EKF 锚点、状态机停在自检——未连接时这些不是 Bug；连接后若仍如此，按
心跳 → GPS fix → 锚点流（#49）顺序排查，不要伪造，也不要改代码绕过。

**室内提示（2026-10-10，现场在室内）**：室内可能拿不到 GPS fix / Home / 锚点——此时
状态机停留自检、TargetEstimator 等待 EKF 锚点属**预期现象，不是通信问题**。判据：
先看「PX4 心跳已连接」是否出现（出现=通信正常，去查 GPS/Home/锚点流）。分阶段
验证见 `docs/PX4实链验证清单.md`。

## 3. 三分钟快速检查

### 3.1 确认运行进程

```bash
pgrep -af 'drone_control|video_latency_probe|px4_link_smoke'
```

如果正式程序和视频探针同时存在，先正常停止其中一个。

### 3.2 确认实际配置

启动日志中查找：

```text
正式主程序加载配置: path=...
主程序集成创建: video=... px4=... ground_station=... target_estimator=... control=...
```

不要只看源码目录中的`config/config.json`。构建目录和部署目录可能各自有配置副本，必须以启动日志的`path`为准。

### 3.3 找最新日志

```bash
ls -lt logs/ | head
```

实时查看：

```bash
tail -f logs/<最新日志文件>
```

按关键字过滤：

```bash
grep -E 'ERROR|WARN|启动失败|超时|回退|拒绝|断开' logs/<日志文件>
```

### 3.4 确认构建版本

开发机：

```bash
cmake -S . -B build
cmake --build build -j$(nproc)
ctest --test-dir build --output-on-failure
```

当前基线：466/466测试通过。

## 4. 程序无法启动

### 现象A：控制台提示配置文件不存在

检查：

```bash
./build/drone_control --config /绝对路径/config.json
```

配置查找顺序：

1. 显式`--config`；
2. 可执行文件旁`config/config.json`；
3. 当前目录`./config/config.json`。

代码：

- `main.cpp::ParseRequestedConfig()`；
- `src/config/config.cpp::ResolveConfigPath()`。

### 现象B：配置解析失败

常见原因：

- JSON逗号或引号错误；
- 队列容量、周期或超时为0/负数；
- 地面站启用但PX4关闭；
- TargetEstimator启用但地面站或PX4关闭；
- `enable_control=true`但PX4或地面站关闭，或`controller`节参数违反`Validate()`（阶段四装配门禁，Task 6 起允许前置齐备时加载）；
- 身份、component或串口参数不合法。

先运行：

```bash
./build/config_test
```

代码：`src/config/config.cpp`。

### 现象C：程序返回“没有任何模块成功启动”

检查启动日志中每个模块的启动失败原因。`DroneApplication`允许单模块降级，只要有一个模块成功就继续运行；全部失败才返回错误码2。

代码：`src/application/drone_application.cpp::Start()`。

## 5. 视频完全没有画面

按下面顺序检查，不能直接跳到YOLO。

```text
视频输入源：video.camera_source = rtsp 还是 uvc？
【rtsp】摄像头网络可达？
→ RTSP能否被ffprobe读取？
→ CameraReceiver是否收到字节？
【uvc】/dev/videoN 节点存在且权限可读？
→ UvcCameraReceiver是否收到字节（ReceivedBytes）？
→ VideoDecoder是否输出帧？
→ 【stereo_split=true】StereoFrameSplitter左右目是否输出？
→ FrameCompositor是否输出标注帧？
→ VideoSender是否写出RTSP？
→ MediaMTX和HM30路径是否正确？
```

### 5.1 网络和RTSP输入

```bash
ping -c 3 192.168.144.25
ffprobe -rtsp_transport tcp 'rtsp://192.168.144.25:8554/main.264'
```

以实际配置地址为准。确认输入实际编码是H.265/HEVC，不要根据URL扩展名猜编码。

代码和文档：

- `src/video/camera_receiver.cpp`；
- `include/video/camera_receiver.md`。

### 5.2 CameraReceiver有连接但没有后续画面

检查日志是否出现：

- RTSP打开失败；
- 读取超时；
- 重新连接；
- 参数集未就绪。

关键计数：

```text
CameraReceiver::ReceivedBytes()
CameraReceiver::ErrorCount()
```

判断：

- `ReceivedBytes`不增长：问题在摄像头、网络或RTSP接收；
- `ReceivedBytes`增长但解码帧不增长：进入解码器排查。

### 5.3 UVC双目输入（camera_source=uvc）

先确认设备与档位，再看接收器计数：

```bash
ls -l /dev/video*                       # 节点是否存在、当前用户是否在video组
v4l2-ctl -d /dev/video0 --list-formats-ext   # 确认MJPG与目标分辨率/帧率档位存在
```

典型现象：

| 现象 | 优先检查 |
|---|---|
| 启动日志`打开UVC设备失败`反复重连 | 设备节点/权限、USB接触、`uvc_device`配置是否指向正确节点 |
| `UVC档位协商失败` | 设备不支持配置的MJPG/宽高分帧率：以`--list-formats-ext`实际档位为准改`uvc_width/uvc_height/uvc_fps` |
| `ReceivedBytes`不增长且无错误 | 拔插后节点号变化；或摄像头被其他进程（探针/上一实例）独占 |
| 接收正常但拆分器`ErrorCount`增长（`输入帧非法`） | 解码输出尺寸≠`uvc_width/height`：档位被驱动回退到默认值，以G_FMT回读日志为准修正配置 |
| 左右目`Dropped`增长 | 对应目输出池耗尽；右目无消费者属预期计数路径，异常的是左目丢帧 |
| `RgaFallbackCount`增长 | librga调用失败（日志含原因），已自动回退memcpy不影响画面；查DRM/RGA驱动 |

关键计数：

```text
UvcCameraReceiver::ReceivedBytes() / ErrorCount() / ConnectCount()
StereoFrameSplitter::LeftFrameCount() / RightFrameCount() / *DroppedCount() / RgaFallbackCount()
```

代码和文档：

- `src/video/uvc_camera_receiver.cpp`、`src/video/stereo_frame_splitter.cpp`；
- `include/video/uvc_camera_receiver.md`、`include/video/stereo_frame_splitter.md`。

注意：拆分链路下YOLO/叠加消费的是左目`kDecodedFrameLeft`；左目有画面但“画面反了”（左/右物理目相反）是已知悬置项，不影响出图，见拆分器实现文档。

## 6. 收到码流但解码失败

关键计数：

```text
EncodedFrameCount
DecodedFrameCount
DroppedFrameCount
ErrorCount
```

典型判断：

| 现象 | 优先检查 |
|---|---|
| 编码帧增长，解码帧一直为0 | 编码类型、VPS/SPS/PPS、关键帧、rkmpp加载 |
| 启动时短暂`invalid pps id`后恢复 | 可能是GOP中途接入，等待参数集/随机访问帧 |
| RGA DMA持续回退 | DRM对象/图层/线性NV12/NV16布局或librga |
| 帧池满 | 下游过慢、句柄未释放、池容量不足 |
| 软件解码正常、硬解失败 | ffmpeg-rockchip/rkmpp环境和像素格式 |
| 全部 `_rkmpp` 解码器/编码器消失（`ffmpeg -decoders \| grep rkmpp` 为空） | apt 用发行版 FFmpeg 覆盖了 ffmpeg-rockchip（同版本号撞车）；按 `docs/部署与打包.md` §8 恢复并 `apt-mark hold` |
| 解码器创建日志 `设备=drm` 而非 `rkmpp` | 链接的 FFmpeg 不含 rkmpp 设备类型（发行版库混装）；查 `pkg-config --modversion libavcodec` 是否 62.x、`ldd build/drone_control \| grep avcodec` 指向 |
| 硬解画面偏色/错位 | 看 DRM 图层日志 fourcc：mjpeg_rkmpp 应为 `NV16` 并走 RGA `imcvtcolor`；详见 `include/video/drm_nv12_transfer.md` |

硬解和RGA相关日志必须结合计数判断，不能只看单条原生库输出。

代码和文档：

- `src/video/video_decoder.cpp`；
- `src/video/drm_nv12_transfer.cpp`；
- `include/video/video_decoder.md`；
- `include/video/drm_nv12_transfer.md`。

## 7. 有原始画面但没有YOLO检测

检查顺序：

1. `YoloDetector`是否启动成功；
2. 模型路径是否为部署目录中的实际文件；
3. `ProcessedFrameCount()`是否增长；
4. `ErrorCount()`是否增长；
5. NPU运行和后处理是否有样本；
6. 置信度阈值是否过高；
7. 当前画面是否确有模型可识别目标。

关键配置：

```json

  "conf_threshold": 0.60,
  "nms_threshold": 0.45,
  "input_queue_capacity": 1,
  "npu_core_mode": "all"

```

注意：一帧没有目标时，当前YoloDetector不会发布`DetectionResult`，这本身不表示线程停止。

不要用未经重新训练的ReLU性能探针判断识别精度。

代码：

## 8. YOLO有结果但画面没有框

重点检查`FrameCompositor`：

- 解码帧和检测结果的`frame_sequence`是否一致；
- 检测是否超过`max_detection_frame_lag`；
- 检测框宽高是否有效；
- `AnnotatedCount()`是否增长；
- `DroppedFrameCount()`或`ErrorCount()`是否增长；
- 类别名是否来自正确配置。

数据流：

```text
DecodedFrame ───────────────┐
DetectionResult(frame_seq) ─┴→ FrameCompositor → AnnotatedFrame
```

代码：`src/video/frame_compositor.cpp`。

## 8.1 视觉稳定性判定不锁定或频繁丢失

数据流：

```text
YoloDetector 帧级观测（每推理帧一条）
  → VisualTargetMonitor
  → VisualTargetStatus（SEARCHING/ACQUIRING/LOCKED/LOST）
```

排查顺序：

1. `YoloDetector::ObservationCount()` 是否随帧增长？
   - 不增长：问题在推理链路（后端异常、无输入帧、模型未加载），与门限无关；
   - 增长：继续下一步。
2. `YoloDetector::DetectedObservationCount()` 是否增长？
   - 不增长：模型当前看不到目标，检查画面内容、置信度阈值和模型是否匹配；
   - 增长：继续下一步。
3. 看日志中的视觉稳定性行（默认每5秒一条摘要，状态变化时另有一条）：

   ```text
   视觉稳定性状态变化: SEARCHING -> ACQUIRING 连续检测=1 ... 累计转换=1 累计观测=1
   视觉稳定性状态变化: ACQUIRING -> LOCKED 连续检测=5 ... 累计转换=2 累计观测=5
   视觉稳定性摘要: state=LOCKED valid=true 连续检测=812 ... 上次检测=0ms前 累计观测=1230 累计转换=2
   ```

   - 一直是 `SEARCHING` 但 `累计观测` 在涨：模型没看到目标，不是门限问题；
   - 长期 `ACQUIRING`：`visual_monitor.lock_frames` 相对实际检测率过大；
   - 频繁 `LOCKED <-> LOST` 且 `累计转换` 快速增长：检测在间歇抖动，先查YOLO侧；
   - 报 `视觉观测超时，判定目标丢失`：观测流中断，回到第1步查推理线程。

注意：

- 该状态当前只是影子输出，不驱动飞行控制；
- 不要为了让状态“看起来稳定”而盲目增大 `lost_frames`，应先确认漏检根因；
- 状态变化本身不打日志；需要看时序时观察 `LastStatus()` 或订阅 `kVisualTargetStatus`。

代码和文档：

- `src/perception/visual_target_monitor.cpp`；
- `include/perception/视觉目标稳定性判定.md`。

## 11. 地面站没有目标ACK

按顺序检查：

1. 地面站GCS心跳是否建立连接；
2. TIMESYNC是否达到`SYNCHRONIZED`；
3. 65010目标地址是否为当前飞机`1/25`；
4. `protocol_version`是否为1；
5. `target_id`是否非0；
6. 经纬度范围是否合法；
7. `flags`是否只使用bit0～bit6；
8. `update_seq`是否严格递增；
9. `valid_for_ms`和传输年龄是否仍有效。

错误地址按协议静默，不发送ACK。其他拒绝通常返回65011及原因码。

**实链发现（2026-10-16 / 2026-10-19）：目标流运行中突然停止刷新 + 一批 result=13 被拒**——
`地面站心跳超时: timeout_ms=3000` WARN 与随后的 `地面站心跳建立` 成对出现即为该模式：
心跳中断超过 `heartbeat_timeout_ms` 后**按设计置离线并清空时间同步**，离线期间到达的
目标一律按 TIME_SYNC_UNAVAILABLE（result=13）拒收；心跳恢复后还需重新积累
`minimum_samples` 个 TIMESYNC 样本（≈1 秒）才恢复接收；估计器会先打
`目标估计状态已过期`，恢复时打 `目标估计器重新初始化: reason=previous_state_expired`。
实链例：心跳中断 3~4s → 约 10 / 5 条目标被拒（result=13）→ 自动恢复，总空窗 ~2~3 秒。
机载节流日志通常看不到这批拒绝，需从地面站目标记录核对。**心跳为何缺失取决于地面站
侧**（其 1Hz 心跳定时器与目标流同链路，故障时仅心跳缺失）——在 GS 主机/服务端观察
发送时间戳定位；机载侧行为符合设计，不是缺陷。

**2026-10-19 再次复现（0041）**：16:02:26 先出现
`地面站时间同步偏移突变: state=SYNCHRONIZED->DEGRADED` → 74ms 后目标估计过期；
16:02:45 `地面站心跳超时: timeout_ms=3000` → 1s 后心跳恢复、再 1s 后时间同步建立 →
`目标估计器重新初始化: reason=previous_state_expired`。两次都在约 1~1.5s 内自动恢复，
目标流最终累计到 1800 条（count=1800）。Web 控制台同期可见 V2_EXTENSION 与
TRACK_TARGET_ACK 连续，目标流未整体中断；1Hz 心跳发送时间戳已在 Web 平台补打点
（`GS_HB_DIAG_LOG=1` 逐秒打印，或 `/api/health` 的 `diagnostics.heartbeat`；见
`tools/web平台/README.md`「心跳诊断」），下次实链用于区分「GS 未发」与「发了但丢」。
同日 0043 复核（16:38~16:42）在目标流稳定段（16:40:01~16:42:35，约 2.5 分钟）未再出现
心跳超时或时间同步 DEGRADED，说明问题非持续复现；待更长驻留与 GS 诊断记录定位。
本轮与 Home 漂移无关（Home 变化仅打
`PX4 Home变化（诊断记录，估计器不重置）`），问题定位仍在 GS 侧 1Hz 心跳发送/事件循环

## 12.1 「PX4 Home变化」WARN 每约 2 秒重复刷屏

现象（2026-10-16 晚 至 2026-10-20）：`PX4 Home变化（诊断记录，估计器不重置）: 旧=(...) 新=(...) gps_fix=N 卫星=N eph=... epv=... 锚点ref=(...收N) 局部位置=(...)`
——**方案 C 落地后 Home 变化不再重置估计器**，该 WARN 只是漂移观测记录；旧文案
`PX4 Home变化，目标估计器已重置局部NED滤波状态` 仅存在于 2026-10-16 及以前的日志。
该版本以精确 ≈2.0s 周期逐条持续出现。

**2026-10-20 日志降噪后**：每次启动只保留**首条**完整明细，其后改为**每 30s 一条**
`PX4 Home变化窗口汇总（周期|停止）: 窗口=...s 变化=N次 首=(...) 末=(...)
水平范围=...x...m 净漂移=...m 高度净漂移=±...m 高度范围=...m 最大单步=...m +
gps_fix/卫星/eph/epv/锚点ref/局部位置`；停止时强制输出未满 30s 的窗口。
判读 Home 漂移仍看窗口行（首条明细给出起点，窗口行给出次数/范围/净漂移/最大单步）。
首条明细与窗口汇总之间的采样间隔最多 30s，需要更高分辨率时临时降低日志等级或
在独立探针中采集，不在生产热路径恢复逐条打印。

**先判性质，这通常不是 Bug**（2026-10-13 室内首测、**2026-10-15 室外复测定论**）：

- 2.0s 周期 = PX4 默认 0.5Hz `HOME_POSITION` 广播周期；
- PX4 在 **disarmed 期间会持续把 Home 更新为当前全局位置估计**（`HomePosition::update`，
  disarmed+landed 时按 `max(2×eph, 1.0m)`/`max(2×epv, 1.5m)` 判据刷新），
  全局位置估计本身随 GNSS/EKF 游走 → Home 跟着漂；
- **2026-10-15 室外实测订正（重要）**：室外开阔高地、良好收星（卫星 21~29 颗、
  eph 0.58~0.87m）条件下 **Home 依然持续漂移**（12 分钟水平包络 ≈20m×5m、高度
  22m 平滑往复），**维护者现场确认 QGC 同源数据同步漂移**——**"室外稳定 fix 后
  Home 应收敛"的旧判据不成立**，漂移是 PX4/GNSS 侧行为（非机载代码缺陷），
  与收星质量非简单相关（多路径/卫星几何变化/气压计温漂共同作用）；
- **诊断字段用法（2026-10-15 新增）**：
  - `锚点ref=(纬度,经度,高度,收N)`：EKF 投影参考锚点（GPS_GLOBAL_ORIGIN），
    **收 N = 锚点被重设的次数**——N 不增长且数值恒定 = 锚点稳定（即"坐标系锚
    不随全局估计漂移"，与 Home 的漂移形成对照）；N 持续增长 = 锚点也在变；
    ⚠️ **2026-10-16 实机订正（根因：消息号写错）**：**GPS_GLOBAL_ORIGIN 的消息号
    是 49，不是 411**（411 = CURRENT_EVENT_SEQUENCE）——历史配置把锚点流请求写成
    411，因此实机 PX4 对两条请求分别回 `REQUEST_MESSAGE(411)`→result=2、
    `SET_MESSAGE_INTERVAL(411)`→result=4（**配置已订正为 49**）。订正前 `--`/收0
    **不能判读为"锚点稳定"**（也可能是流未实例化）；先用只读探针定案：
    `px4_link_smoke --probe-message-interval 49`（interval_us=-1 → 流未实例化；
    >0 → 该流按此周期调度，此时"收 0"才等于"锚点稳定"，详见
    `tools/px4_link_smoke.md` §2.4）。定案前不要用"收 N"做处置方案裁决；
  - `局部位置=(x,y,z)`：飞机相对锚点的局部坐标——静止时的漂移量即
    "EKF 局部估计残差"（方案裁决的关键收益量）；
  - 三者一条日志齐全：Home 漂（全局快照）/ ref（锚点）/ local（局部残差）。
- **Home 生命周期（PX4 v1.17.0 源码结论，2026-10-16）**：`Commander.cpp:1841` 自动
  跟随条件 = `!已解锁 && landed && 无任务`，阈值 = 水平 max(2×eph,**1m**) / 垂直
  max(2×epv,**1.5m**)（`HomePosition.hpp:54-55`）。即：**未解锁期间 PX4 持续把 Home
  贴到当前位置估计上**；**解锁即停更（Home 冻结）**，起飞瞬间（`Commander.cpp:2145-
  2150`，`was_landed && !landed`）再按离地那一刻重设一次；`COM_HOME_IN_AIR=0`（默认）
  → 飞行中不再跟随（例外：起飞后 120s 内的高度一致性修正、航向重置改 yaw、显式
  `DO_SET_HOME`）；落地+上锁后自动跟随恢复。**推论：解锁后"Home 漂移 + 每 2s 重置"
  在实飞阶段自消；但锁存值 = 解锁/起飞时刻的估算值，不是真值。**
- **"局部 NED 原点 = PX4 Home" 是近似约定（飞行阶段存在固定偏置 H）**：项目约定见
  `flight_controller.cpp:519-521`，但 PX4 局部帧原点实际是 EKF 锚点（#49，已实测
  稳定），Home 是另一个点。地面阶段 PX4 让 Home 贴住飞机 → 目标 NED（Home 原点）
  与自身/视觉（锚点原点）的基准差 ≤ 跟随阈值（1~2m，漂移的大幅摆动被"贴住"机制
  吸收）；**起飞后 Home 冻结而飞机飞走 → 基准差变为固定值 H ≈ 起飞时刻飞机的局部
  坐标**（实测同漂移量级，几米；上电后搬机再起飞则为搬动距离）。H 影响：S5 引导
  指向偏 H；视觉与目标估计的创新偏差 = H，而 S7 交接创新门限为 3m —— **|H|>3m 会
  吃掉交接判定**。当前快照只有 Home 全局量（`types.h` 无 home 局部坐标），补偿需先
  补字段；**统一到锚点基准（方案 C，锚点已实测稳定）可一并消除地面重置与空中偏置**。
- **实机验证（2026-10-16 下午，0040 会话 + 探针）**：配置订正后启动期 **12/12 请求
  result=0**（原 sequence=3/12 的 result=2/4 消失）；探针 `--probe-message-interval 49`
  输出 `interval_us=1000000`（流已实例化、1Hz）+ REQUEST_MESSAGE ACK=0 + 实收 1 帧
  （锚点值与会话内 `锚点ref` 一致）；该会话 4.5 分钟内锚点 `收1` 数值恒定，而 Home
  水平 8.9m/高度 10.5m 平滑往复、局部位置同步（9.2m/10.9m）→ **"Home 漂而锚不漂"
  坐实**（漂的是位置估计本身，不是基准）。

处置结果（2026-10-16 定案并落地）：

- **方案 C（换用 EKF 锚点做转换基准）已实施**：目标估计器换算一律以锚点

## 17.1 S5 位置速度前馈（P3，2026-10-19）

现象与排查：

- **S5 意图前馈全为 0**：先查 `controller.enable_position_velocity_feedforward`

- **前馈值偏小/被截断**：查 `FlightController::ClampedCount()` 是否增长与

  水平模长与垂直分量分别钳制。按目标速度谱设置上限（P1）。
- **前馈某轴被丢弃**：查 `FeedforwardDroppedCount()` 与节流 WARN“前馈轴非有限已丢弃”
  /“前馈掩码含未知位”。坏轴只丢该轴，位置意图照常发布，属安全降级。

- **接近围栏时过冲**：前馈不参与位置围栏（围栏只钳制位置目标），边界附近可能
  出现瞬态过冲，由 PX4 geofence 兜底；需要更保守时降低 `max_feedforward_mps`。
- **前馈已到控制器但 PX4 行为无改善**：先在 PTY 契约用例确认线上 type mask 同时
  放行位置与速度轴；再用 `--sitl-stage4-feedforward`（FF 开/关）复跑 A/B 并核对
  `tools/feedforward_report.py` 的稳态滞后；同时核对 PX4 `MPC_XY_VEL_MAX`/`MPC_XY_P`。
  2026-10-19 SITL 实测 FF 开启使 p95|lag| 从 1.49m 降到 0.40m。

## 17.2 拦截后返航/降落（S11~S14，2026-10-19）

- **发射后不停留 S10、直接进 S12**：属 V1 单发设计（发射命令入队即视为动作结束，不判命中）；`return_home.enabled=false` 仅用于捕网执行器隔离测试。
- **S12 原地悬停**：`home_valid`/`ned_ref_valid`/`local_position_valid` 任一无效，或返航超 60s；查 WARN「返航等待 Home/EKF 锚点有效」「返航超时」。Home 局部坐标由 Home 经纬度 + EKF 锚点换算，不依赖 `HOME_POSITION.x/y/z`。
- **S12 不进入 S13**：到达判据为水平 2m、垂直 0.5m、水平速度 0.5m/s 持续 1s；查位置/速度遥测、位置意图 reason 低位=8。
- **S13 不发 AUTO.LAND**：命令接口未注入（`enable_control=false` 或装配异常）、PX4 已被 failsafe 接管（状态机按设计让权、只监控）；查 WARN「AUTO.LAND 入队失败」「PX4 已离开 Offboard」。
- **S13 落地后不到 S14**：仍 armed 且 DISARM（400）未 accepted；查命令 ACK/PX4 disarmed。
- **不应出现 PX4 RTL**：正常返航不切 RTL；若观察到 4/5，说明返航设定值流中断触发了 PX4 Offboard 丢失 failsafe，或 PX4 被其他 failsafe 接管——按 PX4 侧参数与链路排查。

## 17.3 S9/S10 拦截入口（2026-10-19）

- **一直不进 S9**：先查 `interception.enabled`（生产默认 **false**，需在本地副本显式开启）；再逐项查 `lock_frames` 连续 LOCKED、测距 `valid`+新鲜且落在 `min_range_m~max_range_m`（**射程为占位值，必须按实机捕网有效射程冻结**）、PX4 `connected+armed+Offboard(6/0)`、姿态/局部位置有效、命令接口已注入、捕网未触发/无复位挂起。`min_battery_percent` 当前保持 **0（不启用）**；设为 >0 后若电池遥测无效或低于门限，S9 入口会被保守挡住。
- **S9 进进出出**：看 WARN「拦截条件失效」——通常是视觉状态断流、测距超龄/越窗、PX4 离开 Offboard 或锁定帧计数被 LOST 清零；S9 条件恢复后由 S7 重新进入。
- **S9 不自动进 S10**：`auto_authorize=false` 时地面站确认授权协议尚未实现，只能等 `authorization_timeout_ms` 超时返航；V1 现场使用应保持 `auto_authorize=true` 或等待授权协议落地。
- **S9/S10 期间飞机减速/刹车**：S9/S10 设计为继续输出视觉伺服意图；若日志显示伺服降级/停发，按 S7 伺服排查（姿态/视觉超龄）。
- **入口默认安全**：`interception.enabled=false` 时整机不会自动发射；`enable_control=false` 时即使开启也无命令接口（S9 入口条件不满足）。

## 17.4 G4 串口台架（2026-10-20）

- **启动即报“必须同时提供 --bench-ack-props-off”**：这是强制安全确认，不是参数错误；
  拆桨、固定机体、遥控器可接管后再加该开关。
- **报“只允许 transport=serial”**：台架模式不接 UDP SITL；UDP 用
  `--sitl-stage4-controller`，两者互斥。
- **预检停在 landed/armed/位置姿态**：查 PX4 是否真的落地且未解锁、EKF 局部位置
  与姿态是否有效；台架不允许在 armed/空中启动。Home 无效只 WARN，但 ARM 可能被
  PX4 preflight 拒绝。
- **ARM ACK denied**：查 PX4 preflight、GPS/Home、遥控器链路与 QGC 告警；禁止
  force arm。`--bench-ack-props-off` 不等于允许绕过 PX4 安全检查。
- **脉冲段报方向判定失败**：看打印的控制器发布侧设定值北/东分量；若设定值方向正确
  但电机实际方向不对，按 G4-2 人工记录并检查电机/桨序/机架坐标约定，不要改工具
  阈值掩盖。
- **停发后不退出 Offboard**：查 PX4 `COM_OF_LOSS_T`、Offboard 丢失保护参数与
  串口链路；工具只停发意图，不主动切模式。
- **停发时 landed=false**：工具拒绝 DISARM 并尝试 AUTO.LAND；先确认是否真的离地，
  不要为通过测试伪造 landed 或强制上锁。
- **完整命令、自动判定项与人工项**：`tools/px4_link_smoke.md` §2.5。

## 19. 静止期日志噪音（周期性摘要刷屏）

现象（2026-10-10 室内 PX4 验证日志实证，`logs/0028_*.log`）：没有目标/没有检测时，
以下周期摘要按固定间隔重复打印几乎相同的内容，污染日志：

| 行 | 来源 | 间隔 | 静默期表现 |
|---|---|---|---|
| `双目测距摘要: 帧=0 匹配帧=0 … 处理avg=0.00ms` | StereoRanger | 10s | 全 0，无信息量 |
| `视觉稳定性摘要: state=LOST … 连续丢失=N` | VisualTargetMonitor | 5s | 状态与内容不变 |
| `视觉跟踪影子摘要: 模式=零速刹车 … 距离=--(有效=0)` | VisualTrackingShadow | 10s | 状态与内容不变 |

**已修复（2026-10-12，代码内静默抑制，间隔配置不变）**：

1. **StereoRanger**：窗口内无帧、无发布、无截断、无未配对（四项累计计数均无增量，
   即无目标时的全 0 行）⇒ 整段摘要（含阶段耗时行）跳过；启动后首个窗口仍打印一次。
2. **VisualTargetMonitor**：窗口内无有效检测、状态停在 `SEARCHING/LOST`、无状态转换、
   无新增错误 ⇒ 摘要跳过（状态转换另有独立的状态变化日志）；启动后首个窗口仍打印一次。
   **LOCKED 期间即使本窗口无检测也照常打印**——连续丢失增长是掉锁前兆，必须可观测。
3. **VisualTrackingShadow**：离散状态（模式/有效/coast/虚拟姿态/距离有效性）变化时
   立即打印一次；窗口到期时与上次打印指纹完全相同（含速度/距离数值）⇒ 跳过；
   首拍必打印一次。

改完后静默期日志只剩生命周期/错误/状态变化行；**一旦有目标/检测/异常，摘要照常出现**
（回归用例：三组件各一条 `SummarySuppressed*` 测试守住该行为）。

仍保留的兜底手段（应急，勿作常态）：
- 降频：调大 `visual_monitor.status_log_interval_ms`（现 5s）、
  `stereo_ranger.summary_log_interval_ms`（现 10s）、
  `visual_tracking.shadow.summary_log_interval_ms`（现 10s）到 30~60s；
- 临时静音：`config/config.json` 的 `log.level` 改 `warn`——会同时丢掉 INFO 级
  生命周期信息（启动/连接/状态机转移），只建议短时排查用。


## 20. 视觉观测融合（TargetEstimator 第二阶段）

开关 `runtime.enable_visual_position_fusion`（依赖目标估计器+双目测距+PX4，配置期校验）。
语义：视觉观测只在地面站有效期内细化估计，不初始化、不延展（§19 纪律下跳过类不打日志，
只计数）。

### 20.1 视觉更新计数一直为 0（VisualUpdateCount 不增长）

按门禁链从上往下查（每类拒绝有细分 reason 的节流 WARN）：

| 拒绝 reason | 含义 | 排查 |
|---|---|---|
| 视觉距离不可用或字段非有限 | valid=false / NaN | 双目测距侧：有效占比、近端簇点数（stereo_ranger.md） |
| 视觉观测时刻为0 | 帧缺失批次的节拍消息 | 正常节拍，不计异常 |
| 视觉观测时刻在未来 | 钟域错乱 | source_time_ms 来自左目帧 timestamp，应与 steady_clock 同域 |
| 视觉观测超龄 | 管线积压超过 max_observation_age_ms | 看测距处理耗时与帧率 |
| 同帧多框歧义 | 一帧多个框 | v2 单目标约定；确认场景确实单目标 |
| PX4快照缺失或超龄 | flight_state_max_age_ms 内无快照 | PX4 链路/心跳（第 10 节） |
| PX4姿态无效 / 局部位置无效 | attitude_valid / local_position_valid 为 false | 室内无 GPS fix 时 local_position 无效属预期 |

未初始化（无地面站目标）与地面站已过期两类**跳过不计错误**——视觉不造目标、
不延展有效期（过期政策归状态机）。

### 20.2 视觉 NED 方向/位置系统性错误

- 固定角度偏转：`target_estimator.visual.mount_*` 仍是全 0 准直假设（未标定）？
  1° 安装误差 ≈ 20m 处 0.35m 系统偏差；标定前属预期。
- 整体平移错误：核对 **LOCAL_POSITION_NED 原点 ≈ HOME_POSITION** 假设——
  室外悬停时把 GLOBAL_POSITION_INT 经 `GeodeticToLocalNed(Home, …)` 换算后与
  LOCAL_POSITION_NED 对比；PX4 EKF origin 在 GPS 切源时可静默重置，发现不一致
  先怀疑原点假设。
- 估计滞后/相位延迟：观测已过 EMA（smooth_alpha=0.4）再过 KF 的双重平滑，
  影子阶段录制对比后再决定是否调参。
