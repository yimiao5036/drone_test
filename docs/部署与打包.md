## 一、部署形态：目录式打包（绿色软件）

正式工程采用 Linux 目录式部署：可执行文件、配置文件、模型文件组成一个自包含目录，
整个目录拷贝到香橙派任意位置即可运行，不依赖安装过程。

```
drone_app/                        ← 整个目录 = 一个软件包
├── drone_control                 ← ARM64 可执行文件（香橙派上编译，Release + strip）
├── config/
│   └── config.json               ← 配置（log / yolo 等配置节）
├── models/
│   └── yolo26n_int8.rknn         ← YOLO 模型
└── logs/                         ← 运行时自动生成
```

部署实例：`tar -xzf drone_app.tar.gz -C /opt/ && cd /opt/drone_app && ./drone_control`。

## 二、路径解析约定（config.h 第 7 步实现时的强制要求）

程序必须能"知道自己在哪里"，所有路径相对自身目录解析，保证目录拷到任何位置都能运行：

1. **程序目录定位**：启动时读 `/proc/self/exe` 符号链接得到可执行文件所在目录
   `app_dir`（Linux 标准做法）。
2. **相对路径解析**：配置、模型、日志一律相对 `app_dir` 解析：
   - 配置：`app_dir/config/config.json`
   - 模型：`app_dir/models/`（config.json 内 `yolo.model_path` 写相对路径，如
     `models/yolo26n_int8.rknn`，config 模块加载时拼接）
   - 日志：`app_dir/logs/`（不存在时自动创建）
3. **候选路径链（E 方案）**：`config.json` 的查找按优先级依次尝试，先找到者胜出：
   1. 命令行参数（如 `--config <路径>`，V1 可选）
   2. 环境变量（如 `DRONE_CONFIG`，V1 可选）
   3. 程序目录旁：`app_dir/config/config.json`
   4. 当前工作目录：`./config/config.json`（兜底，与现状行为一致）
   全部未找到时：打告警日志，使用内置默认值启动（不崩溃）。
4. **禁止写死绝对路径**：部署机路径（如 `/opt/drone_app/`）与开发机不同，
   config.json 内不得出现开发机专属绝对路径。

> 说明：当前 `main.cpp` 的 `LoadLogConfig` 使用相对路径 `config/config.json`
> （依赖进程工作目录）。第 7 步实现 `config.h` 时按本约定收口，替换现有逻辑。

## 三、打包流程（部署前执行，当前未实施）

在**香橙派**上编译（可执行文件不能跨架构：开发机 x86_64 产物无法在 ARM64 运行），
然后白名单拷贝 + strip + 压缩：

```bash
# 第 1 步：香橙派上编译（Release + RKNN 后端）
# ARM64 原生构建默认开启 RKNN；-U 用于清除旧缓存中的 OFF 值。
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -U DRONE_HAVE_RKNN
cmake --build build -j6

# 构建 drone_control 后，CMake 会自动复制仓库 models/ 到 build/models/，
# 便于直接运行 build/drone_control；正式发布仍按下面白名单整理。

# 第 2 步：整理发布目录（白名单拷贝，只放运行所需文件）
mkdir -p drone_app/config drone_app/models
cp build/drone_control          drone_app/
cp config/config.json           drone_app/config/
cp models/yolo26n_int8.rknn     drone_app/models/

# 第 3 步：去除调试符号（见"源码保护"）
strip drone_app/drone_control

# 第 4 步：压缩为安装包
tar -czf drone_app.tar.gz drone_app/
```

固化方式（后续实施）：新增 `deploy/pack.sh` 打包脚本 + CMake `install()` 规则
（`cmake --install` 直接产出 drone_app/），一条命令出包。脚本采用白名单拷贝，
杜绝误带源码。

## 四、源码保护

### 基本认知

- C++ 编译为机器码后，**源代码不进入发布包**：`include/`、`src/`、`CMakeLists.txt`
  一律不进包，他人拿到可执行文件看不到任何一行源码，只能对机器码逆向。
- 但这不意味着零风险，以下措施按"必须/可选"分级。

### 必须措施（发布前执行）

1. **Release 编译**：`-DCMAKE_BUILD_TYPE=Release`（`-O3` + `NDEBUG`），
   优化后的机器码难以阅读。当前开发机默认构建未设 Release，发布前必须显式指定。
2. **strip 符号表**：`strip drone_control`。不 strip 时，逆向工具（Ghidra/IDA/
   objdump）可直接看到 `YoloDetector::DetectLoop`、`RknnDetectionBackend` 等
   函数名与结构，大幅降低逆向门槛。
3. **不打包源码**：发布目录白名单拷贝（见打包流程），只含可执行文件、配置、模型。
4. **日志字符串是明文**：机器码内嵌字符串（日志文本、路径等）可用 `strings`
   直接查看。日志中不得写入模型内部结构、算法细节、密钥等敏感信息
   （现状"只打关键路径"日志纪律已覆盖大部分场景）。

### 可选增强（按需，成本递增）

| 手段 | 工具 | 效果 | 成本 |
|------|------|------|------|
| 模型加密 | Rockchip 官方 rknn-toolkit（模型加密导出） | `.rknn` 模型文件加密，板端解密加载 | 需查官方文档确认当前版本流程 |
| 代码混淆 | Obfuscator-LLVM（OLLVM）/ Hikari | 函数名/控制流混淆，逆向难度大增 | 需重新配置工具链 |
| 可执行压缩 | UPX | 增加静态分析难度 | 嵌入式慎用（兼容性） |

> 模型加密可行性：Rockchip 提供模型加密能力，具体版本流程**待查官方文档确认**
> 后再采用，不得凭记忆操作。

### 现实预期

任何软件都无法 100% 防逆向，但对本系统：
- **代码逻辑**：Release + strip 后，从机器码还原完整业务逻辑成本极高；
- **模型**：`.rknn` 为 NPU 专用量化格式，脱离 RK3588 环境难以复用；
- 真正敏感的信息应放服务端/授权机制，比单纯防逆向可靠。

## 七、图传输出部署：MediaMTX 中转方案（2026-08-14 确定）

### 7.1 架构

思翼（SIYI）链路要求：供其拉取的 RTSP 视频地址必须落在 `192.168.144.0/24` 网段，
且 `.11/.12/.20` 已被链路天空端/地面端/手持地面站占用、不可用。为不绑定思翼专用
接口、便于日后更换图传设备，采用 **MediaMTX 中转**：

```
真实相机 .25 ─拉流─▶ 香橙派程序 ─推流─▶ 本机 mediamtx(127.0.0.1:8554/drone_out)
                                        │ 对外发布 rtsp://<香橙派144IP>:8554/drone_out
                                        ▼
                          任意图传/思翼地面端 ─拉取─
```

要点：
- 香橙派程序 `VideoSender` 仍用 RTSP **主动推流**，但目标指向本机 mediamtx
  （`config.video.output_rtsp = rtsp://127.0.0.1:8554/drone_out`），无需改代码。
- mediamtx 对外发布，供图传/地面端**拉取**（`rtsp://192.168.144.201:8554/drone_out`
  或 `.202`，视思翼可达的香橙派网卡 IP）。
- **换图传设备 = 不动香橙派代码/配置**，只要新设备支持 RTSP 拉流。

### 7.2 香橙派部署步骤（已验证到 mediamtx 可启动监听 8554）

1. 下载 MediaMTX **arm64** 版（RK3588）：
   `https://github.com/bluenviron/mediamtx/releases` → `mediamtx_<ver>_linux_arm64.tar.gz`。
   国内可用镜像 `ghproxy / mirror.ghproxy.com / gh-proxy.com`；或 Windows 下载后 scp。
2. 解压放到 `/opt/mediamtx/mediamtx`，并放置配置 `/opt/mediamtx/mediamtx.yml`
   （仓库：`deploy/mediamtx.yml`）。配置要含 `drone_out`（`source: publisher`），并
   **必须 `moq: false`**（否则 MoQ 需写 `auto.key/auto.crt`，目录无写权限会整体退出）；
   `rtmp/hls/webrtc/srt` 按需置 false。目录需 `chown orangepi:orangepi /opt/mediamtx`。
3. 启动（systemd 自启）：
   - 手工验证：`cd /opt/mediamtx && ./mediamtx mediamtx.yml` → 应日志 `RTSP started :8554` 且持续不退出。
   - 注册自启：写 `/etc/systemd/system/mediamtx.service`（ExecStart=
     `/opt/mediamtx/mediamtx /opt/mediamtx/mediamtx.yml`，User=orangepi，Restart=always），
     `systemctl enable --now mediamtx`；`ss -tlnp | grep 8554` 应看到监听。
   - 一键脚本：`deploy/install_mediamtx.sh`（二进制若已放 /opt/mediamtx/ 可直接跑）。

### 7.3 写配置文件踩坑记录（香橙派实操）

- **heredoc 在该终端常卡在 `> ` 提示符（`^C`）**：换用 `printf '%s\n' '行1' '行2' ... > 文件`
  一次写入；粘贴时不要在行尾残留 `\` 续行（会被终端渲染成 `│` 报错）。
- **YAML 顶层键不可重复**：往已有 yml 末尾追加 `moq/srt/...` 会“key already defined”；
  应整份重写，一次性把所有服务开关写全。
- **MoQ 证书**：`moq: false` 可避免需写 `auto.key/auto.crt`；否则目录必须可写。

### 7.4 图传/思翼拉取地址与传输协议

- 本机验证：`ffprobe -rtsp_transport tcp rtsp://127.0.0.1:8554/drone_out`
- Wi-Fi 管理网验证：`rtsp://192.168.31.163:8554/drone_out`
- HM30/QGC 正式地址：`rtsp://192.168.144.202:8554/drone_out`
- **RTSP 必须使用 TCP**：HM30 链路实测 VLC/QGC 使用 UDP RTP 时花屏或只有会话无画面，
  强制 TCP 后画面稳定。MediaMTX 配置应为：
  ```yaml
  rtspTransports: [tcp]
  ```
  VLC 验证命令：
  ```powershell
  & "C:\Program Files\VideoLAN\VLC\vlc.exe" `
    --rtsp-tcp --network-caching=500 `
    "rtsp://192.168.144.202:8554/drone_out"
  ```
- QGC 选择 `RTSP Video Stream`，URL 填写 `.202/drone_out`；MediaMTX 仅允许 TCP 后，
  QGC 无需额外填写传输协议参数。

### 7.5 双网口重叠子网的永久配置教程（NetworkManager/nmtui）

#### 7.5.1 问题背景与最终拓扑

摄像头和 HM30 都使用 `192.168.144.0/24`，但分别接在香橙派两个物理网口。若两个网口
都配置 `/24`，Linux 会生成两条相同子网路由并按 metric 选择其中一条，导致摄像头或
HM30 流量走错网口。最终固定配置如下：

| 接口 | 用途 | 香橙派地址 | 路由职责 |
|------|------|------------|----------|
| `enP3p49s0` | 摄像头专用 | `192.168.144.201/32` | 仅 `192.168.144.25/32` |
| `enP4p65s0` | HM30/Windows/QGC | `192.168.144.202/24` | 整个 `192.168.144.0/24` |
| `wlP2p33s0` | Wi-Fi 管理 | `192.168.31.163/24` | 默认网关 `192.168.31.1` |

两个有线连接都不配置 Gateway 和 DNS，默认路由只保留在 Wi-Fi。`/32` 摄像头地址用于
阻止系统自动在 `enP3p49s0` 上再生成一条冲突的 `192.168.144.0/24` 路由。

#### 7.5.2 确认连接名称

```bash
CAM_CONN="$(nmcli -g GENERAL.CONNECTION device show enP3p49s0)"
HM_CONN="$(nmcli -g GENERAL.CONNECTION device show enP4p65s0)"
echo "摄像头连接：$CAM_CONN"
echo "HM30连接：$HM_CONN"
```

当前实机名称为：

```text
Wired connection 1 → enP3p49s0
Wired connection 2 → enP4p65s0
```

#### 7.5.3 用 nmtui 配置摄像头连接

运行：

```bash
sudo nmtui
```

选择 `Edit a connection` → `Wired connection 1`，设置：

```text
Device: enP3p49s0
IPv4 Configuration: Manual
Addresses: 192.168.144.201/32
Gateway: 留空
DNS servers: 留空
Routing → Edit → Add:
  Destination/Prefix: 192.168.144.25/32
  Next Hop: 留空
  Metric: 留空即可
[X] Never use this network for default route
[X] Ignore automatically obtained routes
[X] Ignore automatically obtained DNS parameters
[X] Automatically connect
[X] Available to all users
```

路由中的 Next Hop 必须留空，因为摄像头是直连设备。保存后，`Routing` 不应再显示
`No custom routes`。

#### 7.5.4 用 nmtui 配置 HM30 连接

编辑 `Wired connection 2`：

```text
Device: enP4p65s0
IPv4 Configuration: Manual
Addresses: 192.168.144.202/24
Gateway: 留空
DNS servers: 留空
Routing: 不添加自定义路由
[X] Never use this network for default route
[X] Ignore automatically obtained routes
[X] Ignore automatically obtained DNS parameters
[X] Automatically connect
[X] Available to all users
```

`192.168.144.202/24` 会自动生成 HM30 侧的整网段直连路由，无需手工再添加 `/24`。

#### 7.5.5 重新激活并验收

```bash
sudo nmcli connection down "$CAM_CONN"
sudo nmcli connection up "$CAM_CONN"
sudo nmcli connection down "$HM_CONN"
sudo nmcli connection up "$HM_CONN"
```

检查地址：

```bash
ip -br addr
```

期望：

```text
enP3p49s0  UP  192.168.144.201/32
enP4p65s0  UP  192.168.144.202/24
wlP2p33s0  UP  192.168.31.163/24
```

检查路由选择：

```bash
ip route get 192.168.144.25
ip route get 192.168.144.12
ip route get 192.168.144.5
```

期望：

```text
192.168.144.25 dev enP3p49s0 src 192.168.144.201
192.168.144.12 dev enP4p65s0 src 192.168.144.202
192.168.144.5  dev enP4p65s0 src 192.168.144.202
```

链路验证：

```bash
ping -I enP3p49s0 -c 4 192.168.144.25
ping -I enP4p65s0 -c 4 192.168.144.12
```

当前实机两条链路均已验证 `0% packet loss`。最后执行 `sudo reboot`，重启后重复地址、
路由和 ping 检查；配置仍存在才算永久配置验收通过。

### 7.6 MediaMTX 与视频链路验收

1. 服务状态：
   ```bash
   sudo systemctl is-enabled mediamtx
   sudo systemctl is-active mediamtx
   sudo ss -ltnp | grep ':8554'
   ```
   期望 `enabled`、`active` 且 8554 正在监听。
2. 本机流信息：
   ```bash
   ffprobe -v error -rtsp_transport tcp \
     -show_entries stream=codec_name,width,height,r_frame_rate \
     -of default=noprint_wrappers=1 \
     rtsp://127.0.0.1:8554/drone_out
   ```
   当前实测为 H.264、1280×720、25 fps。
3. 持续出帧：
   ```bash
   ffmpeg -nostdin -hide_banner -loglevel warning -stats \
     -rtsp_transport tcp \
     -i rtsp://192.168.144.202:8554/drone_out \
     -map 0:v:0 -t 10 -f null -
   ```
   当前实测 10 秒约 245 帧。
4. Windows/QGC：Windows 地址 `192.168.144.5` 可 ping `.202`、TCP 8554 可达，ARP
   映射到 `enP4p65s0` 的 MAC `c0:74:2b:f8:7e:e7`；QGC 使用 TCP 后无花屏。
