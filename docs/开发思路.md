### 1.3 工作流程

整个系统采用多线程并发架构，各线程通过共享队列和消息机制进行数据交换与协同。共包含以下 6 个核心线程：

#### 1.3.1 线程总览

#### 1.3.2 线程职责与数据流

##### ① 视频处理线程（Video Thread）

- **输入**：摄像头（SIYI A8mini）原始视频流
- **处理**：
  1. 从摄像头读取原始视频帧
  2. 解码并做预处理（尺寸缩放、格式转换、归一化等），使其满足 YOLO 模型输入要求
  3. 将预处理后的帧送入**目标识别队列**
  4. 从识别队列取回带检测框的图像帧，编码为 H.264 供图传模块下发
- **输出**：预处理后的图像帧 → 目标识别线程；H.264 编码流 → 通讯线程（图传）

##### ② 目标识别线程（Detect Thread）

- **输入**：视频处理线程送来的预处理帧
- **处理**：
  1. 对每一帧执行 YOLO 目标检测（识别目标为无人机）
  2. 在原图上绘制检测框、置信度等标注信息
  3. 根据检测结果（目标位置、大小、运动趋势等）计算飞控指令（如追踪、悬停、降落等）
- **输出**：
  - 带检测框的图像帧 → 送回视频处理线程（供编码与图传）
  - 飞控指令 → 控制指令队列 → 飞机控制线程

##### ③ 飞机控制线程（Control Thread）

- **核心**：多状态状态机（如：待机、起飞、追踪、悬停、降落、紧急停止等）
- **输入**：
  - 目标识别线程发来的飞控指令
  - 通讯线程转发的地面引导指令
  - 避障保护线程的避险信号
  - 从飞控（PX4）读取的当前飞行状态（位置、姿态、速度、电池等）
- **处理**：
  1. 维护状态机，根据当前状态判定是否执行外部传入的指令
  2. 仅当状态机允许时，将指令注入 PX4 飞控（通过 MAVSDK 或串口 MAVLink）
  3. 定期从飞控拉取飞行信息，打包转发给通讯线程
- **输出**：MAVLink 指令 → PX4 飞控；飞行状态信息 → 通讯线程

##### ④ 通讯线程（Communication Thread）

- **输入**：
  - 下行：飞机控制线程传入的飞行状态、视频处理线程传入的 H.264 编码流
  - 上行：数传图传电台接收到的地面端数据
- **处理**：
  1. 下行数据打包（飞行状态 + 视频流），通过电台发送至地面站
  2. 上行数据解析：将地面引导指令转为内部指令格式（可考虑加入预测/平滑处理）
  3. 将地面指令转发至飞机控制线程的控制指令队列
- **输出**：数传/图传射频信号 ↔ 地面站

##### ⑤ 避障保护线程（Safe Thread）

- **输入**：
  - 摄像头画面（光流信息）
  - TF-Luna 激光雷达测距数据
- **处理**：
  1. 融合视觉光流与激光雷达数据，判断无人机前方是否有障碍物
  2. 根据危险等级决定避障策略（减速、转向、悬停、紧急刹车）
  3. 必要时直接向 PX4 飞控发送紧急避险指令（可绕过状态机以缩短响应时间）
- **输出**：避障/避险指令 → PX4 飞控（或同时通知控制线程）

##### ⑥ 摄像头控制线程（Camera Heartbeat Thread）

- **职责**：维持摄像头的心跳保活，**不主动调节摄像头参数**
- **处理**：
  1. 定时向摄像头发送心跳包，确保连接不断开
  2. 仅在系统初始化时做一次摄像头配置
  3. 运行期间一般保持摄像头当前状态（焦距、光圈等均由自动模式维持）
  4. 特定情况下会控制相机转向
- **输出**：心跳信号 → 摄像头

#### 1.3.3 线程间通信机制

| 数据流 | 生产者 | 消费者 | 通信方式 |
|--------|--------|--------|----------|
| 预处理后的视频帧 | 视频处理线程 | 目标识别线程 | 共享帧队列（生产者-消费者） |
| 带检测框的图像帧 | 目标识别线程 | 视频处理线程 | 共享帧队列 |
| 飞控指令 | 目标识别线程/通讯线程 | 飞机控制线程 | 指令消息队列 |
| 飞行状态信息 | 飞机控制线程 | 通讯线程 | 状态共享区 + 信号量 |
| H.264 编码流 | 视频处理线程 | 通讯线程 | 环形缓冲区 |
| 避险指令 | 避障保护线程 | PX4 飞控（直连） | 串口/MAVLink（绕过状态机） |

| 编号 | 状态 | 说明 | 触发来源 | 可迁往状态 |
|------|------|------|----------|-----------|
| ① | `INIT` | 初始态，系统上电/启动后的初始阶段，等待各模块初始化完成 | 系统启动 | ② |
| ② | `READY` | 准备态，所有模块就绪，无人机待命，等待地面起飞指令 | ① 初始化完成 | ③ |
| ③ | `TAKEOFF` | 起飞态，无人机从地面起飞至指定高度 | ② + 地面起飞指令 | ④ |
| ④ | `GUIDED_FOLLOW` | 跟随引导态，按地面站发送的引导指令飞行至指定位置（GPS/RTK 引导） | ③ 到达高度、地面引导指令 | ⑥ |
| ⑥ | `TRACKING` | 追踪态，YOLO 连续 N 帧均检测到目标后自动切入，持续追踪目标 | ④ + YOLO 持续检测到目标 | ⑦ |
| ⑦ | `INTERRUPTED` | 中断态，处于追踪态时 YOLO 连续 M 帧丢失目标，进入中断等待 | ⑥ + YOLO 丢失目标 | ⑧ |
| ⑧ | `TRACKING_END` | 追踪结束态，任务完成或中断超时后进入，决定下一步动作 | ⑥/⑦ + 任务完成或超时 | ⑩/⑪ |
| ⑨ | `EMERGENCY_EVASION` | 紧急避险态，起飞后任何状态下遇到危险均可无条件切入，优先级最高。**避险时间短 → 恢复避险前任务；避险时间长 → 转入降落或返航** | **任何状态** + 避障保护线程触发 | 恢复原状态 / ⑩ / ⑪ |
| ⑩ | `LANDING` | 降落态，垂直下降至地面 | ⑧/⑨ + 电量充足时选择降落 | ⑫ |
| ⑪ | `RTL` | 返航态，自动返航至起飞点（Return To Launch），着陆 | ⑧/⑨ + 电量不足时自动返航 | ⑫ |
| ⑫ | `DISARMED` | 上锁态，无人机电机上锁，结束任务入库 | ⑩/⑪ 着陆完成 | — |

**状态迁移要点：**

- **跟随引导 → 追踪（④ → ⑥）**：当系统处于跟随引导飞行时，若 YOLO 检测模块在连续 N 帧中均稳定发现目标，自动切入追踪态，由"飞向引导点"切换为"追踪目标"。
- **追踪 → 中断（⑥ → ⑦）**：追踪过程中若 YOLO 连续 M 帧（N < M）均未检测到目标（目标丢失或被遮挡），切入中断态，在此状态下短暂等待目标重新出现。
- **中断 → 追踪结束（⑦ → ⑧）**：若中断超时（目标长时间未出现），进入追踪结束态，不再等待。
- **追踪结束 → 降落/返航（⑧ → ⑩/⑪）**：根据当前无人机剩余电量决定：
  - 电量充足 → 直接降落
  - 电量不足 → 自动返航
- **紧急避险（⑨）**：**起飞之后**的任何状态，避障保护线程均可通过**直接注入飞控**的方式切入紧急避险态，不受状态机约束（硬抢占），确保实时安全。避险解除后根据避险持续时长分两种情况处理：
  - **短时避险**：避险动作完成后，恢复到避险前正在执行的任务状态（如之前正在追踪则回到追踪态），继续原任务流程
  - **长时避险**：避险持续较长时间（超时阈值），判定当前任务已不可继续，转入降落态或返航态（根据电量决定）
- **上锁（⑫）**：降落或返航着陆后自动上锁，任务终结。

## 2 视频编解码与目标检测 （视频处理线程 + 目标识别线程）

### 2.2 视频输入与MPP硬件解码

#### 2.2.1 RTSP流接入

- 摄像头型号：SIYI A8mini，通过以太网输出 RTSP 视频流
- 拉流方式：使用 FFmpeg（libavformat / libavcodec）打开 RTSP URL，获取 H.265 编码的 AVPacket
- 关键参数：
  - 协议：`rtsp://<camera_ip>:<port>/<stream_path>`
  - 传输：优先 TCP（`rtsp_transport=tcp`），减少丢包
  - 超时：设置 `stimeout`（如 5s），避免网络异常时阻塞
  - 输出格式：提取 H.265 Annex-B 裸流（含 SPS/PPS/VPS），逐包送入 MPP 解码器

#### 2.2.2 MPP解码器初始化

| 配置项 | 值 | 说明 |
|-------|---|------|
| 上下文类型 | `MPP_CTX_DEC` | 解码模式 |
| 编码格式 | `MPP_VIDEO_CodingHEVC` | H.265/HEVC |
| `base:split_parse` | `1` | **必须启用**，让MPP内部自动进行NAL单元分帧 |
| 输出格式 | NV12（硬件默认） | 后续由RGA转换 |

初始化流程：
1. `mpp_create()` → 创建 MPP 上下文
2. `mpp_init(ctx, MPP_CTX_DEC, MPP_VIDEO_CodingHEVC)` → 初始化为 H.265 解码器
3. 配置 `split_parse = 1`（通过 `MPP_DEC_GET_CFG` / `MPP_DEC_SET_CFG`）
4. `mpp_packet_init()` → 创建复用的 MppPacket 对象

#### 2.2.3 送包-取帧循环（pkt_done 模式）

采用官方 `mpi_dec_test` 的 **pkt_done 控制送取交替循环**：

```
while (!eos) {
    从RTSP读取一个H.265数据包 → 设置到MppPacket

    do {
        // 阶段1: 送包
        if (!pkt_done)
            ret = decode_put_packet(ctx, packet)
            if (ret == OK) pkt_done = 1

        // 阶段2: 取帧（循环取出所有可用帧）
        do {
            ret = decode_get_frame(ctx, &frame)
            if (frame == NULL) break

            if (info_change) → 处理分辨率变化
            if (正常帧)     → 送入RGA预处理 → 返回
            if (eos帧)     → 结束
        } while (1)

        if (pkt_done) break     // 包已送完，读下一个包
        usleep(1000)            // 队列满，等待后重试
    } while (1)
}
```

**关键设计要点：**
- 送包失败（`MPP_ERR_BUFFER`，队列满）时**不重试**，立即转入取帧阶段释放输出压力
- 取帧超时采用有限次重试（如30次 × 1ms），避免永久阻塞
- 每次外层循环保证"至少尝试送一次包 + 尝试取所有帧"

#### 2.2.4 info_change 事件处理

当视频流分辨率发生变化（如摄像头切换模式）时，MPP 会报告 `info_change` 事件：

处理步骤：
1. 从 frame 中获取新的 `width`、`height`、`hor_stride`、`ver_stride`、`buf_size`
2. 创建（或复用）外部 `MppBufferGroup`（类型 `MPP_BUFFER_TYPE_DRM`）
3. 调用 `MPP_DEC_SET_EXT_BUF_GROUP` 将 buffer group 交给解码器
4. 调用 `MPP_DEC_SET_INFO_CHANGE_READY` 通知解码器继续工作
5. 更新内部帧尺寸记录，后续 RGA 按新尺寸处理

> ⚠️ 若不处理 info_change，解码器将停止输出帧，导致系统卡死。

### 2.3 RGA硬件预处理

#### 2.3.1 处理目标

将 MPP 解码输出的 NV12 帧转换为 YOLO26n 模型所需的输入格式：

| 项目 | 源（MPP输出） | 目标（NPU输入） |
|------|------------|-------------|
| 像素格式 | NV12 (YCbCr_420_SP) | RGB888 |
| 分辨率 | 1920×1080（摄像头原始） | 640×640 |
| 填充方式 | 无 | Letterbox（等比缩放 + 灰色填充） |
| 内存布局 | 带 stride 对齐 | 连续内存 |

#### 2.3.2 Letterbox 策略

为保持目标宽高比不变形，采用 Letterbox 填充：

1. 计算缩放比例：`scale = min(640/src_w, 640/src_h)`
2. 缩放后尺寸：`new_w = src_w × scale`，`new_h = src_h × scale`
3. 填充偏移：`x_pad = (640 - new_w) / 2`，`y_pad = (640 - new_h) / 2`
4. 填充颜色：灰色（114, 114, 114）
5. 记录 `{x_pad, y_pad, scale}` 供后处理坐标还原使用

#### 2.3.3 RGA调用方式

```cpp
// 源: NV12 带stride
rga_buffer_t src = wrapbuffer_virtualaddr(src_ptr, src_w, src_h,
                                          hor_stride, ver_stride,
                                          RK_FORMAT_YCbCr_420_SP);
// 目标: RGB888 640×640
rga_buffer_t dst = wrapbuffer_virtualaddr(dst_ptr, 640, 640,
                                          640, 640,
                                          RK_FORMAT_RGB_888);
// 执行: 缩放 + 格式转换（RGA硬件一次完成）
imresize(src, dst);
```

> 注：Letterbox 填充可通过 RGA 的 `imcomposite` 或分步 `imresize` + `imfill` 实现；
> 也可先 RGA 缩放再由 CPU 填充，视性能需求选择。

### 2.4 NPU推理（RKNN）

#### 2.4.1 模型信息

| 项目 | 说明 |
|------|------|
| 模型文件 | `yolo26n_int8.rknn` |
| 量化精度 | INT8（INT8 量化，速度优先） |
| 输入尺寸 | 640×640×3 (RGB) |
| 输入类型 | `RKNN_TENSOR_UINT8`（0~255，无需归一化） |
| 输出 | 多尺度检测头（box回归 + 分类得分 + score_sum） |
| NPU核心 | 使用 RK3588 的 3 个 NPU 核心（可配置） |

#### 2.4.2 内存管理

采用 **RKNN 零拷贝内存**（`rknn_tensor_mem`）模式提升性能：

1. 初始化时通过 `rknn_create_mem()` 预分配输入/输出 tensor 内存
2. 每帧推理前将 RGB 数据填入预分配的输入内存（避免重复 malloc）
3. 通过 `rknn_set_io_mem()` 绑定输入/输出内存到推理上下文
4. 推理完成后直接从输出内存读取结果（零拷贝）

#### 2.4.3 推理执行

```
1. 将预处理后的 RGB888 640×640 数据写入 input_mem
2. rknn_run(ctx) → 执行推理
3. 从 output_mem 读取原始张量数据
4. 将张量数据交给后处理模块
```

> 可选优化：使用多上下文（ctx[0~2]）实现流水线并行——当 NPU Core0 推理第 N 帧时，CPU 同时后处理第 N-1 帧。

### 2.5 后处理

#### 2.5.1 YOLO输出解析

YOLO26n 输出为多尺度检测头（如 80×80、40×40、20×20 三个网格），每个网格包含：
- **box_tensor**：边界框回归值（含 DFL 编码）
- **score_tensor**：各类别置信度
- **score_sum_tensor**：得分汇总（用于加速过滤）

解析步骤：
1. **DFL 解码**：对 box_tensor 执行 Distribution Focal Loss 解码，得到精确的 `(x1, y1, x2, y2)`
2. **置信度过滤**：遍历所有网格点，保留 `score > BOX_THRESH (0.25)` 的候选框
3. **坐标还原**：将 640×640 坐标映射回原始图像坐标（利用 Letterbox 记录的 pad 和 scale）

#### 2.5.2 NMS（非极大值抑制）

- 阈值：`NMS_THRESH = 0.45`
- 按类别分组，对同类别候选框按置信度降序排列
- 依次计算 IoU，抑制重叠框
- 输出最终检测结果列表：`{box, cls_id, confidence}[]`

#### 2.5.3 绘制检测框 & 计算飞控指令

- 在原始 RGB 图像上绘制：矩形框 + 类别标签 + 置信度文字
- 根据检测结果计算飞控指令：
  - 目标中心偏移量 → 偏航/俯仰调整
  - 目标框面积（大小） → 距离估计 → 油门调整
  - 目标运动趋势（多帧跟踪） → 速度前馈

### 2.6 MPP硬件编码

#### 2.6.1 编码目的

将带有检测框标注的图像帧编码为 H.265 视频流，通过通讯线程（图传）下发至地面站，供操作员实时观察识别结果。

#### 2.6.2 编码器配置

| 配置项 | 值 | 说明 |
|-------|---|------|
| 上下文类型 | `MPP_CTX_ENC` | 编码模式 |
| 编码格式 | `MPP_VIDEO_CodingHEVC` | H.265/HEVC |
| 输入格式 | RGB888 | 需RGA转为NV12或直接支持 |
| 分辨率 | 与检测输出帧一致（如640×640或原始分辨率） | 可配置 |
| 码率控制 | CBR / VBR | 根据图传带宽选择 |
| 帧率 | 25~30 fps | 与解码帧率匹配 |

#### 2.6.3 编码流程

```
1. 接收带检测框的 RGB 帧
2. （如需）RGA 转换格式/缩放至编码目标尺寸
3. 将帧数据填入编码输入 MppBuffer
4. encode_put_frame() → 送入编码器
5. encode_get_packet() → 取出编码后的 H.265 数据包
6. 将编码数据写入环形缓冲区 → 供通讯线程读取发送
```

### 2.7 类/文件结构设计

```
src/
├── videoProcess.hpp / .cpp     ← 视频处理线程（解码 + 预处理 + 编码）
├── detect.hpp / .cpp           ← 目标识别线程（NPU推理 + 后处理）
├── postProcess.hpp / .cpp      ← 后处理工具（DFL、NMS、绘制、指令计算）
```

#### 各类职责

| 类名 | 文件 | 职责 |
|------|------|------|
| `VideoProcess` | videoProcess.hpp/cpp | 管理 RTSP 拉流、MPP 解码、RGA 预处理、MPP 编码；持有帧队列的读写端 |
| `Detector` | detect.hpp/cpp | 管理 RKNN 模型加载/推理/内存；从帧队列取帧 → 推理 → 输出检测结果 |
| `PostProcess` | postProcess.hpp/cpp | 纯算法工具类：DFL解码、NMS、坐标映射、绘制检测框、计算飞控指令 |
| `FrameQueue` | frameQueue.hpp | 线程安全的有界队列，支持背压（满时丢弃最旧帧或阻塞） |

#### 关键数据结构

```cpp
/// 一帧图像及其元数据
struct Frame {
    std::vector<uint8_t> data;   ///< RGB888 像素数据
    int width, height;           ///< 图像尺寸
    int64_t timestamp;           ///< 时间戳 (ms)
    int frame_id;                ///< 帧序号
};

/// 单个检测结果

struct DetectResultList {
    int frame_id;
    std::vector<DetectResult> results;
};

/// 飞控指令（由检测结果计算得出）
struct ControlCommand {
    float yaw_delta;     ///< 偏航增量
    float pitch_delta;   ///< 俯仰增量
    float throttle_delta;///< 油门增量
    int   action;        ///< 动作码（追踪/悬停/降落等）
};
```

### 2.8 线程间数据交互

#### 2.8.1 队列设计

| 队列 | 生产者 | 消费者 | 容量 | 满时策略 |
|------|--------|--------|------|----------|
| 预处理帧队列 | VideoProcess | Detector | 2~3帧 | 丢弃最旧帧（保证实时性） |
| 检测结果队列 | Detector | VideoProcess | 2~3帧 | 丢弃最旧帧 |
| 编码流缓冲区 | VideoProcess | 通讯线程 | 环形缓冲(如256KB) | 覆盖最旧数据 |
| 飞控指令队列 | Detector | Control线程 | 8条 | 丢弃最旧指令 |

#### 2.8.2 帧同步与背压

- **实时性优先**：视频流处理不追求每帧都处理，允许跳帧，但保证延迟最小
- **背压策略**：当 NPU 推理速度 < 解码速度时，帧队列满则丢弃最旧的未处理帧
- **帧ID关联**：每帧携带唯一 `frame_id`，检测结果与编码帧通过 `frame_id` 匹配
- **无锁设计（可选）**：帧队列可采用 `std::atomic` + 环形数组实现无锁 SPSC 队列

#### 2.8.3 数据流时序

```
VideoProcess线程              Detector线程              Control线程
     │                            │                       │
     │── 解码帧N → 帧队列 ──────▶│                       │
     │                            │── 推理帧N             │
     │                            │── 后处理              │
     │◀── 带框帧N ← 结果队列 ────│                       │
     │── 编码帧N → 图传缓冲       │── 指令N → 指令队列 ──▶│
     │                            │                       │── 注入飞控
     │── 解码帧N+1 → 帧队列 ───▶│                       │
     ...                         ...                     ...
```

### 2.9 异常处理与容错

| 异常场景 | 检测方式 | 处理策略 |
|---------|---------|----------|
| RTSP连接断开 | FFmpeg 返回错误/超时 | 自动重连（指数退避，最大间隔10s），重连期间暂停解码线程 |
| 解码失败（errinfo/discard） | `mpp_frame_get_errinfo()` / `get_discard()` | 跳过该帧，记录日志；连续失败超阈值则重置解码器 |
| info_change（分辨率突变） | `mpp_frame_get_info_change()` | 重建外部 BufferGroup，通知解码器继续（见2.2.4） |
| 送包队列满 | `decode_put_packet` 返回 `MPP_ERR_BUFFER` | 立即停止送包，转入取帧阶段释放压力 |
| 取帧超时 | `decode_get_frame` 返回 `MPP_ERR_TIMEOUT` | 有限重试（30次×1ms），仍超时则跳过本轮 |
| NPU推理失败 | `rknn_run()` 返回非0 | 记录错误，跳过该帧；连续失败则重新初始化模型 |
| NPU推理耗时异常 | 单帧推理 > 100ms | 触发告警，检查NPU负载/温度 |
| RGA转换失败 | `imresize()` 返回非 `IM_STATUS_SUCCESS` | 跳过该帧，记录错误信息 |
| 编码器输出异常 | `encode_get_packet` 失败 | 重置编码器上下文 |
| 帧队列持续为空 | 消费者等待超时（如 > 2s） | 通知上游线程检查，必要时重启视频处理线程 |

**总体容错原则：**
- 单帧异常 → 跳过，不影响后续帧处理
- 模块级异常 → 尝试重置该模块（如重新初始化解码器/编码器）
- 连接级异常 → 自动重连 + 通知状态机（控制线程可据此切换状态）
- 所有异常均记录日志（含时间戳、错误码），便于事后排查
