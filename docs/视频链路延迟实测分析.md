# 视频链路延迟实测分析

> 测试日期：2026-09-09  
> 测试平台：Orange Pi 5 Plus（RK3588）  
> 工具：`video_latency_probe`  
> 测试时长：120秒，10秒输出一次，统计窗口为最新2048个样本  
> 当前配置：1280×720、25 FPS、H.264输出码率6000000 bit/s

## 1. 测量边界

本次从摄像头编码访问单元进入机载进程开始，到H.264数据写入本机RTSP发布端结束。

不包含：

- 摄像头曝光、传感器读出和摄像头内部编码；
- 摄像头到机载电脑的网络传输；
- MediaMTX之后的HM30链路；
- 地面站FFmpeg转码、JSMpeg缓冲和浏览器显示。

因此本文结论只用于判断机载进程内部的视频处理瓶颈，不能代表完整端到端显示延迟。

## 2. 吞吐量

120秒累计收到2997个编码访问单元，平均约24.98 FPS；解码、YOLO、叠加和H.264发送均累计2947帧。输入与后续阶段固定相差约50帧，差值从第10秒开始不再增长，说明差值主要形成于启动同步阶段，稳定运行后各阶段均维持约25 FPS，没有持续积压或持续丢帧。

RTSP写包统计比编码帧少2个样本，整个测试期间差值不增长，符合编码器内部少量延迟包尚未在快照时写出的表现，未观察到持续推流丢失。

## 3. 主要结果

### 3.1 前90秒稳定区间

| 阶段 | 平均 | P95 | P99 | 结论 |
|---|---:|---:|---:|---|
| 解码输入排队 | 0.21 ms | 1 ms | 4 ms | 无解码输入积压 |
| H.264硬解与NV12转存 | 3.47 ms | 5.23 ms | 5.38 ms | 正常且稳定 |
| 入口到解码输出 | 3.60 ms | 6 ms | 6 ms | 正常 |
| YOLO输入排队 | 14.07 ms | 34 ms | 38 ms | 检测链路主要等待项 |
| YOLO/RKNN完整处理 | 29.17 ms | 38.02 ms | 40.29 ms | 接近25 FPS单帧40 ms预算 |
| 入口到YOLO完成 | 46.82 ms | 74 ms | 82 ms | 检测结果约滞后1～2帧 |
| NV12复制与标注 | 0.49 ms | 0.66 ms | 1.05 ms | 不是瓶颈 |
| H.264输入准备 | 0.46 ms | 0.66 ms | 0.91 ms | 不是瓶颈 |
| H.264编码与RTSP调用 | 1.68 ms | 3.03 ms | 7.55 ms | 硬编码性能充足 |
| RTSP单包写入 | 0.40 ms | 0.92 ms | 3.34 ms | 本机RTSP无明显阻塞 |
| 入口到本地RTSP完成 | 6.06 ms | 9 ms | 14.53 ms | 机载视频支路通常低于一帧 |

### 3.2 90秒后的解码长尾

维护者确认当前输入是H.264/AVC；首版探针的“H265硬解”只是固定显示文案，并不代表FFmpeg实际识别结果。该文案已改为根据`EncodedFrame.codec`动态显示。

90秒后，H.264解码与NV12转存耗时开始上升：

| 快照时刻 | 解码平均 | 解码P95 | 解码P99 | 入口到本地RTSP P95 |
|---:|---:|---:|---:|---:|
| 90 s | 3.47 ms | 5.23 ms | 5.38 ms | 9 ms |
| 100 s | 4.37 ms | 10.12 ms | 21.22 ms | 13 ms |
| 110 s | 4.97 ms | 21.10 ms | 21.27 ms | 23 ms |
| 120 s | 6.52 ms | 21.16 ms | 30.37 ms | 23 ms |

最终快照是最近2048帧、约82秒的混合窗口，仍包含较早的稳定样本，因此`6.52 ms`不是最后10秒的独立平均值。按窗口替换量估算，最后10秒新进入窗口的解码样本平均耗时约16 ms，仅用于判断变化趋势，不作为精确阶段指标。

解码输入队列P95始终约1 ms，编码、叠加和YOLO处理耗时也没有同步恶化，所以当前没有证据表明整个系统发生全面CPU过载。异常更集中于解码器取帧、DRM硬件帧转存或相关硬件调度路径。温度/频率变化、场景和码流复杂度变化仍需通过同步采样确认，不能仅凭本次数据确定原因。

即使出现该长尾，120秒快照中的入口到本地RTSP完成仍为平均8.93 ms、P95 23 ms、P99 32.53 ms、最大36 ms，尚未超过25 FPS对应的40 ms单帧预算，也未造成持续队列积压。

## 4. 瓶颈判断

### 4.1 当前主要瓶颈是检测链路

`入口→YOLO完成`平均约47 ms、P95约74 ms、P99约84 ms，显著高于本地视频发布支路。其组成主要是：

- 解码约3～7 ms；
- YOLO输入等待平均约12～14 ms、P95约33～35 ms；
- RGA预处理、RKNN推理、输出搬运和后处理合计平均约28～29 ms、P95约38 ms。

YOLO总吞吐仍达到约25 FPS，说明当前不是持续算力不足，而是存在明显的帧到达抖动、阶段相位或短时服务时间波动。仅凭聚合数据不能判断输入排队来自解码帧成簇到达，还是连续慢推理造成，需要增加解码输出帧间隔和YOLO各子阶段统计。

### 4.2 H.264编码和本机RTSP不是瓶颈

H.264输入准备平均约0.45 ms，编码与推送调用平均约1.5～1.7 ms，RTSP写包平均约0.4 ms；编码输入队列P95约1 ms。现阶段不应优先投入H.264零拷贝或RTSP写入优化。

### 4.3 叠加不是瓶颈

完整NV12复制、检测框和文字叠加平均约0.49 ms、P95约0.65 ms。当前1280×720下性能余量充分。

## 5. 检测框显示时序说明

YOLO与视频叠加/编码是并行支路。叠加线程不会等待同一帧YOLO完成，而是使用取帧时已经收到的最新检测结果。

因此：

- `入口→本地RTSP完成`约6～9 ms不代表检测框也能在6～9 ms后出现；
- 检测结果平均约47 ms后才生成，此时原始帧和下一帧通常已经完成叠加；
- 新检测框通常只能应用到更后面的帧，实际“目标出现到带框画面发布”预计还要等待下一个可叠加帧；
- 精确帧滞后应统计`当前叠加帧sequence - DetectionResult.frame_sequence`，不能通过现有14项指标直接得出。

该行为适合保持图传低延迟，但控制和状态估计必须使用检测结果自己的源帧时间戳，不能把带框视频的发布时间当作检测时间。

## 6. 后续验证与优化顺序

1. **先定位90秒后的解码长尾**：探针已把现有解码聚合耗时拆为AVPacket分配/码流复制、`avcodec_send_packet`、`avcodec_receive_frame`、`av_hwframe_transfer_data`、NV12内存池复制五项，细分窗口为最近256帧。
2. **增加运行时关联数据**：探针已增加实际输入编码、硬解/软解模式、区间FPS、区间码率和关键帧数；下一轮仍需同步记录热区温度与CPU频率，判断长尾是否与温度、码率、GOP或调度有关。
3. **测量检测帧龄**：增加YOLO消费时的`sequence`跳变、队列丢帧数，以及叠加时检测结果落后帧数。
4. **再优化YOLO等待**：可对比YOLO队列容量2与最新帧容量1。容量1可能通过主动丢弃短时旧帧降低最大帧龄，但必须以检测有效帧率和P95/P99实测决定。
5. **暂不优化H.264、RTSP和叠加**：这些阶段当前占比低，优化收益有限。
6. **最终做跨端测量**：硬件齐备后使用LED/时间码/高速摄影测量摄像头到浏览器的完整延迟。

## 7. 当前结论

- 稳态视频吞吐达到25 FPS，未发现持续丢帧和队列堆积。
- 正常区间内，机载入口到本地RTSP发布平均约6 ms、P95约9 ms，性能良好。
- H.264硬编码、本机RTSP写入和画面叠加均不是当前瓶颈。
- 检测链路是主要延迟来源：入口到YOLO完成平均约47 ms、P95约74 ms。
- 90秒后出现独立的H.264解码/转存长尾，虽尚未破坏25 FPS吞吐，但需要继续定位。
- 当前数据不能代表HM30和Web显示端到端延迟。
