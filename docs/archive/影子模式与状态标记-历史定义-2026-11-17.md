# 影子模式与状态标记的历史定义（2026-09 ~ 2026-11-16）

> **归档说明（2026-11-17）**：本文保留**已废弃**的"安全影子 / 影子链路"口径原文，供追溯。
> 现行定义见 [`../运行模式与模块状态定义.md`](../运行模式与模块状态定义.md)。
> 归档原因：见该文件 §1 —— "影子"同时指"整机运行模式"与"模块状态"，
> 导致功能代码去判断整机装配模式（S13a 影子分支即为反例，已删除）。

## 1. 旧的状态标记表（原 `项目总览与数据流.md` §3）

本文统一使用以下状态：

| 状态 | 含义 |
|---|---|
| 正式 | 已进入`DroneApplication`实际装配，处理真实数据 |
| 影子 | 运行真实算法并发布状态，但输出不产生飞行控制 |
| Stub | 只有接口或占位生命周期，没有正式业务算法 |
| 独立 | 单独子工程或工具，未进入正式`DroneApplication` |
| 阻塞 | 缺硬件资料、标定或实机条件，禁止猜测实现 |

## 2. 旧的 `enable_control` 口径

这些句子在 2026-09 ~ 2026-11-16 期间是准确的（当时仓库生产配置为 `false`），
2026-10-30 之后前半句已不成立，2026-11-17 起整体作废：

> - `config/config.json` 保持 `runtime.enable_control=false`，正式程序不向 PX4 发送飞行控制。
> - `enable_control=false`（仓库生产基线）：影子运行——不注入 PX4 快照源
>   （`SetPx4LinkSource`），授权链恒不通过、保持 IDLE 停发；`Px4Setpoint` 无消费者。
> - `enable_control=true`（仅现场本地副本，永不入库）：`SetPx4LinkSource` 注入 +
>   `Px4Link::SetInput(FlightController::SetpointOutput())` 绑定 + WARN
>   「正式控制输出已启用」；同分支注入状态机命令窄接口。
> - 回滚通道：把 `config/config.json` 的 `enable_control` 改回 `false` 重启即回纯影子。
> - 意图输入纪律：`FlightController` 只接 `MissionStateMachine::IntentOutput()`；
>   `VisualTrackingShadow` 的影子意图不带授权请求位，若接入控制器会每拍清锁存压死
>   授权门禁，永不接线。

## 4. 当时为什么这么设计

试飞期（2026-09 ~ 2026-10）确实需要一条"程序全跑、但绝不碰飞控"的保险：

1. 状态机/控制器/估计器都在快速迭代，出现异常时不能有任何控制输出；
2. PX4 只在室内串口做过只读验证，尚未室外首飞；
3. 门禁 G1~G5 还没走完，任何控制输出都必须是"显式打开"而非默认。

因此把整机装配切成两条路径，默认只读；功能内部也随之出现"影子分支"
（如 S13a 初版的 `landing_descent_phase_ = (enable_control && …)`）。

## 5. 为什么废弃

1. 2026-10-30 维护者把仓库默认配置改为 `enable_control=true`，"默认只读"已经不对称成立；
2. 2026-11-17 试飞（含事故）已经积累了足够实测，控制链本身不再需要靠"不接线"兜底；
3. 最关键的是第 3 条：**功能内判断装配模式会造出两条都要维护、都要测试的路径**，
   现场出问题时第一件事变成"现在跑在哪条路径"，反而增加风险。维护者当日的裁决是
   **功能里不判断影子、只看能力**，`enable_control` 降为纯装配层的"只读运行"开关。

具体反例与删除记录见 [`../降落与估计器保护设计-2026-11-17.md`](../降落与估计器保护设计-2026-11-17.md) §4.8。
