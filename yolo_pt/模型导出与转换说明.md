# YOLO26模型导出与RKNN转换说明

## 1. 当前材料

- `best.pt`：SHA-256 `e2b98214672628c2d901a18728dbe9cee60a3387d8270d10f26744d46b347ffb`；
- checkpoint记录的Ultralytics版本：8.4.131；
- 模型：`yolo26n.yaml`，单类别`Drone`，`reg_max=1`，checkpoint原生`end2end=True`；
- 训练：640×640、300 epochs、batch 128；
- checkpoint指标：precision 0.94338、recall 0.90882、mAP50 0.95413、mAP50-95 0.64603；
- 数据集：22568张，CC BY 4.0；本地train/valid/test为19752/1876/940张；
- 现有RKNN来源脚本：`pt_rknn.py`，通过Ultralytics直接`format="rknn"`导出。

checkpoint元数据声明Ultralytics AGPL-3.0。若产品对外分发或提供网络服务，应由维护者确认AGPL合规方式或Ultralytics企业许可；数据集使用时保留Roboflow来源和CC BY 4.0署名。

## 2. 当前RKNN为什么是`[1,5,8400]`

Ultralytics 8.4.131的RKNN导出器会：

1. 强制关闭YOLO26的end-to-end/TopK分支；
2. 导出非end2end的decoded box + score输出；
3. 对前4个框坐标按输入宽高归一化，避免框坐标0～640与分类分数0～1共用单tensor INT8 scale时压垮分类精度；
4. 生成`[1,4+nc,8400]`，单类别即`[1,5,8400]`；
5. 默认使用RKNN Toolkit2的W8A8、normal、channel和optimization level 3。

因此直接使用普通`format="onnx"`再手工转RKNN，不等价于Ultralytics的RKNN专用ONNX路径。

## 3. 网上三份代码核查

第一份与第三份完全重复，且不符合RKNN Toolkit2 2.3.2官方API：

- `merge_ptq_and_qat`不是2.3.2 `config()`参数；
- `custom_hybrid`属于`hybrid_quantization_step1()`，类型应为输入/输出名子图列表，不是`config(custom_hybrid='hybrid.cfg')`；
- `build(pre_compile=True)`不是2.3.2官方参数；
- `eval_perf_accuracy()`不是2.3.2接口；正确性能接口为`init_runtime(...)+eval_perf()`，量化分析接口为`accuracy_analysis()`；
- `RKNN_FLAG_PRIOR_HIGH`与这些PC转换参数无关；
- 300+校准图主要影响量化精度和转换时间，不会把相同W8A8图的推理时间从24ms降到15ms。

第二份手工ONNX→RKNN代码的RKNN调用流程基本成立，但存在模型语义风险：

- 官方2.3.2推荐`quantized_dtype="w8a8"`，也可省略使用默认值；
- 普通`yolo export format=onnx`会保留checkpoint的end2end分支，除非显式关闭；
- 普通ONNX导出不会应用Ultralytics RKNN专用坐标归一化包装；
- end2end/TopK可能无法正确转换，或得到`[1,300,6]`；
- decoded box像素坐标和0～1分类分数共用INT8输出scale时可能严重损失分类精度。

因此不能直接采用网上三份代码。

## 4. 基线复现

环境必须冻结：

```text
ultralytics==8.4.131
rknn-toolkit2==2.3.2
onnx>=1.16.1,<1.19.0
setuptools<82
```

运行：

```bash
cd yolo_pt
python3 pt_rknn.py 2>&1 | tee export_baseline.log
```

脚本显式使用：

```text
quantize=8（整数）
imgsz=640
batch=1
opset=19
simplify=True
fraction=1.0
```

opset 19是Ultralytics 8.4.131 RKNN导出的当前默认值；网上的opset 11只能作为独立候选，不能静默替换基线。

## 6. 转换候选

`export_rknn_candidates.py`复用Ultralytics的RKNN专用ONNX路径，在临时ONNX被删除前保存副本，并构建：

- `baseline`：显式复现W8A8/normal/channel/optimization level 3；
- `flash_attention`：仅增加`enable_flash_attention=True`，用于针对逐层报告中占9.04%的两个`exSDPAttention`做A/B。

先构建opset 19：

```bash
cd yolo_pt
python3 export_rknn_candidates.py --opset 19 --verbose-rknn \
    2>&1 | tee export_candidates_opset19.log
```

再把opset 11作为单独变量：

```bash
python3 export_rknn_candidates.py --opset 11 --verbose-rknn \
    2>&1 | tee export_candidates_opset11.log
```

输出目录为`best_rknn_model/`，包含：

```text
best-rk3588-opset19-normalized.onnx
best-rk3588-opset19-baseline.rknn
best-rk3588-opset19-flash_attention.rknn
best-rk3588-opset11-normalized.onnx
best-rk3588-opset11-baseline.rknn
best-rk3588-opset11-flash_attention.rknn
dataset.txt
metadata-opset19.yaml
metadata-opset11.yaml
```

每个候选在RKNN custom string中记录PT哈希、工具版本、opset和FlashAttention开关。

## 7. A/B纪律

每次只改变一个变量：

1. 当前生产模型 vs opset19 baseline：验证新流程可复现；
2. opset19 baseline vs opset19 flash：只比较FlashAttention；
3. opset19 baseline vs opset11 baseline：只比较opset；
4. 通过后再考虑ReLU/ReLU6训练候选；
5. 不把FlashAttention、opset、激活和attention删除混在一次模型中。

将候选复制到香橙派后，可通过探针参数直接覆盖模型路径，不修改生产JSON：

```bash
./build/video_latency_probe --duration 120 --interval 10 \
    --yolo-model ./models/candidates/best-rk3588-opset19-baseline.rknn \
    --yolo-queue 1 --npu-core all
```

每个模型必须验证：

- 输出shape/type/scale和框坐标语义；
- 同一图片的FP32/PT与INT8检测结果；
- 940张test或固定标注集的precision/recall/mAP；
- 远距离小目标召回率和误检率；
- 板端Y2平均/P50/P95/P99；
- `RKNN_QUERY_PERF_DETAIL`中的OP占比和核心分配。

性能更快但检测结果错误的模型不得进入正式配置。

## 8. 当前逐层结果对转换方向的约束

当前RKNN逐层结果：

```text
ConvExSwish       63.03%，100%落在Core0
exSDPAttention     9.04%，100%落在Core0
Split              5.21%，主要Core0
可三核分摊部分     约16.9%
Input/Output边界   合计35us
```

因此：

- `optimization_level=3`已经是当前默认，不会单独解决问题；
- 改量化校准图数量不会明显改变推理耗时；
- FlashAttention理论收益上限主要受9.04%的attention占比约束；
- opset可能改变图融合，但必须看逐层报告；
- 真正的大收益候选是改变SiLU/Swish结构，使63%的`ConvExSwish`不再全部落在单核，但这需要训练/微调和精度验证；
- 原始检测头输出、CPU解码只能争取约1ms级收益。

## 9. 数据集数量与划分核查

训练集19752张的绝对数量不算多，真正问题是独立样本数量、跨集合泄漏和负样本缺失。按Roboflow文件名去掉`.rf.<hash>`后统计：

```text
train：19752张，约3831个源basename，所有basename均有多个版本，单basename最多27张
valid：1876张，约1599个源basename
 test： 940张，约875个源basename
train-valid源basename重叠：1136
train-test源basename重叠：620
valid-test源basename重叠：247
```

对前250个train与valid/test重叠basename做64位dHash抽样：45个basename（18%）存在距离不大于5的近似重复，32个存在完全相同dHash。basename可能有同名碰撞，dHash也不是严格图像身份判定，但两者结合已经足以判定当前划分存在较高的数据泄漏风险。当前所有label文件均非空，数据集中没有明确的无无人机负样本，也会使真实场景误检评估失真。

Roboflow说明图像在导出前被Stretch到640×640，并生成多个盐椒噪声版本；正式运行却使用保持比例letterbox。建议后续按原始视频/拍摄序列分组后重新划分，再只对训练集在线增强，valid/test保留未增强原图；加入鸟、飞机、云、灯光、昆虫和纯背景等真实负样本。当前precision/mAP在清理泄漏前只能作为参考，不能作为最终验收基线。

训练数据不应简单按数量砍半，应保留多距离、多姿态、多天气、多背景的独立样本，删除相邻帧和增强副本冗余。量化校准则不需要使用全部1876张valid图；RKNN官方对normal算法建议约20～100张，Ultralytics建议300张以上。后续可从清理后的train中固定选取约300张代表性图片作为候选模型统一校准集，并保持test完全不参与训练和校准。校准数量不会改善推理速度，只影响量化精度和转换时间。

## 10. 后续训练候选

ReLU/ReLU6候选不能直接修改现有模型后投入生产。建议：

1. 加载`best.pt`；
2. 将Conv模块激活替换为ReLU/ReLU6；
3. 使用相同数据集充分微调；
4. 保存独立checkpoint；
5. 使用本文件的基线流程导出；
6. 先比较精度，再比较性能。

在维护者确认训练预算、训练设备和可接受精度下降前，不自动执行该结构修改。
