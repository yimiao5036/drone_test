# YOLO26模型导出与RKNN转换说明

## 1. 当前材料

- `best.pt`：SHA-256 `e2b98214672628c2d901a18728dbe9cee60a3387d8270d10f26744d46b347ffb`；
- checkpoint记录的Ultralytics版本：8.4.131；
- 模型：`yolo26n.yaml`，单类别`Drone`，`reg_max=1`，checkpoint原生`end2end=True`；
- 训练：640×640、300 epochs、batch 128；
- checkpoint指标：precision 0.94338、recall 0.90882、mAP50 0.95413、mAP50-95 0.64603；
- 数据集：22568张，CC BY 4.0；本地train/valid/test为19752/1876/940张；
- 现有RKNN来源脚本：`pt_rknn.py`，通过Ultralytics直接`format="rknn"`导出。

checkpoint元数据声明Ultralytics AGPL-3.0。若产品对外分发或提供网络服务，应由维护者确认AGPL合规方式或Ultralytics企业许可；数据集使用时保留Roboflow来源和CC BY 4.0署名。

## 2. 当前RKNN为什么是`[1,5,8400]`

Ultralytics 8.4.131的RKNN导出器会：

1. 强制关闭YOLO26的end-to-end/TopK分支；
2. 导出非end2end的decoded box + score输出；
3. 对前4个框坐标按输入宽高归一化，避免框坐标0～640与分类分数0～1共用单tensor INT8 scale时压垮分类精度；
4. 生成`[1,4+nc,8400]`，单类别即`[1,5,8400]`；
5. 默认使用RKNN Toolkit2的W8A8、normal、channel和optimization level 3。

因此直接使用普通`format="onnx"`再手工转RKNN，不等价于Ultralytics的RKNN专用ONNX路径。

## 3. 网上三份代码核查

第一份与第三份完全重复，且不符合RKNN Toolkit2 2.3.2官方API：

- `merge_ptq_and_qat`不是2.3.2 `config()`参数；
- `custom_hybrid`属于`hybrid_quantization_step1()`，类型应为输入/输出名子图列表，不是`config(custom_hybrid='hybrid.cfg')`；
- `build(pre_compile=True)`不是2.3.2官方参数；
- `eval_perf_accuracy()`不是2.3.2接口；正确性能接口为`init_runtime(...)+eval_perf()`，量化分析接口为`accuracy_analysis()`；
- `RKNN_FLAG_PRIOR_HIGH`与这些PC转换参数无关；
- 300+校准图主要影响量化精度和转换时间，不会把相同W8A8图的推理时间从24ms降到15ms。

第二份手工ONNX→RKNN代码的RKNN调用流程基本成立，但存在模型语义风险：

- 官方2.3.2推荐`quantized_dtype="w8a8"`，也可省略使用默认值；
- 普通`yolo export format=onnx`会保留checkpoint的end2end分支，除非显式关闭；
- 普通ONNX导出不会应用Ultralytics RKNN专用坐标归一化包装；
- end2end/TopK可能无法正确转换，或得到`[1,300,6]`；
- decoded box像素坐标和0～1分类分数共用INT8输出scale时可能严重损失分类精度。

因此不能直接采用网上三份代码。

## 7. A/B纪律

每次只改变一个变量：

1. 当前生产模型 vs opset19 baseline：验证新流程可复现；
2. opset19 baseline vs opset19 flash：只比较FlashAttention；
3. opset19 baseline vs opset11 baseline：只比较opset；
4. 通过后再考虑ReLU/ReLU6训练候选；
5. 不把FlashAttention、opset、激活和attention删除混在一次模型中。

将候选复制到香橙派后，可通过探针参数直接覆盖模型路径，不修改生产JSON：

```bash
./build/video_latency_probe --duration 120 --interval 10 \
    --yolo-model ./models/candidates/best-rk3588-opset19-baseline.rknn \
    --yolo-queue 1 --npu-core all
```

每个模型必须验证：

- 输出shape/type/scale和框坐标语义；
- 同一图片的FP32/PT与INT8检测结果；
- 940张test或固定标注集的precision/recall/mAP；
- 远距离小目标召回率和误检率；
- 板端Y2平均/P50/P95/P99；
- `RKNN_QUERY_PERF_DETAIL`中的OP占比和核心分配。

性能更快但检测结果错误的模型不得进入正式配置。

## 8. 当前逐层结果对转换方向的约束

当前RKNN逐层结果：

```text
ConvExSwish       63.03%，100%落在Core0
exSDPAttention     9.04%，100%落在Core0
Split              5.21%，主要Core0
可三核分摊部分     约16.9%
Input/Output边界   合计35us
```

因此：

- `optimization_level=3`已经是当前默认，不会单独解决问题；
- 改量化校准图数量不会明显改变推理耗时；
- FlashAttention理论收益上限主要受9.04%的attention占比约束；
- opset可能改变图融合，但必须看逐层报告；
- 真正的大收益候选是改变SiLU/Swish结构，使63%的`ConvExSwish`不再全部落在单核，但这需要训练/微调和精度验证；
- 原始检测头输出、CPU解码只能争取约1ms级收益。

## 9. 数据集数量与划分核查

训练集19752张的绝对数量不算多，真正问题是独立样本数量、跨集合泄漏和负样本缺失。按Roboflow文件名去掉`.rf.<hash>`后统计：

```text
train：19752张，约3831个源basename，所有basename均有多个版本，单basename最多27张
valid：1876张，约1599个源basename
 test： 940张，约875个源basename
train-valid源basename重叠：1136
train-test源basename重叠：620
valid-test源basename重叠：247
```

对前250个train与valid/test重叠basename做64位dHash抽样：45个basename（18%）存在距离不大于5的近似重复，32个存在完全相同dHash。basename可能有同名碰撞，dHash也不是严格图像身份判定，但两者结合已经足以判定当前划分存在较高的数据泄漏风险。当前所有label文件均非空，数据集中没有明确的无无人机负样本，也会使真实场景误检评估失真。

Roboflow说明图像在导出前被Stretch到640×640，并生成多个盐椒噪声版本；正式运行却使用保持比例letterbox。建议后续按原始视频/拍摄序列分组后重新划分，再只对训练集在线增强，valid/test保留未增强原图；加入鸟、飞机、云、灯光、昆虫和纯背景等真实负样本。当前precision/mAP在清理泄漏前只能作为参考，不能作为最终验收基线。

训练数据不应简单按数量砍半，应保留多距离、多姿态、多天气、多背景的独立样本，删除相邻帧和增强副本冗余。量化校准则不需要使用全部1876张valid图；RKNN官方对normal算法建议约20～100张，Ultralytics建议300张以上。后续可从清理后的train中固定选取约300张代表性图片作为候选模型统一校准集，并保持test完全不参与训练和校准。校准数量不会改善推理速度，只影响量化精度和转换时间。

## 10. 后续训练候选

ReLU/ReLU6候选不能直接修改现有模型后投入生产。建议：

1. 加载`best.pt`；
2. 将Conv模块激活替换为ReLU/ReLU6；
3. 使用相同数据集充分微调；
4. 保存独立checkpoint；
5. 使用本文件的基线流程导出；
6. 先比较精度，再比较性能。

在维护者确认训练预算、训练设备和可接受精度下降前，不自动执行生产结构修改。

为了先判断是否值得投入重训，已提供`export_relu_performance_probe.py`。它把`best.pt`中Ultralytics `Conv`模块的SiLU直接替换为ReLU，保存独立PT后按同一opset19/W8A8/1876张校准集导出。该模型没有重新训练，只能用于测量Y2和`WorkLoad(0/1/2)`，其检测精度结论无效，禁止覆盖生产模型。

运行：

```bash
cd yolo_pt
python3 export_relu_performance_probe.py 2>&1 | tee export_relu_performance_probe.log
```

板端正常模式已验证显著收益：未重训ReLU探针Y2平均13.57ms、P95 19.02ms、P99 21.20ms，完整处理16.57ms，输入队列5.98ms，入口到完成25.58ms；同时间段SiLU生产模型Y2约25.62ms、完整处理29.09ms，分别降低约47%和43%。逐层报告进一步确认73个`ConvRelu`和14个`ConvReluAdd`均约33%/33%/33%分摊三核，合计5.208ms；旧模型87个单核`ConvExSwish`为17.524ms。总OP时间从27.804降至11.908ms，两个`exSDPAttention`绝对时间仍约2.469ms且全部在Core0，现占20.73%。正式模型改用ReLU6激活（训练见第12节，转换见第11节）。**已确认一次失败**：`yolov26_Relu.pt`来自`runs/single_cls_baseline_relu6-2`，训练脚本调用了`replace_activation(model.model, nn.ReLU6)`，但反汇编checkpoint后`Conv.act`的类引用是`torch.nn.modules.activation.SiLU`，模型yaml里也没有`activation`键，即该checkpoint实际是SiLU模型，不能作为ReLU6模型使用。性能探针模型没有重训，仍禁止依据当前识别结果替换生产模型。

根因是Ultralytics `train()`会按`model.yaml`重建网络后加载权重：只修改已加载模块的`module.act`，重建时会全部退回`Conv.default_act`（默认SiLU）。必须在调用`train()`**之前**把激活写进模型YAML，即`model.model.yaml["activation"]="nn.ReLU6(inplace=True)"`。另外`export_relu_performance_probe.py`中那行YAML写入是2026-09-10 11:10补的，而探针PT生成于10:24，因此该写法至今未经任何一次实际训练验证；探针PT的ReLU来自`model.save()`直接序列化内存实例，与YAML机制无关。修正后的训练脚本是`train_relu6.py`，它在`train()`前后各做一次激活校验（用`DetectionModel(cfg=model.model.yaml)`复现`train()`的重建行为），未通过就直接终止。

## 11. 重训ReLU6模型的转换流程

`pt_to_rknn.py`取代`pt_rknn.py`作为新checkpoint的转换入口，解决`pt_rknn.py`把`best.pt`路径和固定SHA-256写死、新训练出的模型无法转换的问题。脚本不接收命令行参数，源PT、输出目录和输出文件名在文件顶部的“配置区”里直接改。

配置区（只改这三行，其余保持默认）：

```python
ROOT = Path(__file__).resolve().parent

# 源 PT 模型（重训后的 ReLU6 模型）
PT_PATH = ROOT / "yolov26_Relu.pt"

# 转换产物目录
OUT_DIR = ROOT / "yolov26_Relu6_rknn_model"

# 产物主文件名，不含扩展名，最终生成 <OUT_NAME>.rknn
OUT_NAME = "yolo26n-drone-relu6"
```

同区还有`DATA_PATH`（校准data.yaml）、`PLATFORM`（默认`rk3588`）、`IMGSZ`（640）、`BATCH`（1）、`OPSET`（19）、`QUANTIZE`（8）、`FRACTION`（1.0），以及四个开关：

```text
EXPECT_ACTIVATION = "relu6"   期望激活；any 只统计，relu6 强制校验
SAVE_ONNX         = False     True 时保存中间归一化ONNX，供Netron核对
STRICT_VERSIONS   = False     True 时工具版本不一致直接失败
DRY_RUN           = False     True 时只检查激活与路径，不执行转换
FORCE             = False     True 时允许覆盖已存在的产物
VERBOSE_RKNN      = False     True 时打印RKNN Toolkit详细日志
```

运行：

```bash
cd yolo_pt

# 第一步：把 DRY_RUN 改成 True，核对激活函数、校准集与产物路径
python3 pt_to_rknn.py

# 第二步：改回 DRY_RUN = False 正式转换
python3 pt_to_rknn.py 2>&1 | tee export_yolo26n_drone_relu6.log
```

与既有脚本的关系：

- **转换内核完全一致**：仍走Ultralytics 8.4.131的RKNN专用导出路径（`format="rknn"`），自动关闭YOLO26 end2end/TopK并对框坐标按输入尺寸归一化，W8A8/normal/channel/optimization level 3与基线相同，因此产出的`[1,5,8400]`输出语义不变；
- `pt_rknn.py`保留为基线复现脚本（含固定哈希校验），不要改；
- `export_rknn_candidates.py`保留为FlashAttention/opset的A/B脚本，也不要用本脚本替代；
- 本脚本只做“单个已训练checkpoint → 单个可部署RKNN”。

产物：

```text
yolov26_Relu6_rknn_model/yolo26n-drone-relu6.rknn             部署用模型
yolov26_Relu6_rknn_model/yolo26n-drone-relu6.provenance.yaml  追溯记录
yolov26_Relu6_rknn_model/dataset.txt                          实际使用的校准清单
yolov26_Relu6_rknn_model/metadata.yaml                        Ultralytics导出元数据
yolov26_Relu6_rknn_model/yolo26n-drone-relu6.normalized.onnx   仅 SAVE_ONNX=True 时生成
```

`provenance.yaml`记录源PT的SHA-256与字节数、产物SHA-256与字节数、Ultralytics与RKNN Toolkit2版本、imgsz/batch/opset/quantize/fraction、校准集路径与SHA-256、期望激活、以及checkpoint激活函数统计和`model.yaml`中声明的`activation`。

三点硬约束：

1. **INT8量化必须给`DATA_PATH`**，否则RKNN无法构建；校准集仍用`drone.v1i.yolo26/data.yaml`（当前指向1876张valid），在按第9节重新划分数据前，该校准集只作为过程一致性的临时选择；
2. **`EXPECT_ACTIVATION`保持`"relu6"`**。它会在加载checkpoint后遍历所有带`act`属性的模块统计真实激活类型，若一个`ReLU6`都没有就直接失败。这是发现“训练实际仍是SiLU”的唯一可靠时机——`metadata.yaml`里的`activation`只反映Ultralytics的导出配置，不反映权重训练时用的激活。`PT_PATH`必须填`train_relu6.py`产出的`best.pt`（见第12节）；仓库里的`yolov26_Relu.pt`虽名为Relu，实测激活是SiLU，填它会被本检查直接拒绝，这是预期行为；
3. **注意探针用的是ReLU，正式模型用的是ReLU6**。两者在NPU上都走多核分摊的加速路径，但RKNN逐层报告里的算子名可能不同（ReLU探针显示为`ConvRelu`/`ConvReluAdd`），算子绝对耗时也不保证完全一致，第10节探针的Y2收益只能作为量级参考，不能当作ReLU6模型的性能结论。

转换完成后按第7节的A/B纪律执行：先做固定录制输入的FP32/INT8与旧模型精度对比，再测板端Y2和逐层核心分配。性能更快但检测结果错误的模型不得进入正式配置。

注意`model.export(name=...)`里的`name`是RKNN的`target_platform`（如`rk3588`），不是输出文件名；输出文件名由配置区的`OUT_NAME`决定，两者不要在沟通中混用。

## 12. ReLU6训练：激活被静默丢弃的问题与修正

### 12.1 现象

用于训练ReLU6模型的脚本里调用了`replace_activation(model.model, nn.ReLU6)`，训练也正常完成，但产出的checkpoint实际是SiLU模型。

反汇编三个checkpoint的pickle（`archive/data.pkl`）后，`GLOBAL`操作码给出的激活类引用是：

```text
best.pt                        torch.nn.modules.activation.SiLU   生产基线
best_relu_performance_probe.pt torch.nn.modules.activation.ReLU   性能探针
yolov26_Relu.pt                torch.nn.modules.activation.SiLU   ← 名为Relu，实为SiLU
```

`yolov26_Relu.pt`内嵌的训练参数进一步确认它来自`runs/single_cls_baseline_relu6-2`，起点权重`./weights/yolo26n.pt`，数据集`yolo_content/output/data.yaml`，与训练脚本完全对应。三个checkpoint的模型yaml都只有`nc / scales / backbone / head / reg_max / end2end`，**没有任何一个带`activation`键**。

因此`yolov26_Relu.pt`必须废弃或改名为`yolov26_relu_silu_failed.pt`之类，避免后续被误当成ReLU6模型送进转换流程。

### 12.2 根因

Ultralytics `Model.train()`内部：

```python
self.trainer.model = self.trainer.get_model(weights=self.model, cfg=self.model.yaml)
```

`get_model()`会`DetectionModel(cfg=model.yaml, nc=...)`**重新构造一个网络**，再用旧权重`load()`。`parse_model()`只从yaml读取激活：

```python
if act:
    Conv.default_act = eval(act)   # act 即 d.get("activation")
```

yaml里没有`activation`，`Conv.default_act`就保持默认的`nn.SiLU()`，重建出的Conv全部是SiLU；脚本在已加载实例上设的`module.act`随重建一起被丢弃。

`best_relu_performance_probe.pt`之所以成功，是因为探针脚本走`model.save()`，直接序列化内存实例，**没有经过`train()`**，与yaml机制无关。

### 12.3 修正

`train_relu6.py`在`train()`之前做三件事，并把校验放在训练之前：

```python
model.model.yaml["activation"] = "nn.ReLU6(inplace=True)"   # 唯一决定性的一步
replace_activation(model.model, nn.ReLU6)                    # 让内存模型立即正确，便于自检
Conv.default_act = nn.ReLU6(inplace=True)                    # 兜底
```

随后`verify_rebuild()`用`DetectionModel(cfg=model.model.yaml, nc=len(model.names))`**完整复现`train()`的重建行为**，统计重建网络里的激活构成；ReLU6为0或SiLU不为0就抛异常终止，不会白跑300轮。训练结束后再加载`best.pt`和`last.pt`各校验一次，打印PASS/FAIL并在失败时以非0码退出。

2026-09-11实测（run `single_cls_baseline_relu6_fixed`启动时的自检输出）：

```text
[激活] 已就地替换 105 个 SiLU 实例，并设置 Conv.default_act
[自检] 按 model.yaml 重建后的激活统计（train() 路径）：
        ReLU6: 105 个
        Identity: 9 个
[自检] 通过：重建网络使用 ReLU6，不会退回 SiLU。
```

105这个数字与性能探针当年的日志完全一致（`export_relu_performance_probe.log`：`已替换105个Conv模块的SiLU为ReLU`）。两处独立来源互相印证，说明yolo26n的SiLU激活模块总数就是105，两次替换都是全量替换。

**9个`Identity`不是漏替换的激活。** 重建走的是`model.yaml`（`parse_model()`执行`Conv.default_act = eval(act)`），只有被显式建成`act=False`的`Conv`才会拿到`nn.Identity()`（Ultralytics `Conv.__init__`里`act=False`的固定行为）。它们来自注意力块的`qkv`/`proj`/`pe`/`ffn`投影卷积与检测头等结构，属于架构固有，换不换激活都一样；第10节记录的探针板端逐层报告里也只有`ConvRelu`/`ConvReluAdd`，没有Swish类算子，可作旁证。

因此判据简化为：**`ReLU6 > 0`且`SiLU == 0`即通过，`Identity`属正常**。`train_relu6.py`已用配置区`EXPECTED_EXTRA_ACTIVATIONS = {"Identity"}`显式放行，只有出现其他激活才告警。

运行：

```bash
cd yolo_pt
python3 train_relu6.py 2>&1 | tee train_single_cls_baseline_relu6_fixed.log
```

只检查某个checkpoint、不训练：把配置区`CHECK_ONLY_PT`设为pt路径（如`"yolov26_Relu.pt"`），脚本只统计激活并返回退出码，可用于复核历史权重。

配置区常量：`MODEL`（起点权重）、`DATA`、`PROJECT`/`NAME`、`ACTIVATION`、`EPOCHS`/`IMGSZ`/`BATCH`/`DEVICE`/`WORKERS`/`SEED`/`OPTIMIZER`/`LR0`/`LRF`/`WARMUP_EPOCHS`/`SINGLE_CLS`、增强字典`AUGMENT`，以及续训用的`RESUME`/`RESUME_RUN_DIR`/`RESUME_OVERRIDES`（见第13节）。

### 12.4 训练参数的选择与验收标准

**换激活的目的不是做精度对照实验，而是让模型能在RK3588 NPU上三核并行。** SiLU在RKNN里会被拆成单核的`ConvExSwish`类算子（第8、10节：87个`ConvExSwish`合计17.524ms且全部落在Core0），ReLU6可融合为`ConvRelu6`/`Clip`，探针实测73个`ConvRelu`+14个`ConvReluAdd`三核各约33%分摊、合计5.208ms。收益来自算子融合与多核分摊，与训练时用了什么超参无关。

因此：

- **起点权重、epochs、batch、seed、learning rate、增强参数都不要求与SiLU基线对齐**，按训练效果自行选择。此前记录的“起点权重与超参必须逐项一致”只适用于“要把指标差异归因到激活函数”的场景，本项目不做这种归因，该约束作废；
- 换激活唯一的硬约束仍是第12.1～12.3节的激活生效问题：`model.yaml`里必须有`activation`，否则训练出来的仍是SiLU，上板不会有任何并行收益；
- 训练本身只验收两条：① 训练后激活计数正常（ReLU6 > 0、SiLU = 0）；② valid集mAP/recall不低于可接受水平，作为参考值记录，不作为与原基线的对比门槛。

真正的验收在板端和转换环节：

1. 逐层报告确认ReLU6相关算子落在NPU、**无CPU fallback**，且`ConvRelu6`类算子三核分摊（对照第10节的`ConvExSwish`全在Core0）；
2. 测板端Y2与完整处理时延，与SiLU生产模型对比（第10节探针的13.57ms只能作量级参考，因为探针用的是普通ReLU）；
3. 固定录制输入做FP32/INT8与旧模型的精度对比，性能更快但检测结果明显变差的模型不得进入正式配置（第7节）。

### 12.5 待确认

- 原SiLU基线的完整训练命令无需再归档：本项目不以“把指标差异归因到激活函数”为目的，ReLU6这一轮按训练效果独立选参数；
- `Conv.default_act`是Ultralytics进程级全局变量，同一进程内若先后加载SiLU与ReLU6模型并混用，需注意其可能被后设置的模型覆盖；本项目通过分别独立进程运行脚本规避该风险。
- **训练机的Ultralytics版本是8.4.146**（2026-09-11训练日志：`Ultralytics 8.4.146 / Python-3.12.13 / torch-2.13.0+cu130 / CUDA:0 A10`），与项目冻结的`8.4.131`不一致。训练侧版本差异不影响“激活是否真的生效”（判据是`model.yaml`的`activation`键与重建后的激活计数），也不影响转换——转换只看权重与yaml；但**若之后要在训练机上直接导出RKNN，必须先把版本对齐**，否则产物无法与第5节基线对比（见第11节`STRICT_VERSIONS`）。

## 13. 训练中断后的续训

### 13.1 先判断属于哪种中断

| 情形 | 判据 | 做法 |
|---|---|---|
| 训练跑到一半被打断（Ctrl+C、掉电、进程被杀、显存报错） | run目录下有`weights/last.pt`，且`epoch`字段有效 | 配置区`RESUME=True`续训，见13.2 |
| 训练已正常跑完全部epoch | `final_eval()`已对`last.pt`执行`strip_optimizer`：`epoch`被置为`-1`，`optimizer`/`ema`/`updates`/`scaler`/`best_fitness`全部置`None`，且**原地覆盖**该文件 | **不能续训**，只能当起点重训，见13.5 |
| 想改超参（epochs/batch/seed/增强）再继续 | —— | **不能用续训**：续训会忽略这些改动。改`MODEL`指向`last.pt`、`NAME`换新名重开一轮，见13.5 |
| `last.pt`损坏（进程被强杀，文件只写了一半） | 加载即抛异常 | 退回到`best.pt`或`save_period`留下的历史权重重训，见13.4、13.6 |

`strip_optimizer`会把`last.pt`就地改写成"不可续训"的推理态模型，这是"训练跑完之后再想接着练"失败的唯一原因，也让`epoch=-1`成为判断"是否还能续训"的可靠标志。

### 13.2 严格续训：把`RESUME`改成True

```bash
cd yolo_pt
# 配置区：RESUME = True
python3 train_relu6.py 2>&1 | tee -a train_single_cls_baseline_relu6_fixed.log
```

续训目标默认是`PROJECT/NAME`，即上一轮的输出目录；目录不同就写`RESUME_RUN_DIR`。恢复与不恢复的内容：

| 会从`last.pt`恢复 | 不会恢复 / 需注意 |
|---|---|
| 模型权重（含EMA） | 优化器状态缺失时以全新优化器开始，动量与学习率调度不延续（脚本会告警） |
| 优化器状态、梯度scaler | 传入的其他超参被静默忽略 |
| 学习率调度位置、已完成的epoch | 数据增强pipeline与`close_mosaic`的轮次判定（依赖已恢复的epoch，行为正确） |
| `best_fitness`（判定新best的依据） | —— |

run目录原地续写：不会新建`<NAME>2`，也不会覆盖更早的历史权重。反复中断就反复运行，脚本是幂等的。

### 13.3 续训时能改什么

Ultralytics只允许覆盖一小组参数，其余一律以checkpoint内保存的`train_args`为准，而且**不打印任何告警**：

```text
device / imgsz / batch / workers / cache / patience / time /
close_mosaic / augmentations / save_period / freeze / val /
plots / channels_last / save_dir / distill_model
```

（白名单来自`check_resume()`，见`ultralytics/engine/trainer.py`。）需要覆盖时写配置区的`RESUME_OVERRIDES`，例如换了卡号：`RESUME_OVERRIDES = {"device": "1"}`。`epochs`、`seed`、`lr0`、`optimizer`和全部增强参数都不在白名单里，改了不生效——要改就得走13.5。

### 13.4 续训路径下的ReLU6判据

`resume`不是"反序列化后接着跑"：`trainer.setup_model()`会`load_checkpoint(last.pt)`取出`weights`，再用`cfg = weights.yaml`调用`get_model(cfg, weights)`**重建一遍网络**（源码链路：`BaseTrainer.__init__ → check_resume → setup_model → get_model`）。也就是说，续训能不能保住ReLU6，与首次训练是**同一个判据**——checkpoint的`model.yaml`里有没有`activation`键：

- 用`train_relu6.py`发起的run：`activation`由脚本写入yaml并随checkpoint一起序列化，重建后仍是ReLU6；
- 用旧脚本发起的run（`single_cls_baseline_relu6` / `-2`）：yaml里没有`activation`键，重建即退回SiLU，**续训只会把SiLU一路训到底**，等于把之前的浪费继续放大。

因此`run_resume()`在调用`train(resume=True)`之前跑两道闸门，任一不通过立即终止：

1. 检查`last.pt`实例里的激活构成，要求`ReLU6 > 0`且`SiLU == 0`；
2. 用`DetectionModel(cfg=checkpoint的model.yaml)`复现重建行为，确认重建后仍全部是ReLU6。

同时打印checkpoint里的进度与配置（已完成epoch、`best_fitness`、`batch`/`seed`、`optimizer`/`lr0`、起点权重、数据集），用于确认"这就是要接着跑的那一轮"，而不是别的run的`last.pt`。`last.pt`损坏（半截文件）时给出明确中文指引，而不是抛torch原始异常。

### 13.5 不能续训时的替代做法

把`MODEL`改成要接续的权重（`last.pt`或`best.pt`），`NAME`换一个新名字，`RESUME`保持`False`，当普通训练发起：

- 仍会走`set_activation()`与`verify_rebuild()`，激活仍是ReLU6；
- epoch计数从0开始，优化器、学习率调度、EMA全部重置，**不等价于严格续训**；
- `EPOCHS`要按"还想再练多少轮"填，而不是总轮数。

注意这条路会重跑起点权重上已经练过的轮次（epoch计数从0开始），只是换取“能改超参”的自由度；本项目不要求与SiLU基线对齐，因此代价主要是训练时间。若这几轮的结果要写进结论，在本文档记清起点与轮数即可。

### 13.6 中断前的建议

- 长训练建议给`train()`加`save_period`（如5），把中间权重留在`<run>/weights/`下，万一`last.pt`损坏还有退路；`save_period`、`device`、`workers`、`batch`、`epochs`、`seed`、`lr0`、增强都只影响训练过程本身，与“换激活能否在NPU上三核并行”无关，可自由调；
- 中断后不要删`args.yaml`：它是这一轮超参的现场记录，也是`runs`目录里辨识run的凭据；
- 不要用`NAME`指向一个还没跑完的run去"重跑"，那会在同一目录新建递增run，容易和现场混淆；续训只有`RESUME=True`一条路。

### 13.7 待确认

- 上述`resume`内部行为（yaml重建、超参白名单、`strip_optimizer`置`epoch=-1`）是核对Ultralytics源码（main分支）得到的，**尚未在本项目的8.4.131上实测**；正式依赖前先在WSL2里跑一次短周期（如20轮）中断后续训，确认`[续训] 已完成 epoch`与日志里的epoch衔接正确。
