# 视觉目标稳定性判定实现文档

> 对应实现：`include/perception/visual_target_monitor.h`、`src/perception/visual_target_monitor.cpp`
> 更新：2026-09-11
> 上游契约：`include/perception/yolo_detector.md`（帧级观测 `VisualTargetObservation`）

## 功能职责

`VisualTargetMonitor`消费 `YoloDetector` 的**帧级单目标观测**，按帧节拍维护连续检测/连续
丢失计数、平滑后的目标像素中心与置信度，周期发布 `VisualTargetStatus`
（`SEARCHING / ACQUIRING / LOCKED / LOST`）。

当前做：

- 消费 `Topic<VisualTargetObservation>`；
- 累计连续检测帧数与连续丢失帧数；
- 对目标像素中心和置信度做指数滑动平均；
- 按门限判定锁定和丢失；
- 检测观测流中断（YOLO线程停止或卡死）并与“本帧无目标”区分；
- 周期发布影子状态，供日志、诊断和后续视觉跟踪门禁使用。

当前不做（边界）：

- 不做多目标ID、IoU匹配、主目标选举；
- 不做像素到机体系/NED的坐标转换（需要相机标定）；
- 不消费双目深度、光流或PX4姿态；
- 不做任何滤波预测（不做卡尔曼）；
- 不产生 `ControlIntent` 或 `Px4Setpoint`；
- 不修改 `target_tracker/` 独立库。

## 接口与数据流

```cpp
struct VisualTargetMonitorConfig {
    std::size_t input_queue_capacity = 2;
    std::chrono::milliseconds publish_interval{100};
    std::chrono::milliseconds observation_timeout{500};
    int lock_frames = 5;
    int lost_frames = 10;
    double smoothing_alpha = 0.3;
    void Validate() const;
};

class VisualTargetMonitor {
    bool Start();
    void Stop();
    bool IsRunning() const;
    void SetInput(common::Topic<common::VisualTargetObservation>& input);
    common::Topic<common::VisualTargetStatus>& StatusOutput();
    common::VisualTargetStatus LastStatus() const;
    uint64_t ObservationCount() const;
    uint64_t ErrorCount() const;
};
```

数据流：

```text
YoloDetector::ObservationOutput()
   │  Topic<VisualTargetObservation>（每个成功推理帧一条，允许 detected=false）
   ▼
VisualTargetMonitor 消费线程（逐帧推进状态机 + 周期发布）
   │
   ▼  Topic<VisualTargetStatus>（影子；当前无正式控制消费者）
```

输出字段要点：

- `state`：`kSearching/kAcquiring/kLocked/kLost`；
- `valid`：仅在 `kLocked` 时为 true，表示视觉已稳定锁定；
- `consecutive_detected_frames` / `consecutive_missed_frames`：连续计数；
- `center_pixel_x/y`、`confidence`：平滑后结果；
- `frame_width/frame_height`：最近观测的图像尺寸，供后续归一化与标定使用；
- `last_seen_ms`：最近一次有效检测的单调时钟时间；
- `header.frame_id=0`：像素坐标不属于 WGS84/NED 等空间坐标系。

## 状态机

每收到一条观测推进一次：

```text
detected = true:
    consecutive_detected += 1;  consecutive_missed = 0
    consecutive_detected >= lock_frames  → LOCKED
    否则                                  → ACQUIRING

detected = false（本帧推理完成但没有目标）:
    consecutive_detected = 0;  consecutive_missed += 1
    consecutive_missed >= lost_frames    → LOST
    否则若当前不是 LOCKED                 → SEARCHING
    否则（LOCKED 且未超丢失门限）          → 保持 LOCKED
```

周期检查（与观测无关）：

```text
observation_timeout 内未收到任何观测（含无目标观测）
    → LOST（数据中断）
```

设计取舍：

- **锁定后容忍短暂漏检**：YOLO偶发漏检不应立刻退出锁定，否则控制会频繁抖动。
  容忍上限为 `lost_frames`。
- **未锁定时漏检立即退回 SEARCHING**：尚未建立稳定锁定，没有理由继续保持 ACQUIRING。
- **观测超时与无目标分离**：这是本部件存在的核心理由。解码帧会被 YOLO 输入队列丢弃
  （容量为1），因此“没有检测消息”既可能是本帧无目标，也可能是线程停止。只有帧级观测
  才能把两者区分开；`observation_timeout` 专门捕捉后者。
- **多候选只做诊断**：上游已按单目标约定取置信度最高者，`candidate_count > 1` 只计入
  `ErrorCount()` 并节流告警，不改变状态机行为。
- **平滑只影响输出，不影响判定**：`smoothing_alpha` 只作用于发布的中心与置信度，
  锁定/丢失判定完全由帧计数决定，保证行为可预测、可测试。

## 关键实现点

- 线程模型与工程其他部件一致：`Start()` 启动消费线程；`Stop()` 先置停止标志、
  再 `input_sub.Reset()` 唤醒等待、最后 `join()`；`Start` 幂等，停止后重启会重新订阅。
- 消费循环的等待上限取 `min(publish_interval, 20ms)`，兼顾发布节奏和停止响应。
- 未绑定输入时 `Start()` 返回 false 并计一次 ERROR，不静默空转。
- `Start()` 会复位稳定性状态（计数、平滑、锁定），但累计计数
  `ObservationCount()` 不清零，便于跨重启统计。
- 仅 `last_status_` 由互斥锁保护供跨线程读取；其余状态为消费线程独占，不加锁。
- 观测队列容量默认 2（丢最旧）：视觉状态用最新观测即可。

## 配置

`config/config.json`：

```json
"runtime": {
  "enable_visual_monitor": true
},
"visual_monitor": {
  "input_queue_capacity": 2,
  "publish_interval_ms": 100,
  "observation_timeout_ms": 500,
  "lock_frames": 5,
  "lost_frames": 10,
  "smoothing_alpha": 0.3
}
```

约束：

- `enable_visual_monitor=true` 时必须 `enable_video=true`（观测来源是 `YoloDetector`）；
- 队列容量、发布周期、观测超时、`lock_frames`、`lost_frames` 必须为正；
- `smoothing_alpha` 必须在 `(0,1]`。

门限说明：`lock_frames=5`（约25FPS下200ms）和 `lost_frames=10`（约400ms）是影子阶段初值，
必须用实拍视频复核后再作为视觉接管门禁，当前不得据此开放控制。

## 日志行为

| 场景 | 等级 | 节流 |
|------|------|------|
| 创建/销毁/启动/停止 | INFO | 否 |
| 观测输入未绑定导致启动失败 | ERROR | 否 |
| 观测超时判定丢失 | WARN | 第 1 次 + 每满 100 次 |
| 收到多目标候选（按最高置信度处理） | WARN | 第 1 次 + 每满 100 次 |
| 逐帧观测与逐周期状态 | 不打日志 | — |

状态变化本身不打日志，避免25FPS下的状态抖动刷屏；需要跟踪时序时通过
`StatusOutput()` 或 `LastStatus()` 观察。

## 测试方式

```bash
cmake -S . -B build
cmake --build build -j$(nproc)
./build/visual_target_monitor_test
ctest --test-dir build --output-on-failure
```

测试覆盖：

- 配置校验：非法队列容量、帧数和 `smoothing_alpha` 拒绝构造；
- 未绑定输入时拒绝启动；
- Start/Stop 幂等；
- 从未检测时保持 `SEARCHING`；
- 连续检测达到 `lock_frames` 前为 `ACQUIRING`，达到后为 `LOCKED`；
- 锁定后短时漏检保持 `LOCKED`，达到 `lost_frames` 进入 `LOST`；
- 未锁定时漏检立即退回 `SEARCHING`；
- 观测流中断超过 `observation_timeout` 判定 `LOST` 并计入错误；
- 多候选计入错误计数；
- 重启后状态复位。

香橙派验证：

1. 摄像头对准无人机或相似目标，观察状态从 `SEARCHING → ACQUIRING → LOCKED`；
2. 移开目标，观察短暂保持 `LOCKED` 后进入 `LOST`；
3. 停止 YOLO（或断开摄像头），观察 `observation_timeout` 触发的“视觉观测超时”告警；
4. 确认不影响视频、图传和地面站链路；
5. 确认日志未出现逐帧刷屏。

## 排查 / 修改要点

- **一直不锁定**：先看 `YoloDetector::ObservationCount()` 是否增长。不增长说明推理未成功，
  与门限无关。
- **目标明显在画面中却频繁 LOST**：检查 `lost_frames` 是否过小，以及YOLO置信度阈值是否
  导致漏检；不要为了“看起来稳定”直接把 `lost_frames` 调大而忽略漏检根因。
- **状态抖动**：检查是否 `lock_frames` 过小或画面中目标低于置信度阈值反复进出检测。
- **误报超时**：确认 `observation_timeout` 大于正常推理间隔（当前推理约13～28ms，
  100～500ms 足够），不要小于单帧最坏耗时。
- **修改关联**：
  - `VisualTargetStatus` 字段与 `docs/数据接口文档.md` 冻结，改动需同步文档；
  - 判定逻辑改动需同步本文件的状态机小节与 `visual_target_monitor_test`；
  - 后续接入状态机门禁时，只允许消费 `valid` 和 `state`，不得在本部件内生成控制意图；
  - 双目接入后，本部件仍只负责“视觉是否稳定看到目标”，空间位置由双目与PX4姿态链路
    单独产出，不得把本部件改造成空间估计器。
