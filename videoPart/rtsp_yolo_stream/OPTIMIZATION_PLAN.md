# RK3588 RTSP + YOLO 视频链路修复与优化方案

## 1. 文档目的

本文档针对 `videoPart/rtsp_yolo_stream` 当前“RTSP 拉流 → RKNN YOLO26 检测 → 画框 → RTSP 推流”程序的低帧率、高延迟和断线互相影响问题，给出可分阶段实施、验证和回滚的修复方案。

本文档只描述修复设计，不代表相关代码已经完成修改。实施时应按阶段提交，每一阶段在 RK3588 实机上验收后再进入下一阶段。

相关总体设计：

- [项目系统架构](../../docs/系统架构设计.md)
- [视频编解码与目标检测设计](../../develop-ideal.md#2-视频编解码与目标检测-视频处理线程--目标识别线程)
- [YOLO26 RKNN 推理说明](../yolo26-rknn/README.md)

## 2. 适用范围

本次修复范围包括：

- `src/main.cpp`：视频链路编排、看门狗、重连和性能统计。
- `src/rtsp_decoder.cpp`：FFmpeg RTSP 拉流、rkmpp 解码和解码帧输出。
- `src/rtsp_encoder.cpp`：颜色转换、rkmpp 编码和 RTSP 写包。
- `../yolo26-rknn/src/yolo26_detector.cpp`：检测器公共接口。
- `../yolo26-rknn/src/rknn_model.cpp`：RGA 预处理、RKNN 推理和后处理。
- `../yolo26-rknn/src/rga_utils.cpp`：裁剪、缩放及颜色转换。

不在本次范围内：

- PX4 控制策略和飞行状态机。
- YOLO26 模型训练和数据集调整。
- 摄像头固件及地面站播放器实现。
- 未经实测直接替换 FFmpeg、MPP、RGA 或 RKNN 运行时版本。

## 3. 当前实现基线

### 3.1 当前执行架构

当前实现是“单处理线程同步串行流水线 + 看门狗线程”：

```text
主处理线程：
RTSP读取/解码
    -> YOLO预处理与同步推理
    -> CPU后处理
    -> OpenCV画框
    -> 编码
    -> RTSP同步写包

看门狗线程：
监控最后一次成功取帧时间
    -> 超时后设置全局网络中断标志
```

主线程通过一个复用的 `cv::Mat frame` 直接调用各模块。模块之间没有消息队列、帧池或异步调度。任一阶段阻塞都会暂停整条链路。

### 3.2 当前数据通路

```text
RTSP/TCP H.264 或 H.265 AVPacket
    -> FFmpeg 解封装
    -> rkmpp 硬解码
    -> DRM_PRIME/NV12 硬件帧
    -> av_hwframe_transfer_data：转存至系统内存
    -> sws_scale：NV12 转全分辨率 BGR
    -> cv::Mat 正方形 ROI
    -> ROI 非连续时 clone
    -> RGA：缩放并将 BGR 转 RGB
    -> 640x640 RKNN 输入内存
    -> rknn_run 同步推理
    -> CPU：NC1HWC2 转 NCHW、解码、NMS
    -> OpenCV 在原始 BGR 帧画框
    -> sws_scale：BGR 转 NV12
    -> rkmpp 硬编码
    -> av_interleaved_write_frame：RTSP/TCP 推流
```

MPP、RGA 和 NPU 都已使用，但解码帧在进入推理前被转回 CPU BGR，编码前又从 BGR 转回 NV12，因此当前链路不是端到端零拷贝。

### 3.3 已观测性能

仓库现有 `rtsp_yolo_stream.log` 记录：

| 指标 | 观测值 |
|------|--------|
| 稳定阶段解码 | 24.0 ms/帧 |
| 稳定阶段检测 | 52.8 ms/帧 |
| 稳定阶段编码推流 | 21.9 ms/帧 |
| 稳定阶段总耗时 | 98.7 ms/帧 |
| 稳定阶段吞吐 | 约 10.1 FPS |
| 全程运行时间 | 58 s |
| 全程成功帧数 | 170 |
| 全程平均帧率 | 2.9 FPS |
| 最长一次“解码”耗时 | 10460.5 ms |
| 看门狗触发 | 2 次 |

`2.9 FPS` 包含输出 RTSP 连接拒绝、固定 3 秒重连等待、网络阻塞和输入重连，不能等同于算法吞吐。170 个成功帧累计总处理时间约 17.59 秒，活跃处理吞吐约 9.7 FPS。

当前统计还存在口径混合：

- “解码耗时”包含网络等待、解码、硬件帧转存和 NV12→BGR。
- “检测耗时”包含裁剪拷贝、RGA、`rknn_run`、输出重排和 NMS。
- “编码推流耗时”包含 BGR→NV12、硬编码和网络写包。
- 某一阶段成功但后续阶段失败时，阶段耗时会被记录，而“总帧耗时”不会被记录。

因此现有最终阶段平均值和最大值不能直接相加，也不足以定位每个硬件单元的真实耗时。

## 4. 根因分析

### 4.1 串行执行限制吞吐

稳定阶段串行吞吐上限约为：

```text
1000 / (24.0 + 52.8 + 21.9) = 约 10.1 FPS
```

解码、NPU和编码之间没有重叠执行。即使三者分别由硬件加速，主线程仍会等待每一阶段完成。

### 4.2 没有实时丢帧策略

需求输入为 1080p、25 FPS，而当前处理能力约 10 FPS。RTSP 使用 TCP 时，应用层消费速度持续低于摄像头发送速度，数据可能在摄像头、网络栈或 FFmpeg 内部积压。

当前低延迟 FFmpeg 参数只能减少部分内部缓存，不能代替应用层的最新帧队列。若不主动丢弃过期帧，画面延迟可能不断增加。

### 4.3 输入和输出故障互相影响

当前输入和输出共用 `g_net_interrupt`。输出写包阻塞可能触发全局中断并影响输入读取。

首次创建输出链路失败时，异常处理会同时释放已经创建的输入解码器。输出 RTSP 服务不可用会导致程序反复重建输入和输出，扩大故障范围。

### 4.4 全分辨率CPU颜色转换和多次拷贝

当前每帧至少包含：

- DRM/MPP 解码帧转存到系统内存。
- 全分辨率 NV12→BGR。
- 非连续正方形 ROI 的 `clone()`。
- RGA 将裁剪图缩放并转成模型 RGB 输入。
- 全分辨率 BGR→NV12。
- rkmpp 编码器内部导入软件 NV12 帧。

以 1920×1080 为例，一张 BGR 帧约 6.22 MB；居中裁剪为 1072×1072 后，额外 clone 约 3.45 MB。频繁的大块内存读写会增加 CPU、DDR 和缓存压力。

### 4.5 RKNN上下文没有形成多帧并行

模型创建了三个 RKNN 上下文，但检测器固定使用 `ctx_index = 0`。上下文0设置了 `RKNN_NPU_CORE_ALL`，不代表只使用一个NPU核心；但另外两个上下文没有参与多帧并行，仍会占用输入、输出和上下文资源。

### 4.6 推理失败和“未检测到目标”语义相同

当前 `YOLO26Detector::detect()` 在非法输入或推理失败时返回空检测列表。主循环无法区分：

- 推理成功但画面中没有目标。
- RGA预处理失败。
- `rknn_run()`失败。
- 后处理失败。

主循环随后仍会编码发送未画框的原图。视频可继续发送，但控制模块无法可靠判断感知链路是否健康。

### 4.7 输出时间戳与真实处理速率可能不一致

编码PTS按固定 `frame_count_` 递增，编码器FPS来自输入标称FPS或命令行覆盖值。如果标称25 FPS而实际只产生10 FPS，媒体时间戳、包到达节奏和真实采集时间会不一致，可能造成播放器缓冲、抖动或延迟判断错误。

## 5. 修复目标与待确认项

### 5.1 必须满足的功能目标

- 输出RTSP故障不得导致输入RTSP重复重建。
- 图传拥塞不得反压摄像头解码和感知控制链路。
- 队列满时优先保留最新帧，不允许无界积压。
- 每帧携带源时间、接收时间、序号和当前处理状态。
- 推理失败必须与“无目标”区分，并产生健康事件。
- 单帧失败只丢弃该帧；连续模块失败才触发模块重建。
- H.264和H.265输入能力保持与当前实现一致，不因重构被硬编码为单一格式。
- YOLO26当前模型为非end-to-end、无DFL输出；修复不得误引入YOLO11的DFL解码逻辑。

### 5.2 建议的阶段性性能目标

以下是用于验证修复效果的建议门槛，最终数值应在实施前由项目负责人确认：

| 阶段 | 建议目标 |
|------|----------|
| 网络稳定性修复 | 输出服务不可用时输入仍持续更新最新帧；恢复输出后无需重建模型 |
| 有界流水线 | 稳定吞吐不低于15 FPS；队列不出现持续增长 |
| 数据通路优化 | 1080p输入下稳定吞吐向25 FPS目标靠近 |
| 实时性 | 稳态端到端延迟P95建议不超过200 ms，且不随运行时间增长 |
| 稳定性 | 连续运行30分钟无无界内存增长、死锁或非预期链路互相重置 |

如果最终要求“1080p、25 FPS、每帧都必须完成YOLO后才能发送”，则最慢处理阶段必须稳定低于40 ms，或者使用多个推理上下文进行帧级并行。

### 5.3 实施前必须确认

- 是否要求每个输出帧都执行YOLO，还是允许低频检测、其余帧使用跟踪结果。
- 输出标注视频要求使用H.264还是H.265。
- 输出视频必须保持1080p，还是允许缩小到720p或模型输入尺寸。
- 目标稳定帧率是15、20还是25 FPS。
- 最大允许端到端延迟及P95/P99验收阈值。
- 推理失败时应发送原图、使用最近一次有效检测结果，还是丢弃该帧。
- RTSP输出服务的启动顺序、鉴权和断线协议。

## 6. 目标架构

### 6.1 线程模型

建议拆分为四个逻辑执行单元：

```text
┌────────────────────┐
│ 输入线程            │
│ RTSP读取 + MPP解码  │
└─────────┬──────────┘
          │ DecodedFrame，容量1~2，满时覆盖最旧帧
          ▼
┌────────────────────┐
│ 感知线程            │
│ RGA + RKNN + 后处理 │
└─────────┬──────────┘
          │ AnnotatedFrame/DetectionResult，容量1~2
          ▼
┌────────────────────┐
│ 编码线程            │
│ 叠框 + MPP编码      │
└─────────┬──────────┘
          │ EncodedPacket，有界缓冲
          ▼
┌────────────────────┐
│ 输出线程            │
│ RTSP封装 + 网络写包 │
└────────────────────┘

控制/健康管理：分别监控输入、感知、编码、输出的新鲜度和错误计数
```

实际操作系统线程数允许根据FFmpeg、MPP和RKNN后端调整，但模块职责、队列契约和故障隔离不得改变。

### 6.2 队列策略

| 队列 | 建议容量 | 满时策略 | 最大消息年龄 |
|------|----------|----------|----------------|
| 解码帧队列 | 1~2帧 | 丢弃最旧帧，保留最新帧 | 由目标延迟确定 |
| 检测结果/标注帧队列 | 1~2帧 | 丢弃最旧帧 | 由目标延迟确定 |
| 编码包队列 | 有界 | 不允许无限积压；拥塞时重建输出会话或丢弃到下一关键帧 | 由一个GOP上限约束 |
| 健康事件队列 | 小容量事件队列 | 不使用覆盖式最新值替代所有事件 | 配置化 |

禁止使用无界 `std::queue`。每个队列必须统计：

- 当前深度和历史最大深度。
- 入队、出队和丢弃计数。
- 队首帧年龄。
- 消费等待时间。

### 6.3 内存所有权

图像使用固定容量内存池和RAII句柄：

```cpp
enum class PixelFormat {
    kNv12,
    kBgr888,
    kRgb888,
};

struct FrameMetadata {
    uint64_t sequence = 0;
    int64_t source_pts_us = 0;
    int64_t receive_time_us = 0;
    int width = 0;
    int height = 0;
    int horizontal_stride = 0;
    int vertical_stride = 0;
    PixelFormat format = PixelFormat::kNv12;
};

struct FrameHandle {
    FrameMetadata metadata;
    // RAII持有DRM/MPP/DMA-BUF或内存池块，不使用裸指针管理生命周期。
};
```

跨线程只传递句柄和元数据，不逐级复制整张图像。消费者完成后自动归还缓冲。

### 6.4 感知结果语义

检测接口应返回明确状态，而不是只返回数组：

```cpp
enum class DetectionStatus {
    kOk,
    kInvalidInput,
    kPreprocessFailed,
    kInferenceFailed,
    kPostprocessFailed,
};

struct DetectionFrameResult {
    uint64_t frame_sequence = 0;
    int64_t source_pts_us = 0;
    DetectionStatus status = DetectionStatus::kOk;
    std::vector<Detection> detections;
};
```

`status == kOk && detections.empty()`才表示“推理成功但未发现目标”。

## 7. 分阶段实施方案

### 阶段0：建立可信性能基线

#### 修改内容

将现有粗粒度计时拆分为：

```text
输入：
  av_read_frame
  avcodec_send_packet/receive_frame
  av_hwframe_transfer_data
  NV12→BGR

感知：
  ROI准备/clone
  RGA预处理
  rknn_run
  输出布局转换
  解码与NMS

输出：
  画框
  BGR→NV12
  avcodec_send_frame/receive_packet
  av_interleaved_write_frame
```

同时记录：

- P50、P95、P99和最大耗时。
- 输入、输出实际帧率。
- 当前解码器和编码器名称。
- 队列深度、丢帧数和帧年龄。
- 从源PTS或接收时刻到写包完成的端到端延迟。
- CPU、NPU、RGA、DDR负载以及板卡温度。

关闭 `rknn_model::run_inference()` 中逐帧 `printf()`，改为每秒或每100帧汇总。

#### 验收

- 各阶段样本口径一致，成功帧和失败帧分别统计。
- 能明确区分网络等待、颜色转换、NPU和后处理耗时。
- 运行日志确认解码器确实为 `h264_rkmpp` 或 `hevc_rkmpp`，不得静默使用软件回退而不告警。

### 阶段1：修复RTSP故障隔离

#### 修改内容

- 输入、输出分别持有中断标志、最后活动时间和错误计数。
- 输入初始化和输出初始化拆成独立状态机。
- 输出创建失败时保留输入解码器和最新帧，不重新加载RKNN模型。
- 输入断开只重建输入；输出断开只重建输出。
- 固定3秒阻塞等待改为可中断的指数退避，最大间隔配置化。
- 看门狗分别监控输入数据新鲜度、感知完成新鲜度和输出写包新鲜度。
- 连续错误达到阈值后才重建模块；单帧错误只记录并跳过。

#### 验收场景

1. 输出RTSP服务器未启动，输入仍能持续解码并更新最新帧。
2. 运行中停止输出服务器，输入和YOLO不被重建。
3. 恢复输出服务器后，仅输出链路恢复。
4. 断开摄像头网络，输入按退避策略重连，输出线程不发生死锁。
5. Ctrl+C可在规定时间内退出所有线程。

### 阶段2：引入有界流水线和最新帧策略

#### 修改内容

- 将输入解码、感知、编码和网络输出拆为独立执行单元。
- 引入容量1~2的解码帧队列和检测结果队列。
- 队列满时丢弃最旧的未处理帧。
- 每帧携带序号和时间戳，检测结果必须按序号关联原帧。
- 输出拥塞只能造成图传帧丢弃或输出重连，不得反压感知和控制。
- 停止流程使用原子运行标志和队列关闭通知，不使用永久阻塞等待。

#### 理论收益

按当前稳定数据，三级计算流水的理想吞吐上限约为：

```text
1000 / max(24.0, 52.8, 21.9) = 约 18.9 FPS
```

流水化提高吞吐，但不会自动降低单帧计算耗时。最新帧覆盖负责避免排队延迟持续增加。

#### 验收

- 输入25 FPS、感知低于25 FPS时，队列深度保持有界。
- 运行10分钟后端到端延迟没有随时间单调增长。
- 网络输出阻塞时感知结果仍持续更新。
- 丢帧计数与输入、感知帧率差值基本一致。

### 阶段3：低风险图像通路优化

#### 修改内容

1. RGA直接读取原图stride和裁剪矩形，输出模型输入，取消正方形ROI的 `clone()`。
2. 使用RGA替代CPU `sws_scale` 完成编码前BGR→NV12。
3. 复用所有中间缓冲，禁止逐帧分配大块图像内存。
4. 后处理直接读取RKNN原生输出布局，或实测比较原生布局解析与NC1HWC2→NCHW重排。
5. 为局部向量和候选框缓冲预留容量，减少逐帧扩容。

#### 验收

- ROI准备阶段不再发生整块 `clone()`。
- CPU颜色转换耗时明显下降。
- 检测框坐标与优化前录制视频结果一致。
- RGA失败能返回明确错误，不得产生越界或继续使用未初始化图像。

### 阶段4：DMA-BUF零拷贝数据通路

#### 前置调研

在编码前先验证当前板端版本是否支持并兼容：

- MPP解码输出外部 `MppBufferGroup`/DRM缓冲。
- RGA通过DMA-BUF文件描述符读取NV12并写入目标缓冲。
- RKNN输入 `rknn_tensor_mem` 与RGA目标缓冲的导入或共享方式。
- MPP编码器直接接收可复用NV12硬件缓冲。
- 缓存同步、stride、像素格式和缓冲生命周期要求。

不得仅根据API名称假定零拷贝已经生效，必须通过耗时、CPU占用和内存带宽实测确认。

#### 目标数据通路

```text
RTSP压缩包
    -> MPP解码到NV12 DMA-BUF
       ├-> RGA裁剪 + 缩放 + NV12→RGB -> RKNN输入内存
       └-> 原NV12帧/复用表面 -> 硬件叠框或RGA合成 -> MPP编码
```

目标是取消：

- `av_hwframe_transfer_data()`整帧下载。
- 解码后的全分辨率NV12→BGR。
- YOLO裁剪clone。
- 编码前CPU BGR→NV12。

#### 验收

- 对比优化前后CPU占用、DDR带宽和阶段耗时。
- 连续运行30分钟无DMA缓冲泄漏、句柄泄漏和缓存一致性错误。
- 分辨率变化时能够重建BufferGroup和下游RGA/RKNN描述信息。

### 阶段5：NPU并行与模型策略

仅在阶段2~4仍无法达到目标帧率时实施。

#### 方案A：单上下文

- 保留一个RKNN上下文。
- 使用 `RKNN_NPU_CORE_ALL`。
- 优点是实现简单、内存占用低、结果天然有序。

#### 方案B：三个上下文帧级并行

- 创建三个独立上下文。
- 分别绑定 `CORE_0`、`CORE_1`、`CORE_2`。
- 三个推理工作单元处理不同帧。
- 结果携带帧序号；实时模式下可直接使用最新完成结果，不为等待旧帧而积压。

不得让多个并发上下文都绑定 `CORE_ALL` 后直接上线，必须先进行A/B测试，确认NPU调度、DDR竞争、温度和持续吞吐。

#### 可选降载策略

若业务允许，不要求每个视频帧都执行YOLO，可采用：

- YOLO按固定频率检测。
- 中间帧使用ByteTrack等跟踪器更新目标位置。
- 图传保持较高帧率，结构化检测结果按感知频率更新。

引入第三方跟踪库前必须评估许可证、ARM64支持、依赖复杂度和维护活跃度。

## 8. 时间戳与帧同步

### 8.1 时间字段

每帧至少保留：

- 摄像头/RTSP源PTS。
- 算力板接收时间。
- 解码完成时间。
- 推理开始和完成时间。
- 编码完成时间。
- 网络写包完成时间。

内部超时统一使用单调时钟。墙钟只用于人类可读日志。

### 8.2 编码PTS

不能只按“成功处理帧数÷标称FPS”生成时间。应根据输入PTS或单调时钟计算输出PTS：

- 未丢帧时尽量保留输入时间关系。
- 丢帧时PTS应跨过对应时间，不把旧帧压缩到连续固定间隔。
- 输出时间基和帧率配置必须与实际策略一致。
- 输入PTS异常时回退到单调时钟，并记录告警。

### 8.3 检测结果关联

检测结果必须通过 `frame_sequence` 与原始帧关联。不得仅依赖“当前最新检测结果”，否则流水并发后可能把旧检测框画到新帧上。

若业务选择“最近检测结果叠加到后续帧”，必须设置最大结果年龄，超过阈值后停止使用并标记感知过期。

## 9. 异常处理策略

| 故障 | 单次处理 | 连续失败处理 |
|------|----------|--------------|
| RTSP读超时 | 中断本次读取并记录 | 仅重建输入链路 |
| 解码坏帧 | 丢弃坏帧 | 重建解码器并上报健康事件 |
| RGA失败 | 丢弃当前感知任务 | 重新初始化RGA相关缓冲 |
| RKNN失败 | 返回明确失败状态 | 重新初始化对应上下文/模型 |
| 编码失败 | 丢弃当前输出帧 | 仅重建编码器 |
| RTSP写超时 | 中断写包 | 仅重建输出会话 |
| 队列满 | 丢弃最旧帧 | 记录持续过载告警，不扩大队列 |
| 帧过期 | 不进入控制链路 | 记录感知新鲜度异常 |

任何输出故障都不得停止结构化检测结果向控制模块发布。图传可降级，控制链路不能被图传网络反压。

## 11. 测试计划

### 11.1 单元测试

- 有界队列满时丢弃最旧帧。
- 队列关闭能够唤醒等待线程。
- 帧序号和检测结果正确关联。
- PTS换算覆盖丢帧、重复PTS、回退PTS和无PTS情况。
- 输入、输出状态机互不影响。
- 推理失败和无目标返回不同状态。
- Letterbox裁剪和坐标反映射覆盖横屏、竖屏、奇数尺寸及16对齐尺寸。

硬件接口通过mock注入，不要求单元测试访问真实MPP、RGA、RKNN或RTSP服务。

### 11.2 录制视频回放测试

- 使用固定H.264/H.265录制流重复回放。
- 对比改造前后目标类别、置信度和框坐标。
- 记录误差阈值，避免RGA裁剪或颜色格式改变造成精度回退。
- 测试1080p/25 FPS持续输入，验证丢帧和延迟策略。

### 11.3 故障注入测试

- 启动时输出RTSP服务不可用。
- 运行中停止并恢复输出服务。
- 运行中断开并恢复摄像头网络。
- RTSP服务器只建立连接但不再发送数据。
- 输出服务接收极慢，制造写包阻塞。
- RGA、RKNN和编码器mock连续返回错误。
- 运行中改变输入分辨率。
- 高频Ctrl+C和正常退出，检查线程及缓冲释放。

### 11.4 RK3588实机测试

每个版本至少记录：

- 输入、感知、编码和输出FPS。
- 端到端延迟P50/P95/P99/最大值。
- 各队列最大深度和丢帧率。
- CPU各核心利用率。
- NPU负载和频率。
- RGA、VPU使用情况。
- DDR带宽（平台工具可用时）。
- 芯片温度、降频和持续运行稳定性。
- 内存、文件描述符和DMA缓冲数量。

短时峰值结果不能代替持续运行结果。

## 12. 验收标准

在目标帧率和延迟数值确认后，最终验收至少包括：

- 连续运行30分钟无崩溃、死锁和资源持续增长。
- 输出服务器断开不会重建输入解码器或RKNN模型。
- 输入25 FPS、处理不足25 FPS时，帧年龄保持有界，不随运行时间持续增长。
- 图传阻塞不影响结构化检测结果的新鲜度。
- 推理失败能够上报，不伪装成“未发现目标”。
- 输入重连、输出重连和模块重置次数分别统计。
- H.264/H.265输入按已确认范围通过测试。
- 检测精度与当前基线相比没有不可接受回退。
- 日志可以区分网络、编解码、RGA、NPU和后处理耗时。

## 13. 风险与回滚

### 13.1 主要风险

- DMA-BUF在不同MPP/RGA/RKNN版本之间存在兼容差异。
- 多线程后缓冲生命周期错误可能导致DMA内存泄漏或使用已释放帧。
- 多上下文NPU并行可能因DDR竞争而没有线性加速。
- 结果异步返回可能造成检测框与帧错配。
- 编码包不能任意丢弃，丢弃预测帧可能使接收端持续花屏直到下一关键帧。
- 改变颜色转换路径可能影响模型输入颜色顺序和检测精度。

### 13.2 回滚原则

- 每个阶段单独提交，不把网络、线程、零拷贝和多NPU上下文一次性合并。
- 保留上一阶段可运行实现和配置开关。
- 阶段3之后的图像通路优化必须支持回退到软件帧路径，便于比较和应急。
- 多上下文推理默认关闭，实测通过后再启用。
- 任一阶段若出现精度回退、资源泄漏或稳定性下降，回滚该阶段，不影响已通过验收的前序修复。
